# M9 SC1 스톱워치 재측정 — 새 표면으로 5분 내 접속

상태: 기준 확정, 예행·공식 캠페인 미실행.

## 1. 목적과 지위

`docs/PRD.md` §15가 성공 기준 1번과 2번으로 각각 이렇게 적는다.

> 신규 두 장비의 최초 연결을 5분 이내에 완료한다.
> 등록된 host에는 한 개의 명령으로 접속한다.

`docs/ROADMAP.md` M9의 DoD 1은 이걸 실행 가능한 절차로 옮긴다.

> SC1 스톱워치 재측정 — 새 표면으로 독립 3회, 5분 이내, `docs/campaigns/m7-stopwatch.md` 선례 형식을 계승한 캠페인 문서로 baseline(M7 DoD 1 측정치, Q4에 따라 현행 표면으로 먼저 잰다) 대비 단축 기록.

이 캠페인은 M2 mobility 캠페인과 다르다. M2는 참고 자료였고 실패 회차가 마일스톤을 막지 않았다. 이 캠페인은 M6 MCP 캠페인·M7 스톱워치 캠페인과 같은 자리에 있다 — **DoD 1 그 자체이며 합격/불합격 게이트다.** 3회 전부가 5분 이내여야 하고, 그 중앙값이 baseline(M7 3회의 중앙값)보다 짧아야 M9을 닫을 수 있다(§5).

`docs/ROADMAP.md` M9 결정 기록 Q4는 시점을 이렇게 못박는다: "현행 표면으로 먼저 baseline 3회 측정 후, 새 표면으로 재측정해 DoD에서 비교한다." 이 문서가 §8에서 baseline 3회와 재측정 3회를 같은 자리에 기록하는 이유다 — `m7-stopwatch.md`의 3회는 아직 수행되지 않았다(§8 참고).

## 2. 대상 문서

`README.md`의 "First run" 절 하나만 — "Quick start" 절도, "Security posture" 절도 아니다. 피실험자에게는 이 절 외에 아무것도 열어주지 않는다.

M9의 "First run" 절은 두 장비를 pin하는 네 가지 경로(fingerprint 손대조 → `--fingerprint` 없이 다이얼해 첫 연결에서 확인하는 경로 → `qsh pair invite`/`qsh pair accept` 코드 페어링("세 번째 방법") → `qsh identity export` + `qsh trust add --cert-file` 인증서 파일 교환("네 번째 방법"))를 순서대로 소개한다. 이 캠페인이 측정하는 것은 그 절이 **가장 먼저** 제시하는 경로, 즉 fingerprint 손대조 경로다 — 인사이더가 고를 법한 가장 빠른 경로가 아니라, 절을 위에서 아래로 읽는 낯선 사용자가 실제로 밟는 경로를 재는 것이 §5의 PASS 규칙("피실험자가 README \"First run\" 절에 적힌 명령·순서를 그대로 따랐다")의 취지이기 때문이다. 나머지 세 경로는 이 캠페인의 측정 대상이 아니다.

측정 종점은 그 절 안에서도 이르게 온다. "First run" 절은 `qsh dave@box`로 첫 셸을 얻은 뒤에도 코드 페어링·인증서 교환·`hosts.toml` 이야기를 계속하지만, 스톱워치는 첫 셸에서 멈춘다.

## 3. 전제 조건 — "한 번도 설정한 적 없다"의 조작적 정의

두 장비 각각에서 아래가 전부 사실이어야 타이머를 시작할 자격이 있다.

- `$XDG_CONFIG_HOME/qsh`(보통 `~/.config/qsh`)가 없다 — `identity.toml`, `trust.toml`, `acl.toml`, `hosts.toml`, `config.toml` 전부 부재.
- `$XDG_STATE_HOME/qsh`(보통 `~/.local/state/qsh`)가 없다 — `resume.json`, `audit.log` 부재.
- OS 자격 증명 저장소(macOS Keychain, Linux Secret Service)에 `service=qsh` 항목이 없다.
- `$PATH`상에 다른 `qsh` 실행 파일이 없다 — 테스트 대상 바이너리 하나만 해석된다.
- README가 예시로 쓰는 포트(`4433`)를 선점한 프로세스가 없다.
- 잔존 `qsh serve` / `qsh serve --to`(구 `qsh reverse`) / `qsh listen` 프로세스가 없다.
- `qsh service status`가 "미등록"이다(`installed: false`, `docs/CLI.md` §6.18) — M9는 `qsh service install`로 launchd/systemd 유닛을 깔 수 있으므로, 이전 회차가 남긴 유닛이 살아 있으면 타이머 시작 자격이 없다.

이걸 매번 손으로 보장하는 가장 확실한 방법은 회차마다 새로 만들고 끝나면 버리는 **두 개의 VM 또는 컨테이너**를 쓰는 것: `$HOME`이 비어 있으면 위 조건이 전부 자동으로 성립하고, 피실험자는 README에 없는 환경 변수(`QSH_CONFIG_DIR` 등)를 몰라도 된다. README의 "First run" 절 자체가 그런 변수를 요구하지 않으니, 피실험자가 타이핑하는 명령은 README에 적힌 것 그대로여야 한다. 실장비 2대를 쓸 경우 위 7개 항목을 회차 시작 전 손으로 지우고 확인한다.

컨테이너 쪽 준비는 `scripts/stopwatch/`가 맡는다 — `m7-stopwatch.md` §3이 쓴 것과 같은 하네스(`scripts/stopwatch/round.sh N`)를 그대로 재사용하되, 일곱 번째 조건(`qsh service status`)의 검사를 더한다.

두 장비는 서로 실제 네트워크 경로로 도달 가능해야 한다 — 같은 머신의 loopback으로 대신하면 "두 장비"라는 전제 자체가 무너진다. 같은 LAN이나 브리지 네트워크의 VM 두 대면 충분하다.

### 진행자용 사전 점검 체크리스트 (타이머 밖, 진행자가 수행)

피실험자가 아니라 **진행자**가 타이머 시작 전에 아래를 확인한다. 확인 자체는 qsh 명령을 쓰지 않는다 — qsh 명령을 미리 실행해 보면 그게 곧 연습이 되어 버린다.

1. 두 장비 모두 §3의 7개 조건 확인.
2. `which -a qsh` (Windows는 `where qsh`)로 PATH 그림자 없음 확인. 이 시점엔 아직 `qsh init`을 안 해서 `qsh doctor`를 쓸 수 없다 — identity가 없으면 `doctor.run`은 조회 자체를 시작하지 못하고 exit 255로 실패한다(`docs/CLI.md` §6.17).
3. `lsof -i :4433` 또는 동등 명령으로 대상 포트에 남은 프로세스 없음 확인.
4. `ps aux | grep qsh` 로 잔존 `qsh serve`/`serve --to`/`listen` 없음 확인.
5. `~/Library/LaunchAgents/io.qsh.*.plist`(macOS)와 `~/.config/systemd/user/qsh-*.service`(Linux)가 없음을 확인 — 있으면 이전 회차가 `qsh service install`로 남긴 유닛이다. `launchctl bootout`/`systemctl --user disable --now`로 내린 뒤 파일을 지운다.
6. 두 장비 사이 물리적 네트워크 경로가 살아 있음을 ping 등 qsh 아닌 도구로 확인(선택 — 이미 알고 있으면 생략 가능).
7. 스톱워치와 기록 표(§6) 준비.
8. 피실험자에게 README "First run" 절만 열어준다. 다른 절은 닫아 두거나 접근을 막는다.

## 4. 두 터미널의 배치 — 한 사람, 화면 분할로 고정

지문을 옮기고 대조하는 구간이 README도 자인하는 최대 병목이라, 두 터미널을 어떻게 보는지가 회차마다 다르면 측정치가 재현되지 않는다. 이 캠페인은 `m7-stopwatch.md` §4와 같은 배치로 고정한다.

**한 사람이 한 화면에 두 터미널을 나란히 띄워 놓고(탭 분할이든 창 두 개든) 스스로 오간다.** 음성이나 채팅으로 지문을 불러주는 두 사람 릴레이 방식은 쓰지 않는다.

이유는 단순하다. 두 사람 릴레이는 qsh의 UX가 아니라 두 사람 사이의 통신 지연을 재는 셈이 된다. SC1이 재려는 건 "이 소프트웨어가 얼마나 빨리 붙는가"지 "전화로 숫자를 불러주는 데 얼마나 걸리는가"가 아니다.

## 5. 사전 정의된 합격/불합격 기준 (실행 전에 고정, 사후 조정 없음)

| 항목 | 정의 |
|---|---|
| 타이머 시작 | 피실험자가 README "First run" 절의 첫 명령(호스트 쪽 `qsh init --json`)에 첫 키를 입력하는 순간 |
| 타이머 종료 | 클라이언트 쪽 `qsh dave@box`(또는 그에 대응하는, README 그대로 따른 이름)를 실행한 뒤 원격 셸 프롬프트가 화면에 처음 나타나는 순간 |
| 예산 | 300초(5분), 회차당 |
| 회차 PASS | 시작~종료가 300초 이내이고, 피실험자가 README "First run" 절에 적힌 명령·순서를 그대로 따랐다(진행자 개입 없음) |
| 회차 FAIL | 300초 초과, 또는 피실험자가 막혀서 README 문면만으로 종점에 도달하지 못함(진행자가 힌트를 주면 그 시점부터 FAIL 확정) |
| 캠페인 PASS | 독립 3회 전부 PASS |
| 캠페인 FAIL | 3회 중 하나라도 FAIL — §7의 처분을 따른다 |
| baseline 비교 | m7 3회 중앙값 대비 m9 3회 중앙값이 짧아야 DoD 1 충족 — 같은 진행자·같은 날 측정된 두 세트만 비교한다 |

"독립 3회"는 **환경의 독립**을 뜻한다 — 회차마다 §3의 일곱 조건을 처음부터 다시 충족한 상태에서 시작한다(설정·자격 증명·프로세스·포트·서비스 유닛 전부 새로). 사람의 독립까지는 요구하지 않는다: 같은 조작자가 3회를 연달아 수행해도 캠페인 자체는 유효하다. 다만 같은 사람이 반복하면 두 번째, 세 번째 회차는 타이핑 속도와 절차 암기로 빨라지는 게 당연하므로, 1회차를 진짜 최초 노출로 삼는 걸 원칙으로 하고, 2·3회차에 학습효과가 있었다면 §8 기록표 비고란에 그렇게 적는다 — 학습효과를 감추고 평균만 내지 않는다.

## 6. 측정 프로토콜과 기록 템플릿

피실험자가 치는 명령은 README "First run" 절의 fingerprint 경로 문면 그대로다 — 이 문서가 명령을 대신 정하지 않는다. `acl.toml`을 손으로 작성하는 구간(2행)은 M9에서도 변하지 않는다 — ADR-0017이 어떤 명령도 `acl.toml`을 쓰지 않는다고 못박았고(§6.18), `m7-stopwatch.md` §9의 예행은 기계 시간이 5분 예산의 0.25% 미만이고 나머지는 사실상 전부 사람 시간(문서 읽기·acl.toml 손으로 쓰기·fingerprint 옮겨 적고 대조하기·터미널 오가기)이라고 기록했을 뿐, 그 네 항목 중 어느 하나를 병목으로 지목하지는 않았다 — fingerprint 대조 구간이 최대 병목이라는 판단은 위 §4가 README 스스로의 자인에 근거해 내리는 것이다. 그래서 이 캠페인은 큰 폭의 단축을 미리 약속하지 않는다 — fingerprint 경로 자체는 M9에서 달라진 것이 거의 없고(주소의 포트 생략은 이 경로가 그대로 쓰는 `--address host:4433` 표기에 영향을 주지 않는다), 단축이 있다면 §5의 baseline 비교 행이 실측으로 보여준다.

| # | 단계 | 담당 | 유형 | 비고 |
|---|---|---|---|---|
| 1 | `qsh init --json` | host | 기계 | fingerprint 출력 확인 |
| 2 | acl.toml 손으로 작성 | host | 사람 | README의 `[[acl]]` 스니펫을 그대로 옮겨 적음 |
| 3 | `qsh serve --bind 0.0.0.0:4433` | host | 기계 | 백그라운드로 남겨 둠 |

## 7. 실패 시 처분

300초를 넘긴 회차가 나오면 먼저 원인을 분류한다.

- **README 문면의 결함** (피실험자가 문면을 정확히 따랐는데도 막혔다) → README를 고치고, 그 시점부터 3회 카운트를 처음부터 다시 시작한다. 고치기 전 회차와 고친 후 회차는 서로 다른 문면을 측정한 것이라 같은 캠페인으로 묶을 수 없다.
- **제품 결함** (문면대로 했는데 qsh 자체가 기대와 다르게 동작했다) → 이슈로 승격하고 M9 백로그 또는 즉시 수정 대상으로 분류한다. README를 손대는 문제가 아니므로 문면 수정 없이 제품을 고친 뒤 재측정한다.
- **환경/진행자 잡음** (§3 사전 점검을 놓쳐 leftover 프로세스·포트 충돌·leftover 서비스 유닛 같은 게 섞였다) → 그 회차는 PASS도 FAIL도 아닌 **무효**로 기록하고 카운트에서 뺀다. 사전 점검을 다시 하고 새 회차로 대체한다.

사후에 5분 기준 자체를 늘리거나, 실패한 회차를 조용히 빼고 성공한 회차만 보고하는 건 하지 않는다 — §5의 기준은 처음 커밋된 그대로 남는다.

## 8. 환경 기록과 실행 기록 (공식 캠페인 수행 시 채운다)

**baseline과 재측정은 같은 진행자가 하루 안에 이어서 수행한다.** `m7-stopwatch.md`의 3회 측정은 그 문서가 커밋된 뒤로 아직 수행되지 않았다(그 문서 머리말(제목 바로 아래)의 "상태" 줄이 그대로 "공식 캠페인 미실행"이다) — 따라서 이 캠페인의 실행자는 먼저 M9 이전 바이너리(아래 "pre-M9 baseline 커밋"에서 빌드)로 `m7-stopwatch.md`의 3회를 수행해 baseline을 채우고, 이어서 현재 바이너리로 이 문서의 3회를 수행한다. 두 세트를 서로 다른 날, 서로 다른 진행자가 재면 §5의 baseline 비교 행이 재는 것이 표면의 차이인지 사람·환경의 차이인지 구분할 수 없다.

pre-M9 baseline 커밋: `525a2a5`(2026-09-16, `build(deps): rustls 0.23.45 로 lockfile 갱신`) — M9 실행 계획이 `PLAN.md`를 교체한 첫 커밋 `86f8578`("M9 실행 계획으로 PLAN.md 교체")의 바로 앞 부모다.
