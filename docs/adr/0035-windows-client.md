# ADR-0035: Windows는 Linux·macOS와 같은 기능을 연다. client 쪽(콘솔 raw 모드 attach, named pipe localctl과 listener 데몬)과 host 쪽(ConPTY 백엔드의 `serve`·`serve --to`, 작업 스케줄러 서비스 백엔드)을 정방향·역방향 모두 연다

날짜: 2026-10-11 (개정 2026-10-13, 같은 날 두 번째·세 번째 개정, 승인 2026-10-14, 개정 2026-10-15, 2026-10-16)
상태: 승인됨

개정 이력: 2026-10-15에 M16이 착지시킨 두 결정의 Windows 귀속을 기록한다. 결정 14(M19)의 `qsh listen`과 결정 25(M20)의 `qsh serve --to`는 ADR-0031(신뢰 철회 시 연결 닫기)의 재검증 감시를 같은 코드로 쓰고, 그 Windows 쌍둥이 테스트(`crates/qsh-testkit/tests/it/trust_withdrawal.rs`의 `listen`·`serve_to` 모듈, 오늘 `cfg(unix)`)는 각각 M19, M20이 연다. ADR-0044의 자동 부트스트랩은 Windows의 대화형 attach와 `qsh cp`가 M19라 그 분기를 M19가 켜고(결정 1·5), 명시 명령 `qsh pair ssh`는 결정 1대로 M16 착지와 함께 Windows client에서 열렸으며, 응답자 `qsh pair ssh-respond`는 결정 25대로 M20이다. 다른 결정은 바뀌지 않는다. 2026-10-16에 결정 12의 Credential Manager 항목 target을 착지한 형태로 적는다. 구현은 `windows-native-keyring-store`(keyring-core 1)의 기본 이름 방식을 그대로 써서 target이 `<device_id>.qsh`이고 사용자 이름이 `device_id`다. Credential Manager 항목은 target만으로 주소가 정해지므로 맨 `qsh`로 두면 설정 디렉터리 둘이 서로의 키를 덮어쓴다. store의 `target` modifier를 명시하면 사용자 이름이 기록되지 않아 쓰지 않았고, 이름 방식이 crate 갱신으로 바뀌는 것은 실제 항목을 대조하는 `credential_manager_round_trip_on_the_runner`가 잡는다. 결정 12의 "target `qsh`"는 이 줄이 이긴다. 결정의 나머지(형식, 지속성, blob, `auto` 폴백)는 그대로다. 2026-10-16에 결정 14의 conduit에 Windows의 half-close를 더한다. byte 모드 named pipe에는 쓰기 방향만 닫는 방법이 없어, conduit이 `qsh.local.v1` 메시지에서 터널의 날 바이트 중계로 넘어간 뒤의 바이트를 Windows에서는 청크로 싣는다. 청크는 4바이트 big-endian 길이와 그만큼의 바이트이고, 길이 0은 쓰는 쪽이 자기 방향을 끝냈다는 뜻이다(half-close). 길이 상한은 65536이고, 상한을 넘는 길이나 끝 청크 뒤의 바이트는 프로토콜 오류로 보고 I/O 오류와 같은 abort로 conduit을 닫는다. 그래서 reverse route의 `-L` 연결에서 로컬 앱이 쓰기만 닫고 응답을 기다리는 경우도 unix와 같이 동작한다. unix의 UDS는 원래 half-close를 하므로 바이트가 그대로이고, Windows localctl은 M19 전에 배포된 적이 없어 버전 차이 문제가 없다. 청크 형식은 `docs/design/protocol.md`의 localctl 절이 적는다. 2026-10-16에 결정 15를 착지한 형태로 적는다. 절전 감지의 단조 시계 표본은 `client/wake.rs`의 표본 함수(`mono_sample`) 하나가 플랫폼별이고, Windows에서는 `QueryUnbiasedInterruptTime`(100 ns 단위)을 읽어 고정 anchor `Instant`에 카운터가 앞으로 간 만큼을 더한 `Instant`로 돌려준다. 이 모양이라 감지 알고리즘(`WakeSense`, `WAKE_TICK`, `WAKE_SKEW`)과 tokio 타이머는 모든 플랫폼에서 같은 코드다. 표본 함수 옆에 `cfg(windows)` 모듈(`windows_sample`)과 출처 상수 `MONO_SAMPLE_SOURCE`, 틱 변환 `unbiased_ticks_to_duration`이 따라붙고, 테스트가 paused 시계를 주입할 수 있게 `WakeDetector::with_mono_source`가 생겼다. 카운터를 읽지 못하면 표본은 `Instant::now`로 떨어져 감지기가 이전 동작이 된다. 결정 내용은 바뀌지 않고, 이 ADR 맥락 절의 "확인되지 않았다"는 착수 시점의 서술로 읽는다. 실제 절전 복귀는 결정 18의 캠페인 회차 (4)가 본다. 2026-10-16에 결정 6·7(콘솔 복원과 대화형 attach)과 결정 26 마지막 항목(client get의 로컬 쓰기)을 착지한 형태로 적는다. 콘솔 닫기·로그오프·종료 이벤트는 unix의 SIGHUP처럼 detach이고, Windows는 핸들러가 돌아오는 순간 프로세스를 끝내므로 클라이언트는 모드를 복원한 뒤 QUIC 연결을 먼저 닫고 그 전송이 끝날 때까지 최대 4초 핸들러를 붙잡는다. 그래서 호스트는 연결 유실이 아니라 정상 detach로 세션을 본다. ADR-0044 자동 부트스트랩의 ssh 자식이 도는 동안 입력 핸들은 cooked 모드(줄 편집, 에코, 시스템 Ctrl-C 처리)이고 VT 입력 모드는 ssh가 끝난 뒤 attach가 켠다. client 로컬 쓰기는 `*at` 호출이 없는 Windows에서 디렉터리를 `FILE_FLAG_BACKUP_SEMANTICS`로, `FILE_SHARE_DELETE` 없이 연 핸들 아래의 경로로 다루고, 마지막 구성 요소는 `FILE_FLAG_OPEN_REPARSE_POINT` 또는 `CREATE_NEW`로 열어 symlink·junction을 거부한다(unix `O_NOFOLLOW`의 대응). 임시 파일은 결정 9의 소유자 전용 DACL로 만들고 rename 직전 보호를 풀어 디렉터리의 상속 ACL을 받는다. mode는 합성한다(읽기 전용 특성이면 파일 `0o444`, 아니면 `0o644`, 디렉터리 `0o755`). 읽기 전용 특성은 mode의 소유자 쓰기 비트가 꺼졌을 때만 쓰고 `-p`는 `SetFileTime`으로 수정 시각만 맞춘다. 결정 내용은 바뀌지 않는다.

개정 관계: 새 ADR이다. `docs/ROADMAP.md` M19(§5)가 이 번호를 Windows 착수 ADR로 예약했다. 첫 개정(2026-10-13)은 정방향과 역방향은 같은 기능을 갖는다는 사용자 결정(`docs/PRD.md` §4 '연결 방향과 역할의 분리', `docs/ROADMAP.md` §5.1 원칙 7)에 따라 초안이 닫아 둔 `qsh listen`과 localctl 대체(named pipe)를 열었다. 두 번째 개정(2026-10-13)은 "정방향, 역방향, 모든 플랫폼에서 평등한 기능 지원"이라는 사용자 결정을 반영한다. 동등은 방향 사이만이 아니라 Linux·macOS·Windows 사이에도 성립해야 하므로, 첫 개정이 남겨 둔 예외(host 역할 두 방향의 P2, Windows `qsh service` 부재, 콘솔 초대 코드 프롬프트 거부, 절전 감지 미확인, 역방향 CI의 test-only 하니스)를 걷어 낸다. 결정 2·3·10·11·15~19와 맥락·근거·대안·결과를 고쳤고, host 역할(결정 20~26)과 서비스 매니저 백엔드(결정 27~28)를 새로 더했다. 결정 번호 1~19의 주제는 그대로 두어 다른 ADR의 인용이 깨지지 않게 했다. 세 번째 개정(2026-10-13)은 두 번째 개정이 남긴 열린 질문과 남는 차이에 대한 사용자 답("전부 다 알아서 진행해. 원칙에 예외는 없어. Windows도 코드 서명 진행해.")을 반영한다. 신호 `Quit`·`Usr1`·`Usr2`에 Windows 의미를 주고(결정 22), man 페이지를 Windows 자산에도 싣고(결정 16), Authenticode 서명과 winget·scoop 배포를 범위에 넣고(결정 16), 로그인 세션 밖 상시 기동을 Linux linger와 같은 수준으로 열고(결정 27), 서비스 쪽 열린 질문 넷(`manager` 값, 숨김 진입점, doctor finding, 실행 상태 질의)을 정했다(결정 27·28). 마일스톤은 M19 Windows client와 M20 Windows host로 나뉘었고 결과 절이 결정마다 착지할 마일스톤을 적는다.

승인 2026-10-14: 사용자 위임 결정("전부 다 알아서 진행해")으로 승인했다. 세 번째 개정이 닫은 질문 외에 남아 있던 Windows Credential Manager crate가 없을 때 `platform`을 접는 예외(결정 12)를 직접 API 구현 대체로 바꿔 예외를 없앴고, ADR-0032와 ADR-0033이 정한 `qsh service --activate/--live`·`identity move-key`·`qsh audit`의 Windows 동작과 상시 기동 Credential Manager 가정(결정 12·27·28)을 맞췄다.

다른 ADR의 결정을 뒤집지 않는다. 다만 아래 ADR의 Windows 문장은 이 ADR의 승인을 조건으로 바뀌었다. ADR-0044 결정 10의 "플랫폼이 Windows면 `unsupported_platform`"과 결정 25의 "응답자 쪽 Windows는 결정 10대로 거부한다"는 결정 25(이 ADR)로 대체되고, ADR-0044(승인됨)는 2026-10-14 승인 때 결정 10·14·25에 이를 반영했다. ADR-0032(승인됨)의 매니저 호출 표는 2026-10-14에 Windows 열을 얻었고 결정 28이 그 열의 근거다. ADR-0029(승인됨)의 host 쪽 파일 op에는 Windows 구현 규칙(결정 26)이 붙고, `acl.toml` `paths`의 Windows 표기는 ADR-0029 결정 23이 정한다. ADR-0007(resume token custody)에는 "Windows에서 `resume.json`의 기밀성"이라는 빈칸을 채우는 구현을 더한다. ADR-0043(TCP fallback 철회)로 transport는 QUIC 하나이므로 Windows 방화벽·프록시 환경을 위한 우회 경로는 이 ADR의 범위가 아니다. `docs/PRD.md` §4와 §7은 이 개정과 함께 고쳤다. 나머지 계약 문서와 설계 문서는 결정 19의 목록대로 착지 때 고친다.

## 맥락

`docs/PRD.md` §7은 Windows client와 Windows host를 모두 P1에 둔다(2026-10-13 사용자 결정 이전에는 host가 P2였다). 오늘 Windows 빌드는 CI에서 컴파일되고 portable 테스트를 도는 수준이다(`ci.yml`의 `test`·`clippy` Windows leg, `release.yml`의 `x86_64-pc-windows-msvc` zip). 지원 약속은 아니다. 실제로 Windows에서 되는 것과 안 되는 것은 이렇다.

- `exec`, `trust`, `identity`, `tunnel open`(`-L`/`-R`/`-D`), `session` value op는 터미널이나 UDS에 기대지 않아 그대로 돈다. `release_smoke`의 `#[cfg(not(unix))]` 쌍둥이가 `init` → `trust` → `exec --json` 왕복까지 본다.
- 대화형 attach(`tui::run`)는 `#[cfg(not(unix))]`에서 `UNSUPPORTED`다. raw 모드는 `nix` termios, 크기는 `TIOCGWINSZ`, resize는 `SIGWINCH`라서 `crates/qsh-cli/src/tui/term.rs`와 `tui/unix.rs`가 통째로 unix 전용이다. `docs/design/architecture.md` §8은 crossterm을 "TUI는 키를 파싱하지 않고 raw byte를 흘려야 한다"는 이유로 채택하지 않았고, 그 이유는 Windows에서도 그대로다.
- localctl(UDS)은 `localctl/` 모듈 트리 전체가 `#[cfg(unix)]`라서 Windows에서 컴파일되지 않는다. 데몬의 소켓은 `$XDG_RUNTIME_DIR/qsh/<pid>.sock`(없으면 `<state_dir>/run/<pid>.sock`)이고 디렉터리 0700, 소켓 0600이며, accept마다 프레임을 읽기 전에 peer euid를 `UnixStream::peer_cred`(Linux `SO_PEERCRED`, macOS `getpeereid`)로 대조한다(`crates/qsh-core/src/localctl/mod.rs` 모듈 doc의 신뢰 모델). 그 게이트가 `qsh listen`의 기동 경로(`reverse/listen.rs`의 `run_listen_unix`)와 reverse hub·conn table·등록 처리의 쌍둥이 메서드, client 쪽 `client/link.rs`의 `Local` 경로, `ops/exec.rs`의 reverse 분기까지 번져 있어서, 오늘 `qsh listen`은 Windows에서 `UNSUPPORTED`이고 `qsh hosts`는 forward host만 낸다(`docs/CLI.md` §6.13). 터널은 열린 프로세스에만 산다(`docs/CLI.md` §6.14). target 경로 자체(`reverse/target`)는 테스트 빌드에서 이미 Windows에서 컴파일되지만 `qsh serve --to`는 `windows_unsupported()`로 막혀 있다.
- 키·상태 파일의 권한이 없다. `ensure_private_dir_io`와 `write_private_file_io`는 `cfg(not(unix))`에서 `create_dir_all`과 모드 없는 임시 파일 + rename(`fsutil::write_atomically`)으로 떨어져, 파일은 상위 디렉터리의 상속 ACL을 받는다. audit 로그와 그 디렉터리(`audit.rs`), 회전 잠금과 재검증(`audit/writer.rs`의 `lock_path`·`revalidate`)도 `cfg(unix)`다. `crates/qsh-core/src/resume.rs` 모듈 doc은 이 상태를 적고 `resume.json`의 기밀성을 Windows client P1의 일부로 둔다. host 쪽 `acl.toml`의 group/world-writable 경고(`acl/load.rs`의 `warn_if_group_or_world_writable`)는 `cfg(unix)`이고 README Known limitations는 "Windows ACL checking is out of scope"라고 적는다.
- keystore는 Windows에서 stub이다. 모든 연산이 `KeyStoreError::Unavailable`을 내므로 `auto`는 파일 모드로 떨어진다(`identity/keystore.rs`). 파일 모드의 개인키는 위 상속 ACL에 놓인다.
- 초대 코드를 터미널에서 받는 프롬프트는 에코 억제가 없어 `UNSUPPORTED`다(`NO_TERMINAL_ECHO_SUPPRESSION`).
- host 역할에는 PTY가 없다. PTY 백엔드(`pty/posix.rs`)가 `#[cfg(unix)]`이고 `pty::factory()`가 비unix에서 `UnsupportedFactory`를 돌려준다. `qsh serve`는 Windows에서 뜨지만 PTY 세션을 열 수 없고 `exec`와 터널만 낸다. 그 `exec`도 unix의 process group 종료(`exec/mod.rs`의 `kill_group`)와 로그인 환경 고정(`pinned_identity_env`)이 없어 `qsh serve` 프로세스의 환경을 그대로 물려준다. `user@` 힌트 대조(`server/mod.rs`의 `lookup_login_name`)는 비unix에서 늘 불일치다.
- `qsh service install|uninstall|status`는 launchd와 systemd 사용자 유닛만 안다(`crates/qsh-core/src/ops/service/mod.rs`, `SERVICE_UNSUPPORTED_PLATFORM`). 매니저는 `cfg!(target_os)`만으로 정하고, 다른 플랫폼은 무엇도 읽거나 쓰기 전에 `UNSUPPORTED`다.
- 절전 감지(`client/wake.rs`)는 벽시계와 단조 시계(`tokio::time::Instant`)의 차이를 쓴다. Windows에서 `Instant`가 절전 중에 멈추는지는 확인되지 않았고, 멈추지 않으면 감지기가 울리지 않는다.

설계를 가르는 사실은 셋이다.

- 동등의 기준이 바뀌었다. 첫 개정까지의 선은 "client 역할은 열고 host 역할은 두 방향 모두 P2"였다. 방향 간 동등은 지켰지만 플랫폼 간 동등은 아니었다. 2026-10-13 사용자 결정은 모든 플랫폼에서 같은 기능을 요구하므로, Linux·macOS에서 되는 명령은 Windows에서도 되어야 하고 남는 차이는 그 플랫폼에 개념 자체가 없는 것뿐이어야 한다.
- 대화형 attach가 client 가치의 대부분이고, ConPTY 백엔드가 host 가치의 대부분이다. 나머지는 이미 돌거나 unix 구현을 Windows 수단으로 옮기는 일이다.
- Windows에 host가 생기면 한 러너 안에서 정방향·역방향 종단 테스트를 실제 CLI로 돌릴 수 있다. 첫 개정이 test-only 하니스와 사람 캠페인으로 나눠 둔 몫 대부분을 CI가 가져온다.

## 결정

### A. 명령 집합

1. Windows에서 여는 명령은 Linux·macOS와 같다. 연결 방향과 역할에 관계없이 연다. 직접 연결(direct route)에서 나가는 명령과 reverse route 위의 명령이 같은 명령 이름이다.
   - client 쪽: `qsh init`, `qsh identity export`, `qsh trust add|add-ca|list|rename|remove`, `qsh trust ssh-preview`, `qsh cert init|issue`, `qsh identity move-key`(ADR-0032 결정 15), `qsh audit`(ADR-0033), `qsh pair accept`(인자, `--code-stdin`, 콘솔 프롬프트 모두, 결정 11), `qsh pair ssh [--reverse]`(ADR-0044 결정 25와 22), `qsh exec`, `qsh session open|get|read|write|resize|close`, `qsh sessions`, `qsh tunnels`, `qsh tunnel close`, 대화형 `qsh [user@]host`와 `qsh attach <session-ref>`(결정 5~8), `qsh tunnel open --local|--remote|--dynamic`과 대화형 `-L`/`-R`/`-D`, `qsh cp`(ADR-0029, 결정 26), `qsh listen`과 `qsh setup listener`(결정 14), `qsh doctor`, `qsh setup client`, `qsh acl check`, `qsh acl show`, `qsh hosts`, `qsh host`, `qsh schema|capabilities|version`.
   - host 쪽: `qsh serve`(인바운드, 결정 20~24), `qsh serve --to`와 숨김 alias `qsh reverse`(결정 25), `qsh setup host`(`--to` 형태 포함), `qsh pair invite`, `qsh pair ssh-respond`(ADR-0044 응답자, 결정 25).
   - 서비스: `qsh service install|uninstall|status`와 `qsh setup listener --service`·`qsh setup host --service`(결정 27).
   - `qsh cp`의 로컬 operand는 한 글자 뒤의 `:`를 드라이브 문자로 보고 로컬로 해석한다(ADR-0029 결정 2의 operand 해석 문장과 짝이다). 받은 파일의 권한은 결정 26의 규칙을 따른다. ADR-0029와 ADR-0044가 착지하기 전이면 `qsh cp`와 `pair ssh`/`pair ssh-respond`는 그 착지와 함께 열린다.
2. 플랫폼을 이유로 닫는 명령은 없다. 오늘 Windows에서 `UNSUPPORTED`를 내는 경로(`windows_unsupported()`, `SERVICE_UNSUPPORTED_PLATFORM`의 Windows 분기, `tui::run`의 비unix 분기, `NO_TERMINAL_ECHO_SUPPRESSION`, `ops/exec.rs`의 reverse 분기, `UnsupportedFactory`)는 모두 걷어 낸다. 원칙에 예외를 두지 않는다(2026-10-13 사용자 결정). Windows에 같은 이름의 OS 개념이 없는 기능(POSIX 신호, `man`, systemd linger)도 Windows 수단으로 같은 관찰 가능한 동작을 정의해 연다(결정 16·22·27).
3. 동등을 테스트가 고정한다. `crates/qsh-cli/tests/it/exit_code_matrix.rs`에는 Windows 전용 `UNSUPPORTED` 행이 하나도 없다. 대신 `cfg(windows)` 행 하나가 `qsh session close --signal <SIG>`의 허용 값 일곱 개가 Windows host에서 모두 성공(exit `0`)함을 단언한다. 다른 명령은 Windows leg의 기능 테스트(결정 17)가 맡는다. `cfg(unix)`로 빠져 있던 테스트는 이 마일스톤에서 `cfg(windows)` 쌍둥이를 갖는다. 쌍둥이를 가질 수 없는 테스트(POSIX 신호 번호, `$$`, `setsid`처럼 개념 자체가 unix인 것)는 빠진 이유를 주석으로 남기고, 같은 성질을 Windows 수단으로 보는 테스트(Job Object 종료, ConPTY 신호 사상)를 따로 둔다.

### B. 콘솔과 대화형 attach

4. Windows 콘솔 제어는 `windows-sys`의 Win32 콘솔 API를 `qsh-cli`의 `tui/`에 직접 쓴다. crossterm은 채택하지 않는다(`docs/design/architecture.md` §8의 이유 유지). `qsh-core`는 콘솔을 모른다. 대화형 루프는 `tui/unix.rs`에서 플랫폼 중립 부분(escape 처리, 이벤트 루프, 스레드 구성, 종료 코드 매핑)을 꺼내 작은 터미널 trait(raw 모드 guard, 창 크기 조회, stdin 읽기, 끊김 신호)에 올리고, unix와 Windows가 각자 구현한다. 이 추출은 unix 동작을 바꾸지 않는다.
5. raw 모드는 입력 핸들에서 `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, `ENABLE_PROCESSED_INPUT`을 끄고 `ENABLE_VIRTUAL_TERMINAL_INPUT`을 켠다. 출력 핸들은 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`과 `DISABLE_NEWLINE_AUTO_RETURN`을 켠다. 입출력 코드 페이지는 UTF-8(65001)로 바꾸고 원래 값과 두 핸들의 원래 모드를 저장한다. 키는 파싱하지 않는다. VT 입력이 만든 바이트를 그대로 원격 PTY로 보낸다(`docs/CLI.md` §7). 행 시작 escape 처리는 unix와 같은 코드가 한다. `Ctrl-C`는 `ENABLE_PROCESSED_INPUT`이 꺼져 있으므로 `0x03` 바이트로 원격에 간다.
6. 복원은 모든 종료 경로에서 일어난다. 정상 종료와 오류 종료는 guard의 `Drop`, panic은 전역 slot을 쓰는 panic hook, 콘솔 창 닫기·`CTRL_BREAK`·로그오프·종료(`SetConsoleCtrlHandler`가 받는 `CTRL_CLOSE_EVENT`·`CTRL_BREAK_EVENT`·`CTRL_LOGOFF_EVENT`·`CTRL_SHUTDOWN_EVENT`)는 핸들러가 맡는다. 복원 함수는 멱등이다(unix의 `restore`와 같은 규율). 핸들러가 받은 이벤트는 unix의 SIGHUP/SIGTERM과 같이 detach로 처리한다. 세션은 서버에 남는다(`docs/CLI.md` §7).
7. 콘솔을 준비하지 못하면 세션을 열기 전에 끝낸다. 출력 핸들에 VT 처리를 켤 수 없는 환경(Windows 10 1809 미만의 conhost)이면 `UNSUPPORTED`로 끝나고, 메시지는 최소 버전을 적는다. 이것은 기능의 차이가 아니라 지원 OS 버전의 하한이고, macOS·Linux의 최소 버전 밖 환경과 같은 처지다. 1809는 ConPTY(결정 20)의 최소 버전과도 같으므로 Windows 지원 하한은 client와 host 모두 1809 하나다. 이 판정은 `session.open`보다 먼저이므로 호스트에 고아 세션이 생기지 않는다. stdin이 콘솔이 아닌 경우(파이프, 파일 리디렉션, Git Bash의 mintty처럼 pty 대신 파이프를 주는 터미널)는 unix의 비 tty 경로와 같다. raw 모드도 escape 처리도 없이 바이트를 그대로 흘린다(`docs/CLI.md` §7). README는 mintty 계열에서는 `winpty`나 Windows Terminal을 쓰라고 적는다.
8. resize는 이벤트 없이 폴링한다. `WINDOW_BUFFER_SIZE_EVENT`는 `ReadConsoleInput`으로만 오고 그것은 바이트 그대로 읽는 입력 경로와 충돌한다. 전용 스레드가 200 ms마다 `GetConsoleScreenBufferInfo`의 창 영역(`srWindow`) 크기를 읽어 직전 값과 다를 때만 `session.resize`를 보낸다. 최초 크기는 `session.open`에 싣는다. 폴링 간격은 상수로 두고 설정 키는 만들지 않는다. `SessionOpen.term`은 `TERM`이 있으면 그 값, 없으면(Windows의 일반 상태) 7번의 VT 입출력이 켜졌을 때 `xterm-256color`다. locale 환경변수는 Windows에 보통 없으므로 있을 때만 보낸다(`docs/CLI.md` §7 전달 목록의 기존 규칙).

### C. 파일 권한, keystore, 경로

9. 소유자 전용 DACL을 만드는 단일 모듈을 `qsh-core`(`fsutil` 하위)에 둔다. 만드는 쪽은 프로세스 토큰의 사용자 SID로 보호된(protected, 상속 차단) DACL 하나를 쓴다. 파일은 소유자 SID에 `FILE_ALL_ACCESS` ACE 하나, 디렉터리는 같은 SID에 `OBJECT_INHERIT | CONTAINER_INHERIT` ACE 하나다. 파일과 임시 파일은 `CreateFileW`의 `SECURITY_ATTRIBUTES`로 만드는 순간부터 이 DACL을 갖는다. 만든 뒤에 `icacls`로 고치지 않는다(생성과 설정 사이에 상속 ACL로 읽히는 구간이 생기고, 외부 프로세스·로캘에 기대게 된다). 기존 `ensure_private_dir_io`, `write_private_file_io`, resume 저장소의 임시 파일 생성, audit 로그 파일과 디렉터리 생성(`audit.rs`, `audit/writer.rs`)이 `cfg(windows)` 분기에서 이 모듈을 부른다. 대상은 unix에서 0600/0700으로 만드는 파일과 디렉터리 전부다. 곧 `identity/device.pem`·`device.key`(파일 모드, `qsh identity move-key --to file`이 만드는 것 포함), private CA(ADR-0008)의 root 개인키와 발급 산출물(`ca.rs`), `trust.toml`, `config.toml`(쓰는 경우), `resume.json`과 그 `.tmp`·`.lock`, `stateless_reset.key`(ADR-0036), audit 로그와 회전 파일과 잠금 파일, 서비스 작업 정의 파일(결정 27), 그리고 config·state·audit 디렉터리다.
10. DACL을 적용하지 못하면 파일을 만들지 않고 fail closed한다. SID 조회 실패, ACL을 지원하지 않는 파일시스템(FAT/exFAT, 일부 네트워크 공유)이 이유다. 오류는 기존 `config_io_error`의 `CONFIG_ERROR`이고 메시지에 경로와 원인을 담는다. audit 경로에서는 audit writer의 기존 fail-closed 규칙이 그대로 적용되어 기록하지 못하면 op도 없다. 이미 있는 파일이 옛 빌드의 상속 ACL로 만들어졌다면 다음 쓰기(임시 파일 + rename)가 소유자 전용 DACL로 바꿔 놓는다. 읽기 전용 경로는 열 때 ACL을 검사하지 않는다. unix가 `acl.toml` 외에는 읽을 때 모드를 검사하지 않는 것과 같다. `acl.toml`은 unix와 같이 읽을 때 검사하고 경고만 한다(결정 24). README Known limitations의 "Windows ACL checking is out of scope"는 지운다.
11. 초대 코드를 콘솔 프롬프트로 받는 경로를 연다. 프롬프트 동안 입력 핸들의 `ENABLE_ECHO_INPUT`을 끄고 `ENABLE_LINE_INPUT`·`ENABLE_PROCESSED_INPUT`은 켠 채로 한 줄을 읽은 뒤 원래 모드로 돌린다. 복원은 결정 6의 guard·panic hook·콘솔 이벤트 핸들러 규율을 그대로 쓴다. `--code-stdin`의 stdin이 콘솔이면 같은 에코 억제 경로로 읽는다(unix에서 `--code-stdin`이 터미널이면 에코를 끄는 것과 같다). machine mode와 비 콘솔 stdin의 규칙(`docs/CLI.md` §6.11의 `INVALID_ARGUMENT`)은 플랫폼과 무관하게 그대로다. 에코가 실제로 꺼졌는지는 결정 17의 ConPTY 테스트가 단언한다. ConPTY 안에서 `qsh pair accept`를 띄우고 코드를 입력한 뒤, ConPTY 출력 스트림에 코드 문자가 나타나지 않고 프롬프트가 끝난 뒤 콘솔 모드가 원래 값임을 본다. 첫 개정이 이 경로를 막은 이유는 CI가 에코를 단언할 수단이 없다는 것이었는데, ConPTY 출력이 바로 그 수단이다. `NO_TERMINAL_ECHO_SUPPRESSION`은 쓰는 곳이 없어지므로 지운다.
12. keystore는 Windows Credential Manager를 `platform` store로 붙인다. keyring-core 계열 store crate 하나를 `cfg(windows)` 의존으로 더하고, `auto`는 다른 OS와 같이 platform을 먼저 시도하고 `Unavailable`이면 파일 모드(결정 9의 DACL)로 떨어진다. store 호출은 다른 플랫폼과 같이 연산마다 열고 전역 기본 store를 등록하지 않는다. 개인키 blob은 Credential Manager의 크기 상한 안이다. 이 crate가 존재하지 않거나 `deny.toml`(license·advisory)을 못 넘으면 `qsh-core`가 `windows-sys`의 `CredReadW`·`CredWriteW`·`CredDeleteW`(feature `Win32_Security_Credentials`)로 같은 store 인터페이스를 직접 구현한다. 항목은 target `qsh`·사용자 이름 `device_id`·`CRED_TYPE_GENERIC`·`CRED_PERSIST_LOCAL_MACHINE`이고 blob은 다른 플랫폼과 같은 base64 PKCS#8 DER이다. Windows `platform`을 `Unavailable`로 두는 길은 플랫폼 간 동등에 어긋나므로 택하지 않는다. 이 판정은 첫 스텝에서 하고 어느 쪽이든 이 ADR을 개정하지 않는다(구현 선택이다). `qsh identity move-key`(ADR-0032 결정 15)의 `--to platform`·`--to file` 왕복도 Windows에서 같다. 실제 store 왕복은 CI가 못 보므로 다른 플랫폼과 같이 릴리스 전 수동 단계다(`docs/design/testing.md` L1 「플랫폼 키스토어 릴리스 전 수동 단계」에 Windows 줄을 더하고, `move-key` 왕복도 이 줄에 넣는다). 결정 27의 기본 작업은 사용자의 대화형 로그온 토큰으로 돌기 때문에 서비스로 띄운 `qsh serve`·`qsh listen`도 같은 Credential Manager 항목을 읽는다. 상시 기동 변형(`LogonType=Password`)도 프로필과 DPAPI를 적재하므로 읽는다고 보고, 이 가정은 첫 서비스 스텝에서 실측한다. 읽지 못하면 ADR-0032 결정 15의 `keystore_session_bound`를 Windows 상시 기동 작업에도 낸다(remedy는 `qsh identity move-key --to file`).
13. config·state 경로는 ssh 스타일 예측 가능성을 따른다(`docs/design/architecture.md` §7). Windows에서도 `%USERPROFILE%\.config\qsh`와 `%USERPROFILE%\.local\state\qsh`이고 `QSH_CONFIG_DIR`·`QSH_STATE_DIR`·`XDG_*` 우선순위는 그대로다(`Paths::from_env`의 `home_dir()`가 이미 플랫폼 홈을 고른다). `%APPDATA%`와 `%LOCALAPPDATA%`는 쓰지 않는다. runtime dir은 만들지 않는다. `Paths::runtime_dir()`의 값은 결정 14의 pipe 이름에 섞는 입력일 뿐이다.

### D. localctl, supervise

14. localctl transport를 Windows named pipe로 연다. 모양은 unix의 신뢰 모델(`crates/qsh-core/src/localctl/mod.rs` 모듈 doc의 "localctl은 새 권한을 주지 않는다. 같은 OS 사용자만 붙는다")을 그대로 옮긴다.
    - 이름. `\\.\pipe\qsh-<scope>-<pid>`이다. `<scope>`는 현재 프로세스 토큰의 사용자 SID 문자열과 `Paths::runtime_dir()`의 정규 경로(소문자화)를 NUL로 이어 SHA-256을 낸 앞 16 hex다. 사용자 SID와 state dir(곧 `QSH_STATE_DIR`)이 다르면 이름 공간이 갈라져 서로의 데몬을 보지도 건드리지도 않는다. 데몬은 한 번에 하나의 `<pid>`를 쓴다. 발견(`qsh hosts`, `qsh tunnels`)은 `\\.\pipe\`를 열거해 `qsh-<scope>-*` 접두에 맞는 이름만 후보로 삼는다. unix의 `candidate_sockets`가 `<pid>.sock`을 거르는 것과 같다. pipe는 프로세스가 죽으면 사라지므로 오래된 파일을 지우는 경로(unix의 stale 소켓 교체)는 없다.
    - 생성. 서버는 첫 인스턴스를 `FILE_FLAG_FIRST_PIPE_INSTANCE`로 만든다. 그 이름이 이미 있으면(다른 프로세스가 선점했거나 같은 pid의 옛 인스턴스) 기동이 실패한다. 이는 pipe 이름 선점(squatting)을 거부하는 장치이고, 실패하면 QUIC listener를 열기 전에 끝난다(unix에서 runtime dir 권한을 못 박지 못하면 전체 기동이 실패하는 것과 같다). `PIPE_REJECT_REMOTE_CLIENTS`를 항상 켠다. `PIPE_TYPE_BYTE`·`PIPE_READMODE_BYTE`로 두고 프레이밍은 `localctl/frame.rs`가 맡는다.
    - 접근 통제. 모든 인스턴스를 결정 9의 DACL 모듈이 만든 보호된(protected) 소유자 전용 DACL로 만든다. 소유자 SID에 pipe 읽기·쓰기와 `FILE_CREATE_PIPE_INSTANCE`를 주는 ACE 하나다. pipe의 기본 DACL은 Everyone·익명에 읽기를 주므로 반드시 명시한다. 다음 연결을 받을 인스턴스는 현재 연결을 넘기기 전에 만들어 두어, 이름이 빈 틈이 생기지 않게 한다. 소유자 외에는 `FILE_CREATE_PIPE_INSTANCE`가 없으므로 다른 사용자는 같은 이름에 인스턴스를 더 만들지도 못한다.
    - 자격 확인(unix `peer_cred`의 대응). 서버는 accept한 연결마다 프레임을 한 바이트도 읽기 전에 `GetNamedPipeClientProcessId`로 클라이언트 프로세스를 열어(`PROCESS_QUERY_LIMITED_INFORMATION`) 토큰의 사용자 SID가 자기와 같은지 대조한다. 다르거나 조회에 실패하면 말 없이 끊는다. 클라이언트는 연결 직후 첫 프레임을 쓰기 전에 `GetNamedPipeServerProcessId`로 서버 프로세스의 토큰 사용자 SID가 자기와 같은지 대조한다. 다르거나 조회에 실패하면 그 후보를 데몬이 아닌 것으로 건너뛰고 아무것도 보내지 않는다. 클라이언트는 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`으로 열어 가짜 서버가 클라이언트 토큰을 가장(impersonate)하지 못하게 한다. 이 확인은 DACL 뒤의 두 번째 겹이다. 같은 사용자의 상승(elevated)·비상승 토큰은 SID가 같아 통과한다. 남는 틈은 잔여 위험(결정 19)에 적는다.
    - 공통 부분. 프레이밍과 wire(`qsh.local.v1`, `LOCAL_ADMIN`·`LOCAL_CONTROL`·`LOCAL_STREAM`)는 OS와 무관하게 바뀌지 않는다. localctl은 인가 계층이 아니고(데몬은 `Authorizer::check`를 conduit에 대해 부르지 않는다) 클라이언트가 보낸 principal 값을 믿지 않는다는 규칙도 그대로다. resume token은 어떤 localctl 프레임에도 실리지 않는다.
    - 모듈 구조. `localctl/`에서 플랫폼에 닿는 부분만 `cfg`로 가른다. `frame.rs`와 `client.rs`는 `AsyncRead + AsyncWrite` 스트림에 대해 일반화하고 연결·인스턴스 생성·자격 확인은 `localctl/transport/unix.rs`와 `localctl/transport/windows.rs`로 옮긴다. `frame.rs`·`client.rs`는 파일로 남아 `xtask arch`의 파일 단위 금지(`qsh_transport`·`quinn`·`rustls`)를 그대로 받는다. 새 transport 파일 둘도 같은 금지 목록에 올리고, `daemon.rs`는 지금처럼 면제다. `qsh-cli/src`의 금지는 UDS 토큰에 `named_pipe`와 `\\.\pipe`를 더한다. `localctl/mod.rs`의 `#[cfg(unix)]` 게이트와 `lib.rs`의 모듈 선언 주석은 걷어 낸다. 같은 이유로 `reverse/listen.rs`·`reverse/listen/hub.rs`·`registration.rs`·`reverse/target`·`client/link.rs`·`ops/exec.rs`의 `cfg(unix)`/`cfg(not(unix))` 쌍둥이를 없애고 `run_listen`의 `cfg` 분기도 지운다. `windows_unsupported()`는 부르는 곳이 없어지므로 지운다.
    - `qsh listen`의 나머지. 종료 신호는 Windows에서 `tokio::signal::ctrl_c`와 콘솔 닫힘 이벤트(결정 6의 핸들러 계열)이고, 콘솔 없이 작업 스케줄러가 띄운 경우(결정 27)는 작업 종료가 프로세스를 끝낸다. config·정책 진단·감사·ACL 규율(`acl.toml` 1회 로드, default-deny, 감사 fail closed)은 unix와 같고 감사 로그와 stateless reset key 파일은 결정 9 모듈로 만든다. 데몬은 방화벽 허용이 필요한 UDP 포트를 연다. `qsh doctor`의 `controller_unreachable` 문안이 그대로 쓰이고, Windows Defender 방화벽 안내는 README가 적는다.
    - 동작 요약. Windows에서 `qsh hosts`는 forward host와 데몬이 알리는 reverse 항목을 낸다(데몬이 없으면 forward만이고 오류가 아니다). `qsh tunnels`는 데몬 항목을 포함한다. `qsh tunnel close <id>`는 이 프로세스 밖의 터널을 데몬들에 묻는다. 위 변화를 `docs/CLI.md` §6.9·§6.13·§6.14의 Windows 문장에 반영한다.
15. `qsh tunnel open --supervise`는 Windows에서 그대로 열린다. forward route에서는 supervisor가 터널을 연 프로세스 안에 있다. reverse route의 `--remote`는 데몬의 reverse connection이 carrier이고 운영자 닫기를 `LocalHostList`·`LocalTunnelList`로 판별하는데(`docs/CLI.md` §6.14), 이 두 요청이 named pipe 위에서 같은 값을 돌려주므로 판별 규칙은 바뀌지 않는다. 데몬이 재시작하면 reverse 등록과 그 위의 터널이 모두 끝나는 점은 unix와 같다. 절전 감지는 Windows에서도 울려야 한다. 감지기의 단조 시계 표본을 Windows에서는 `QueryUnbiasedInterruptTime`으로 읽는다. 이 값은 절전·최대 절전 중 흐른 시간을 빼도록 문서화된 카운터라서, 벽시계와의 차이가 곧 잠든 시간이 되는 macOS·Linux의 `Instant`와 같은 성질을 갖는다. 감지 알고리즘(`WAKE_TICK`, `WAKE_SKEW`, 앞으로 뛴 차이만 셈)은 그대로이고 표본 함수 하나만 `cfg`로 가른다. tokio 타이머 자체는 바꾸지 않는다. 그래서 `qsh.event/v1`의 `wake` 이벤트와 supervise·target backoff의 즉시 재시도가 Windows에서도 나온다. 결정 17의 단위 테스트가 표본 함수의 단조성을, 캠페인 회차(결정 18)가 실제 절전 복귀를 본다. reverse target(`qsh serve --to`, 결정 25)의 backoff와 경로 감시도 같은 감지기를 쓴다.

### E. 출고, CI, 문서

16. 출고는 macOS·Linux와 같은 항목을 Windows 수단으로 갖춘다.
    - 자산. `qsh-<tag>-x86_64-pc-windows-msvc.zip`에 `qsh-<tag>-aarch64-pc-windows-msvc.zip`을 더한다. macOS·Linux가 arm64와 x86_64를 모두 내는 것과 맞춘다. `SHA256SUMS`·attestation 대상 규칙은 같다. aarch64 자산은 x86_64 러너에서 교차 빌드하고, 기능 확인은 Linux aarch64-musl과 같이 사람 캠페인 회차가 맡는다(결정 18).
    - man 페이지. zip은 unix tarball과 같이 `qsh.exe`와 `man/*.1`(`docs/man/`과 같은 바이트)을 담는다. Windows에서 읽는 수단은 두 가지다. 하나는 `qsh help <command>`와 `--help`로, man 페이지와 같은 clap 트리에서 나오므로 같은 내용이다. 다른 하나는 `.1` 파일 자체로, WSL·MSYS2·Git for Windows의 `man -l`이나 roff 뷰어로 읽는다. 내장 roff 렌더러는 만들지 않는다. `checked_in_man_pages_match_the_generator`가 이미 페이지 집합을 clap 트리와 대조하므로 "man 페이지가 있는 명령은 `qsh help`로도 읽힌다"는 성질은 새 테스트 없이 성립한다. Windows packaging 스텝에 zip 안의 `man/` 목록이 `docs/man/`과 같은지 대조하는 검사를 더한다.
    - 설치 스크립트. `scripts/install.ps1`을 새로 둔다. `install.sh`와 같은 일을 한다. 아키텍처를 골라 zip을 받고, `SHA256SUMS`로 대조하고, `%USERPROFILE%\.local\bin`에 `qsh.exe`를, `%USERPROFILE%\.local\share\man\man1`에 페이지를 풀고, 사용자 `PATH`에 그 bin 디렉터리가 없으면 더한다. 관리자 권한을 요구하지 않는다. README의 한 줄 설치는 `irm <URL> | iex`이다. 서명된 `install.ps1`은 release 자산으로도 올린다.
    - 코드 서명. `qsh.exe`(두 아키텍처)와 자산 `install.ps1`에 Authenticode 서명을 건다. macOS의 Developer ID 서명·공증과 같은 자리다. 서명 주체는 macOS와 같이 유지보수자 본인 이름이 보이도록 개인 신원 검증(individual validation) 코드 서명 인증서를 쓰고, 개인키는 2023년 6월 이후 CA/B Forum 요구대로 클라우드 HSM에 둔다. 제공자는 SSL.com eSigner로 정한다. 비교와 이유는 근거 절에 있다. `release.yml`의 Windows leg은 `Sign the binary` 스텝에서 SSL.com의 CodeSignTool(공식 GitHub Action `sslcom/esigner-codesign`)로 서명하고, SHA-256 다이제스트와 RFC 3161 타임스탬프(`http://ts.ssl.com`)를 붙인다. 타임스탬프가 있어야 인증서가 만료된 뒤에도 서명이 유효하다. 순서는 macOS leg과 같다. 빌드, 서명, 서명 검증, `release_smoke`, 패키징 순이고, 패키징은 서명된 바이트를 담는다.
    - 서명 검증. `Verify the signature` 스텝은 `signtool verify /pa /v`와 PowerShell `Get-AuthenticodeSignature`를 함께 돌려 상태가 `Valid`이고, 서명자 주체가 저장소 변수 `WINDOWS_SIGN_EXPECTED_SUBJECT`와 같고, 타임스탬프 서명이 있음을 확인한다. macOS의 `codesign --verify` 뒤 identity 대조와 같은 역할이다. 서명이 없는 바이너리는 `NotSigned`라서 이 검사가 실패한다. `release_smoke`의 Windows 쌍둥이는 서명된 바이너리로 돈다.
    - 시크릿 게이트. macOS의 Apple 시크릿 여섯과 같은 전부-또는-전무 규칙이다. 시크릿 넷(결과 절)이 모두 있으면 서명하고 검증 스텝이 돈다. 하나도 없으면 서명과 검증을 건너뛰고 태그 push에서는 `Unsigned release` 경고를 낸다. 일부만 있으면 태그 push는 오류로 붉고 브랜치 `workflow_dispatch`는 경고를 내고 건너뛴다. `release.yml`의 `Check for Apple signing secrets` 스텝과 같은 모양이다. 이름과 발급처, 회전 절차는 `docs/deploy/release-secrets.md`에 새 절로 적는다.
    - 패키지 관리자. Homebrew `homebrew-tap` job에 대응하는 두 job을 둔다. `scoop-bucket` job은 `DaveDev42/scoop-bucket` 저장소의 `bucket/qsh.json`을 새 버전·URL·해시로 bump한다. 쓰기는 그 저장소 하나에 범위를 좁힌 배포 키로 하고, 매니페스트에는 `checkver`·`autoupdate`를 둔다. `winget` job은 `microsoft/winget-pkgs`에 `DaveDev42.qsh` 매니페스트 갱신 PR을 연다(`wingetcreate update --submit`, 설치 형식은 zip 안의 portable). 첫 매니페스트 제출은 Homebrew tap의 첫 formula처럼 사람이 한다. 두 job은 `homebrew-tap`과 같이 시크릿이 없으면 green인 채 건너뛰고 `continue-on-error`로 release를 붉히지 않는다. 두 매니페스트는 `man/*.1`을 설치하지 않는다. scoop과 winget portable에는 man 경로 규약이 없고, 같은 내용은 `qsh help`가 준다.
17. CI의 `windows-latest` leg은 다음을 더한다. 종단 테스트는 첫 개정의 test-only 하니스 대신 실제 CLI를 양쪽에 쓴다. Windows에 host가 생겼으므로 한 러너의 loopback 위에서 정방향과 역방향을 끝까지 돌릴 수 있다.
    - 결정 9~10의 DACL 단언 테스트. 소유자 전용 DACL로 `identity/device.key`, `trust.toml`, `resume.json`, audit 로그, `stateless_reset.key`를 만들고 `GetNamedSecurityInfoW`로 읽어 SE_DACL_PROTECTED, ACE 하나, 그 SID가 토큰 사용자, 접근 마스크가 `FILE_ALL_ACCESS`임을 단언한다. 적용 실패를 주입한 변형에서는 대상 파일이 만들어지지 않음을 단언한다.
    - 결정 14의 named pipe 테스트. (1) 같은 이름의 pipe를 먼저 만들어 둔 상태에서 데몬 기동이 QUIC listener를 열기 전에 실패한다. (2) 만들어진 pipe 인스턴스의 보안 설명자를 읽어 SE_DACL_PROTECTED, 소유자 SID의 ACE 하나, Everyone·익명 ACE 없음을 단언하고, `PIPE_REJECT_REMOTE_CLIENTS`가 켜졌는지는 생성 옵션을 담은 순수 함수의 단위 테스트로 고정한다. (3) 자격 확인은 "프로세스 ID에서 사용자 SID를 얻는 함수"를 주입할 수 있게 쪼개서, 서버가 다른 SID의 클라이언트를 프레임을 읽기 전에 끊고 클라이언트가 다른 SID의 서버에 아무것도 쓰지 않음을 단언한다. 진짜 다른 사용자 계정은 CI 러너에서 만들 수 없으므로 주입 범위까지만 CI가 보고, 실제 두 번째 계정의 접속 거부는 캠페인 회차(결정 18)가 맡는다. (4) pipe 이름 규칙: 사용자 SID나 state dir이 다르면 이름이 다르고 같으면 같다. (5) `candidate_sockets`에 대응하는 열거가 접두에 맞는 이름만 고른다. (6) `frame.rs`·`client.rs` 테스트는 스트림 일반화 뒤에도 unix와 Windows 양쪽에서 같은 케이스로 돈다.
    - 결정 4~8과 11의 콘솔 계층 테스트. 테스트 바이너리가 ConPTY(`qsh-testkit`)를 열고 그 안에서 콘솔 probe(`qsh-testkit`의 작은 실행 파일)를 띄운다. probe는 raw 모드 진입 후 입력 바이트가 가공 없이 읽히는지, ConPTY 크기를 바꾸면 폴링이 한 번만 `resize` 콜백을 부르는지, 정상·강제 종료 뒤 콘솔 모드가 원래 값으로 돌아오는지를 stdout으로 보고한다. 모드 비트 계산(원래 모드에서 raw 모드와 에코 억제 모드를 만드는 순수 함수)은 단위 테스트가 따로 고정한다. 초대 코드 프롬프트는 `qsh pair accept`를 ConPTY 안에서 띄워 결정 11대로 단언한다.
    - 결정 20~24의 host 테스트. `crates/qsh-core/src/pty/tests.rs`의 PTY 종단 케이스(spawn, 입출력, resize, 종료 코드, 세션 close, 로그인 환경 고정)를 Windows 백엔드로 도는 쌍둥이를 둔다. 셸은 `cmd.exe`이고 기대값은 Windows 명령으로 바꾼다. Job Object 종료가 손자 프로세스까지 끝내는지, `exec` 타임아웃이 프로세스 트리 전체를 끝내는지, 결정 22의 신호 일곱이 각각 정해진 Windows 사건을 일으키는지(테스트 자식이 `CTRL_C_EVENT`·`CTRL_BREAK_EVENT`·`CTRL_CLOSE_EVENT` 처리기와 `Usr1`·`Usr2` 이벤트 대기로 받은 것을 종료 코드로 보고한다)와 그 뒤 유예·escalation으로 세션이 끝나는지, `acl.toml` DACL 경고가 구조적 필드만 싣는지를 본다.
    - 정방향 종단 테스트. 같은 러너에서 `qsh serve`(인바운드)를 띄우고 `qsh` client가 loopback으로 붙는다. `exec`, `-L` 터널의 TCP echo 왕복, `qsh cp` 왕복(ADR-0029 착지 뒤), 그리고 ConPTY 안에서 대화형 `qsh <name>`을 띄워 입력 echo, resize 전파, `~d` detach 뒤 `qsh attach` resume을 본다. unix의 `tui_expect`가 하는 일을 ConPTY 출력에 대해 하는 것이다.
    - 역방향 종단 테스트. 같은 러너에서 `qsh listen`(데몬)과 `qsh serve --to`(target)를 띄운다. 첫 개정의 test-only 하니스는 만들지 않는다. 볼 것은 `qsh hosts`의 reverse 항목, reverse route 위의 `exec`, `-L`·`-R` 터널 echo, `qsh cp` 왕복(착지 뒤), ConPTY 안의 대화형 attach와 detach 뒤 resume, 데몬을 죽인 뒤 `qsh hosts`가 reverse 항목을 못 내고 forward만 냄, 새 데몬이 서면 target이 재등록하는 것이다. 정방향 종단 테스트와 같은 케이스 목록을 route만 바꿔 돌린다(`docs/ROADMAP.md` §5.1 원칙 7의 "두 route에서 같은 테스트").
    - 결정 15의 표본 함수 단위 테스트, 결정 27의 작업 정의 렌더러가 `docs/deploy/service.md`의 Windows 펜스와 바이트 단위로 같은지 보는 `crates/qsh-core/tests/it/service_docs.rs` 확장.
    - `release_smoke`의 `cfg(not(unix))` 쌍둥이를 unix 쪽과 같은 축으로 넓힌다. 기존 `init` → `trust` → `exec --json`에 `doctor --json`, `tunnel open --local`의 TCP echo 왕복, PTY session open·write·read·close를 더한다. 이 쌍둥이가 만든 파일에도 결정 9의 DACL 단언을 건다.
    - clippy는 이미 Windows를 돈다. `cargo xtask arch`의 의존 방향 규칙은 바뀌지 않는다(`windows-sys`는 `qsh-core`와 `qsh-cli`가 `cfg(windows)`로만 의존한다).

### F. host 역할

20. PTY 백엔드에 ConPTY 구현을 더한다. 위치는 `crates/qsh-core/src/pty/`이고 `posix.rs` 옆에 `conpty.rs`를 두어 `pty::factory()`가 Windows에서 그것을 돌려준다. `UnsupportedFactory`는 지운다. broker(`SessionSource`/`SourceFactory`)의 trait은 바뀌지 않는다. 구현은 `portable-pty`가 아니라 `windows-sys`를 직접 쓴다. `CreatePseudoConsole`, `STARTUPINFOEX`에 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`과 `PROC_THREAD_ATTRIBUTE_JOB_LIST`를 실어 `CreateProcessW` 한 번으로 자식을 만든다. 이렇게 해야 자식이 생기는 순간부터 Job Object 안에 있어 손자 프로세스까지 한 단위로 끝낼 수 있다(unix의 `setsid` + `killpg`에 대응). Job Object는 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 켜서 host 프로세스가 죽어도 세션 트리가 남지 않게 한다. ConPTY 쪽 입출력 핸들은 동기 pipe여야 하므로, host 쪽 끝은 overlapped named pipe(결정 14의 DACL 모듈로 만든 소유자 전용, 이름은 임의 난수)로 만들어 tokio에서 비동기로 읽고 쓴다. 이 배치가 첫 host 스텝에서 서지 않으면 세션마다 읽기 스레드 하나를 두는 방식으로 접고 이 ADR을 개정한다(세션 수는 기존 quota가 묶는다). resize는 `ResizePseudoConsole`이다. 자식 종료는 프로세스 핸들 대기로 받고, 종료 뒤 `ClosePseudoConsole`은 출력을 다 읽은 다음 blocking task에서 부른다(ConPTY는 남은 출력을 내보낸 뒤에야 닫힌다). sequence 태깅, replay, quota, detach·resume 같은 broker 동작은 플랫폼과 무관해서 그대로다.
21. 세션의 환경과 셸. 자식은 `qsh serve` 프로세스의 환경을 물려받지 않는다(unix 결정과 같다). 환경은 `CreateEnvironmentBlock`으로 프로세스 토큰 사용자의 기본 환경(레지스트리의 사용자·시스템 변수, `USERPROFILE`, `USERNAME`, `PATH` 등)을 받고, 그 위에 `TERM`(client 힌트, 기본 `xterm-256color`), locale·시간대 전달(`LANG`, `LANGUAGE`, `LC_*`, `TZ`, 있을 때만), client의 추가 `env`를 얹는다. client가 덮어쓸 수 없는 고정 키는 unix의 `HOME`/`USER`/`LOGNAME`/`SHELL`/`PATH`에 Windows의 신원 변수 `USERPROFILE`/`USERNAME`/`USERDOMAIN`/`HOMEDRIVE`/`HOMEPATH`/`COMSPEC`/`SystemRoot`를 더한 집합이고, Windows 환경변수 이름은 대소문자를 가리지 않으므로 대조도 대소문자 무시다. `argv`가 비어 있으면 셸은 그 환경의 `COMSPEC`(없으면 `%SystemRoot%\System32\cmd.exe`)이다. Windows에는 계정별 로그인 셸 개념이 없으므로 시스템 기본 셸을 쓰는 것이 unix의 `pw_shell`에 대응하고, PowerShell을 원하는 사용자는 `qsh host -- pwsh`처럼 argv로 고른다. 작업 디렉터리는 `USERPROFILE`이다. 사용자 전환은 unix와 같이 없다. `user@` 힌트는 프로세스 토큰의 계정 이름(`USERNAME`, 또는 `DOMAIN\USERNAME` 형태면 둘 다)과 대소문자 무시로 비교하고, 다르면 unix와 같은 `user switching is not supported`로 끝난다. 이 비교는 `server/mod.rs`의 `lookup_login_name`의 Windows 구현이다. utmp/wtmp에 해당하는 기록은 unix와 같이 쓰지 않는다.
22. 신호와 종료 상태. 신호는 오늘 `session close --signal <SIG>`로만 가고, 그 뜻은 "close 절차의 첫 단계를 이 신호로 바꾼다"이다. 첫 신호 뒤에는 `[serve].close_grace_ms` 유예와 HUP → TERM → KILL escalation과 세션 정리가 이어진다(`docs/CLI.md` §6.7). 그래서 Windows에서 정해야 하는 것은 일곱 신호 각각의 첫 단계이고, 어느 신호든 세션은 결국 끝난다. 일곱 모두 Windows에서 성공으로 답한다.
    - `Int`는 세션 콘솔에 붙은 프로세스 전체에 `CTRL_C_EVENT`를 보낸다. `Quit`은 `CTRL_BREAK_EVENT`를 보낸다. `CTRL_BREAK_EVENT`는 Windows에서 관례상 `SIGQUIT` 자리에 있는 사건이다. JVM이 unix에서는 `SIGQUIT`, Windows에서는 Ctrl-Break로 스레드 덤프를 찍는 것이 그 예다. 두 사건은 `GenerateConsoleCtrlEvent`로 보내는데, 이 함수는 호출자가 같은 콘솔에 붙어 있어야 하고 콘솔 붙이기는 프로세스 전역 상태다. 그래서 host 프로세스가 직접 붙지 않고, 같은 바이너리의 숨김 내부 진입점(`qsh internal console-ctrl <pid> <c|break>`, man 페이지와 `--help` 목록에서 제외)을 `DETACHED_PROCESS`로 띄운다. 그 보조 프로세스가 세션 루트 프로세스의 콘솔에 `AttachConsole`로 붙고, 자기 처리기를 끈 뒤 사건을 그룹 0(그 콘솔의 모든 프로세스)에 보내고 끝난다. 세션 루트는 `CREATE_NEW_PROCESS_GROUP` 없이 만들므로 `CTRL_C_EVENT`를 받는다. ConPTY 입력에 `0x03`을 쓰는 방법은 쓰지 않는다. 앱이 처리된 입력을 끄면 그 바이트는 사건이 아니라 문자가 되는데, unix의 `killpg(SIGINT)`는 tty 모드와 무관하게 닿기 때문이다.
    - `Hup`과 `Term`은 `ClosePseudoConsole`로 콘솔에 붙은 프로세스들에 `CTRL_CLOSE_EVENT`를 보낸다. Windows 콘솔에서 "터미널이 사라졌다"와 "끝내라"를 전하는 사건은 이것 하나다. Go 런타임이 이 사건을 `SIGTERM`으로, 터미널 닫힘을 `SIGHUP` 자리로 다루는 것과 같은 사상이다. 첫 신호가 `Hup`이면 escalation의 `Term` 단계는 같은 사건이라 다시 보내지 않고 유예만 지난다.
    - `Usr1`과 `Usr2`는 세션마다 만드는 자동 리셋 이름 있는 이벤트 둘에 `SetEvent`를 건다. host는 세션을 만들 때 이름을 `Local\qsh-sig-<128비트 난수 hex>-usr1`·`-usr2`로 정하고 결정 9의 소유자 전용 DACL로 만들며, 그 이름을 세션 환경의 `QSH_SIGNAL_EVENT_USR1`·`QSH_SIGNAL_EVENT_USR2`에 넣는다(결정 21의 고정 키에 더해 client가 덮어쓸 수 없다). 신호를 받고 싶은 프로그램은 그 이벤트를 열어 기다린다. unix에서 `SIGUSR1` 처리기를 거는 것에 대응한다. 기다리는 프로그램이 없으면 unix의 기본 동작(종료)처럼 세션은 유예 뒤 escalation으로 끝난다. 이름 있는 이벤트를 고른 이유는 Windows에서 같은 사용자의 다른 프로세스에 비동기 통지를 전하는 수단 가운데 프로그램 쪽 구현이 가장 작고(언어마다 `OpenEvent`/`WaitForSingleObject` 두 호출), 이름에 난수와 DACL을 걸어 세션 밖에서 엿보거나 위조할 수 없기 때문이다.
    - `Kill`은 곧바로 `TerminateJobObject`다. 신호 없는 `session close`는 unix와 같이 `Hup`에서 시작한다.
    - 종료 상태는 wire `Exit`의 기존 필드에 싣는다. `exit_code`는 Windows 종료 코드 u32를 같은 비트의 i32로 옮긴 값(std의 `ExitStatus::code()`와 같다)이다. qsh가 위 사상으로 보낸 사건 뒤에 세션이 끝났으면 `signal`에 그 단계의 신호 이름을 싣는다. unix에서 신호로 끝난 프로세스의 `signal`과 같은 자리다. wire와 JSON 모양은 바뀌지 않는다. 새로 생기는 것은 세션 환경변수 두 개뿐이고, `docs/CLI.md` §7의 host가 넣는 환경변수 목록에 additive로 적는다.
23. `exec`. host 쪽 `exec`도 결정 20의 Job Object 안에서 자식을 만들어 타임아웃 kill이 트리 전체에 닿게 한다(unix `process_group(0)` + `kill_group`의 대응). 환경은 결정 21의 규칙을 그대로 써서 `exec/mod.rs`의 `#[cfg(not(unix))]` 분기(서버 환경을 거르지 않고 넘기는 것)를 없앤다. argv는 셸을 거치지 않고 Rust std의 Windows 명령줄 인용 규칙으로 `CreateProcessW`에 넘긴다. `dir`처럼 `cmd.exe` 내장 명령은 unix의 셸 내장 명령과 같이 `cmd /c`를 argv에 직접 적어야 한다.
24. host 쪽 상태와 `acl.toml`. 결정 9 모듈이 audit 로그·회전 파일·잠금 파일과 디렉터리, `stateless_reset.key`를 만든다. audit writer의 회전 잠금은 Windows에서 잠금 파일에 `LockFileEx`를 걸고, 재검증(`revalidate`)은 unix의 (dev, ino) 대신 `GetFileInformationByHandle`의 (볼륨 일련번호, 파일 인덱스)로 같은 파일인지 확인한다. 두 쌍둥이로 unix의 공동 writer 보호가 Windows에서도 성립한다. `acl.toml`은 qsh가 쓰지 않고(ADR-0017) 읽을 때 unix와 같이 경고만 한다. 경고 조건은 파일의 DACL에 소유자, `SYSTEM`, `Administrators` 밖의 SID에게 쓰기 계열 권한(`FILE_WRITE_DATA`, `FILE_APPEND_DATA`, `WRITE_DAC`, `WRITE_OWNER`, `GENERIC_WRITE`, `GENERIC_ALL`)을 주는 허용 ACE가 있거나 DACL이 null인 경우다. unix의 group/world-writable과 같은 뜻이다. 경고 레코드는 unix와 같이 구조적 필드만 싣고 `mode` 대신 문제의 SID 문자열을 싣는다. 거부로 바꾸지 않는 이유도 unix와 같다(`acl/load.rs`의 주석).
25. `qsh serve --to`, `qsh setup host`, `qsh pair invite`, `qsh pair ssh-respond`를 연다. `serve --to`는 `run_reverse` 경로를 그대로 쓰고 PTY는 결정 20의 백엔드다. 인바운드 `qsh serve`와 `serve --to`는 UDP 포트를 열므로 Windows Defender 방화벽의 첫 허용 프롬프트가 뜰 수 있고, README와 `qsh doctor`의 기존 finding 문안이 이를 안내한다. `pair ssh-respond`(ADR-0044 결정 10)는 Windows에서 `unsupported_platform`을 내지 않고 다른 OS와 같은 순서로 동작한다. Windows 원격은 OpenSSH Server(Windows 선택적 기능)가 있어야 하고, 원격 명령은 sshd의 기본 셸(`cmd.exe` 또는 관리자가 바꾼 PowerShell)이 실행한다. ADR-0044 결정 14의 "원격에 qsh가 없음" 판정은 POSIX 셸의 종료 코드 127에 기대므로, 원격 기본 셸이 `cmd.exe`이면 9009도 같은 `remote_qsh_missing`으로 본다. 기본 셸이 PowerShell이면 종료 코드가 1이라 구별되지 않으므로 그 경우는 기존 일반 오류(`REMOTE_ERROR`, `details.reason: "remote_command_failed"`)로 끝나고 message가 `qsh.exe`의 `PATH` 등록이나 `--remote-qsh` 전체 경로를 안내한다. 이 사상은 ADR-0044 결정 14가 2026-10-14에 담았다.
26. host 쪽 `qsh cp`(ADR-0029). Windows host는 ADR-0029의 판정 순서(정규화, 보호 집합, 열린 핸들 재검증, 임시 파일과 rename)를 Windows 수단으로 지킨다. wire와 JSON은 바뀌지 않는다.
    - 경로. 원격 경로 문자열의 `/`와 `\`를 같게 보고, 드라이브 절대 경로(`C:\…`, `C:/…`)와 `USERPROFILE` 기준 상대 경로를 받는다. `host:`는 `USERPROFILE`이다. UNC(`\\server\share`)와 장치 이름 공간(`\\?\`, `\\.\`)은 host가 네트워크나 장치에 대신 접근하는 경로가 되므로 ACL 판정 전에 기존 `INVALID_ARGUMENT`로 거부한다.
    - 정규화와 재검증. 정규 경로는 `GetFinalPathNameByHandleW`의 결과에서 `\\?\` 접두를 뗀 것이다. 비교(`[[acl]] paths` prefix, 보호 집합)는 성분 단위의 대소문자 무시다. `paths` 항목의 표기(`C:/Users/dave/share`처럼 `/`만 쓰는 드라이브 절대 경로, `\`·드라이브 없는 항목·`"/"`는 `CONFIG_ERROR`)는 ADR-0029 결정 23이 정한다. unix의 `O_NOFOLLOW`는 `FILE_FLAG_OPEN_REPARSE_POINT`로 열어 재분석 지점(symlink, junction)이면 거부하는 것으로, 열린 핸들 재검증은 핸들의 최종 경로가 판정한 정규 경로와 같은지 보는 것으로 대응한다.
    - mode. 읽을 때는 mode 비트를 합성한다. 파일은 읽기 전용 특성이면 `0o444`, 아니면 `0o644`, 디렉터리는 `0o755`다. 쓸 때는 받은 mode의 소유자 쓰기 비트가 꺼져 있을 때만 읽기 전용 특성을 켜고 나머지 비트는 쓰지 않는다. 임시 파일은 결정 9의 소유자 전용 DACL로 만들고, rename 직전에 보호를 풀어 대상 디렉터리의 상속 ACL을 받게 한다. unix에서 `0600` 임시 파일을 만든 뒤 `mode & ~umask`를 적용하는 것과 같은 순서다. `-p`의 수정 시각은 `SetFileTime`이다.
    - client 쪽 get의 로컬 쓰기도 같은 규칙이고, 결정 1의 드라이브 문자 해석이 붙는다.

### G. 서비스 매니저 백엔드

27. `qsh service install|uninstall|status`의 Windows 백엔드는 작업 스케줄러의 사용자별 로그온 작업이다. M9가 고정한 동작(파일만 쓰고 등록은 사람 또는 ADR-0032의 명시적 플래그가 한다, `status`는 파일 존재만 본다, audit 한 건 뒤 쓰기, 매니저는 `cfg!(target_os)`로만 정한다)을 그대로 옮긴다.
    - 작업 정의. `install`은 작업 정의 XML을 `<config_dir>\service\qsh-<mode>.task.xml`에 결정 9의 DACL로 쓴다. 이것이 launchd plist와 systemd 유닛 파일에 대응하는 "유닛 파일"이다. 내용은 고정이다. 트리거는 현재 사용자의 `LogonTrigger` 하나, 주체는 그 사용자의 `InteractiveToken`(암호를 저장하지 않는다)과 `LeastPrivilege`, 설정은 `MultipleInstancesPolicy=IgnoreNew`, `ExecutionTimeLimit=PT0S`(시간 제한 없음), 배터리 조건 끔, `RestartOnFailure`(1분 간격)다. 동작은 `current_exe()`의 절대 경로와 run mode의 인자(`serve`/`listen`/`serve --to <controller>`)이고, launchd·systemd 유닛과 같은 인자 규칙을 쓴다. 작업 이름은 `\qsh\qsh-<mode>`다(launchd label `io.qsh.<mode>`, systemd `qsh-<mode>.service`에 대응).
    - 콘솔과 로그. 작업이 콘솔 실행 파일을 띄우면 콘솔 창이 생기고 stdout·stderr를 받아 줄 곳이 없다. launchd의 `StandardOutPath`/`StandardErrorPath`에 대응하는 것을 작업 정의만으로는 만들 수 없으므로, 작업의 동작은 숨김 subcommand `qsh service run <mode>`를 부른다. 이 진입점은 콘솔에서 떨어지고(`FreeConsole`) stdout·stderr를 `<state_dir>\log\<mode>.out.log`·`<mode>.err.log`(결정 9의 DACL, 덧붙이기)로 돌린 뒤 같은 run mode의 진입 함수를 부른다. 그 밖의 동작은 foreground `qsh serve`/`listen`/`serve --to`와 같다. clap에서 `hide = true`이고 man 페이지 생성기와 `--help` 목록에서 빠진다. 모든 플랫폼에서 파싱되지만 unix의 유닛은 이것을 부르지 않으며 unix에서 직접 치면 같은 리디렉션 뒤 같은 진입 함수를 부른다. 로그인 직후 콘솔 창이 잠깐 보였다 사라지는 것은 받아들인다.
    - 재시작. `RestartOnFailure`가 실행 중이던 동작의 비정상 종료에도 다시 띄우는지는 첫 서비스 스텝에서 확인한다. 다시 띄우지 않으면 로그온 트리거에 1분 간격 무기한 반복(`Repetition`)을 더하고 `IgnoreNew`로 중복 실행을 막아 같은 효과(1분 안의 재기동)를 얻는다. 어느 쪽이든 launchd `KeepAlive`, systemd `Restart=always`와 같이 재시작은 detach된 세션을 모두 지운다(`docs/deploy/service.md` Notes for both).
    - 수명. `InteractiveToken` 작업은 로그인한 세션 안에서 돌고 로그오프 때 멈춘다. systemd 사용자 유닛이 linger 없이 도는 것과 같은 수명이다. Linux는 `loginctl enable-linger $USER` 한 줄로 로그인 없이 부팅 때부터 사용자 유닛을 돌릴 수 있고(`docs/deploy/service.md`), qsh는 그 설정을 대신하지 않고 `doctor`의 `systemd_linger_disabled`로 알린다. Windows도 같은 수준으로 연다. `docs/deploy/service.md` Windows 절에 상시 기동 변형의 작업 정의 펜스(로그온 트리거에 시작 시 트리거 `BootTrigger`를 더하고 주체를 `LogonType=Password`로 둔 것)와 등록 명령 `schtasks /Create /F /TN \qsh\qsh-<mode> /XML <file> /RU <DOMAIN\user> /RP`(기본 작업이 이미 등록돼 있으면 덮어쓰도록 `/F`를 둔다. 암호는 프롬프트로 받는다)를 적는다. 사람이 한 번 치는 명령이라는 점과 qsh가 대신하지 않는다는 점이 linger와 같다. 주체를 `Password`로 두는 이유는 그래야 DPAPI가 살아 Credential Manager의 키를 읽기 때문이다. 암호를 저장하지 않는 S4U는 DPAPI가 없어 쓰지 않는다. 작업 스케줄러가 그 사용자의 암호를 보관하게 되고 암호를 바꾸면 다시 등록해야 한다는 점은 `service.md`가 적는다. 일반 사용자가 시작 시 트리거와 `Password` 주체로 작업을 등록할 수 있는지(일괄 작업으로 로그온 권한)는 첫 서비스 스텝에서 확인하고, 관리자 프롬프트가 필요하면 레시피에 그렇게 적는다. `loginctl enable-linger`도 배포판의 polkit 정책에 따라 권한을 묻는 것과 같은 처지다. macOS 상시 기동 레시피는 ADR-0032 결정 13이다.
    - 등록. 작업 등록은 `schtasks /Create /F /TN \qsh\qsh-<mode> /XML <path>`이고(`/F`는 재설치 때 저장된 정의를 새 경로로 덮어쓰기 위해서다) 해제는 `schtasks /End`와 `schtasks /Delete /F`다. 일반 사용자는 자기 계정으로 도는 작업을 관리자 권한 없이 등록할 수 있다. 이 레시피를 `docs/deploy/service.md`의 Windows 절에 적고, `service_docs.rs`가 렌더러 출력과 펜스를 대조한다(결정 17). `docs/deploy/service.md`의 supervised tunnel 예시에도 같은 형태의 Windows 작업 정의를 손으로 쓴 예시로 더한다.
    - `doctor`의 `service_not_registered`와 `service_restart_drops_sessions`는 위 작업 정의 파일 경로로 Windows에서도 낸다. `systemd_linger_disabled`에 대응하는 새 finding `logon_task_session_scoped`(warn)를 더한다. Windows에서만, 해당 mode의 작업이 등록돼 있고 그 주체가 `InteractiveToken`이면 뜬다. 등록 상태는 작업 스케줄러 COM API(`ITaskService` → `IRegisteredTask`의 정의 주체)로 읽고 subprocess는 띄우지 않는다. 읽지 못하면 linger 프로브의 "unknown"처럼 finding을 내지 않는다. remedy는 위 상시 기동 레시피를 가리킨다. `EXPECTED_DOCTOR_CODES`와 `docs/CLI.md` §6.17 표에 additive로 더한다. `qsh setup listener --service`와 `qsh setup host --service`의 `service` 단계는 다른 OS와 같이 이 백엔드를 부른다.
    - `ServiceInstallData`·`ServiceUninstallData`·`ServiceStatusData`의 `manager` 값은 Windows에서 `"task_scheduler"`다. 기존 문자열 필드에 새 값이 생기는 것이고 필드의 타입과 다른 플랫폼의 값은 바뀌지 않으므로 additive로 본다. `docs/CLI.md` §6.18의 값 목록과 버전 헤더에 착지 때 적는다.
28. ADR-0032 결정 3 표의 Windows 열이 이 결정을 옮긴 것이다. 활성화는 `schtasks /Create /F /TN \qsh\qsh-<mode> /XML <path>` 뒤 실행 중이 아니면 `schtasks /Run /TN \qsh\qsh-<mode>`, 비활성화는 등록돼 있으면 `schtasks /End` 뒤 `schtasks /Delete /F`다. 이 열은 2026-10-14부터 ADR-0032 결정 3 표에 들어 있고 실행 중 재등록과 고아 등록 규칙은 같은 ADR 결정 4·5가 정한다. 결정 27의 상시 기동 변형(`Password` 주체)이 등록돼 있으면 `--activate`는 `/Create`·`/Run`을, `--deactivate`는 `/End`·`/Delete`를 부르지 않는다(ADR-0032 결정 18, macOS LaunchDaemon과 같은 규칙). "이미 떠 있는지"(`status --live`와 결정 4의 재시작 회피)는 작업 스케줄러 COM API의 `IRegisteredTask::get_State`가 `TASK_STATE_RUNNING`인지로 판정한다. `schtasks /Query`의 exit code는 등록 여부만 알려 주고 실행 상태는 지역화된 본문에만 있어서, ADR-0032 결정 6의 "외부 출력을 파싱하지 않는다"를 지키려면 COM 호출이 유일한 길이다. 이 호출은 `ManagerRunner` seam 옆에 같은 모양의 작은 trait(작업 이름을 받아 실행 중 여부를 돌려준다)으로 두어 테스트가 가짜를 주입한다. ADR-0032의 `ManagerRunner` seam이 M19보다 늦게 서면 Windows 분기는 그 착지와 함께 들어간다.

## 근거

동등의 단위는 기능이고 기준은 플랫폼과 방향 둘 다다. `docs/PRD.md` §4(2026-10-13)는 정방향 route에서 되는 기능이 역방향 route에서도 되어야 하고, 같은 날 사용자 결정은 그 동등을 모든 플랫폼으로 넓혔다. 첫 개정이 그은 "client 역할만"이라는 선은 방향 간 동등은 지켰지만 Windows를 host가 될 수 없는 플랫폼으로 남겼고, 그 결과 Windows 장비는 `pair ssh`의 응답자도, 역방향 target도, 서비스로 상시 도는 listener도 될 수 없었다. 이 개정은 그 선을 지운다. 세 번째 개정의 사용자 결정대로 예외는 없다. Windows에 같은 이름의 OS 개념이 없는 기능은 "없으니 닫는다"가 아니라 "Windows에서 같은 일을 하는 수단으로 정의한다"로 다룬다. 신호(결정 22), man 페이지(결정 16), 로그인 밖 상시 기동(결정 27)이 그렇게 정해졌다.

host를 이 마일스톤에 넣는 비용은 ConPTY 백엔드가 대부분이고, 나머지는 unix에서 이미 내린 결정(로그인 환경 고정, process group 종료, 0600 상태 파일, `acl.toml` 경고, 회전 잠금)을 Windows 수단으로 옮기는 일이다. 새 설계 결정은 거의 없다. Job Object를 생성 시점에 붙이는 것은 `setsid`와 `killpg`가 주는 성질(자식이 만드는 모든 프로세스를 한 단위로 끝낸다)을 같은 시점에 얻는 유일한 방법이고, 그래서 `portable-pty`를 쓰지 않는다. `portable-pty`의 Windows `spawn`은 Job 목록 속성을 실을 자리가 없다.

host가 생기면 CI가 얻는 것이 크다. 첫 개정은 Windows 러너에 상대가 없어 대화형 attach의 종단을 사람 캠페인에, 역방향 종단을 PTY 없는 test-only 하니스에 맡겼다. 같은 러너의 loopback에 실제 `qsh serve`·`qsh listen`·`qsh serve --to`를 띄우면 정방향과 역방향을 같은 케이스 목록으로 돌릴 수 있고, ROADMAP §5.1 원칙 7이 요구하는 "두 route에서 같은 테스트"가 Windows에서도 문자 그대로 성립한다. test-only 상대는 지원 범위와 테스트 대상이 갈라지는 표면이었는데 그것도 사라진다.

서비스 백엔드로 작업 스케줄러의 로그온 작업을 고른 이유는 M9의 사용자 단위 모델과 맞는 Windows 수단이 이것뿐이어서다. M9의 systemd 사용자 유닛과 launchd LaunchAgent는 관리자 권한 없이 사용자가 직접 등록하고, 그 사용자로 로그인 세션 안에서 돌며, 암호를 어디에도 저장하지 않는다. Windows 서비스(SCM)로 같은 일을 하려면 세 가지가 어긋난다. 서비스 생성에 관리자 권한이 필요하다. 사용자 계정으로 돌리려면 그 사용자의 암호를 SCM에 저장해야 하고 암호를 바꾸면 서비스가 멈춘다. 서비스는 세션 0에서 돌아 사용자 프로필과 DPAPI 문맥이 대화형 로그온과 달라지므로 Credential Manager에 넣어 둔 키를 읽지 못할 수 있다. ConPTY 자체는 세션 0에서도 돌지만(OpenSSH Server가 그렇게 쓴다) 위 셋을 넘지 못한다. 작업 스케줄러의 `InteractiveToken` 로그온 작업은 세 가지를 모두 피하고 수명도 LaunchAgent와 같다. 대가는 로그 리디렉션과 콘솔 창을 qsh가 스스로 처리해야 한다는 점이고, 결정 27의 숨김 진입점 `qsh service run <mode>`가 그것을 맡는다. 숨김 subcommand는 clap 트리에 항목을 하나 더하지만 man 페이지와 `--help`에 나오지 않고 사람이 칠 이유가 없는 내부 표면이라, 공개 계약을 넓히지 않고 같은 일을 할 수 있는 가장 작은 모양이다. 로그인 밖 상시 기동은 Linux가 `loginctl enable-linger` 한 줄로 이미 갖고 있으므로 Windows도 같은 수준(사람이 한 번 치는 등록 명령과 그것을 알리는 doctor finding)으로 연다. 주체를 `Password`로 두는 것은 SCM을 기각한 이유 중 하나(암호 저장)를 다시 들이는 셈이지만, linger와 같이 사용자가 고르는 선택이고 기본 작업은 암호를 저장하지 않는다. S4U는 암호를 저장하지 않는 대신 DPAPI가 없어 Credential Manager의 키를 못 읽으므로 고르지 않는다.

신호는 오늘 `session close`의 첫 단계를 바꾸는 데만 쓰이고, 어느 신호로 시작하든 유예와 escalation 뒤 세션이 끝난다(`docs/CLI.md` §6.7). 그래서 Windows에서 신호마다 정할 것은 "프로세스에 무엇을 먼저 알리는가"이고, 거부할 이유가 없다. `Int`·`Quit`·`Hup`·`Term`은 Windows 콘솔이 가진 세 사건(`CTRL_C_EVENT`, `CTRL_BREAK_EVENT`, `CTRL_CLOSE_EVENT`)에 관례대로 사상된다. `Usr1`·`Usr2`는 Windows에 대응 사건이 없으므로 qsh가 통지 수단을 만든다. 프로그램이 직접 받기로 해야 받는 신호라는 점은 unix의 사용자 정의 신호와 같고, 받지 않는 프로그램은 unix 기본 동작처럼 세션 종료로 이어진다. 동작이 관찰 가능하고 테스트로 고정되므로(결정 17) 지원 범위에 든다.

Windows 코드 서명은 macOS의 Developer ID 서명·공증과 같은 자리이므로 같은 성질을 요구한다. 서명 주체가 유지보수자 본인이고, CI가 사람 개입 없이 서명하며, 타임스탬프로 인증서 만료 뒤에도 유효하고, 시크릿 게이트가 같은 모양이어야 한다. 이 기준으로 제공자를 비교했다. Azure Artifact Signing(구 Trusted Signing)은 월 비용이 가장 낮고 OIDC로 장기 시크릿 없이 서명할 수 있지만, 개인 개발자 신원 검증은 이 ADR을 쓰는 시점의 지식으로는 미국·캐나다 거주자에게만 열려 있었다. 한국 거주 개인은 자격이 없을 가능성이 높다. 확실하지 않으므로 사람이 계정 생성 때 확인하고, 자격이 열려 있으면 이쪽으로 바꾸는 개정을 연다. SignPath Foundation은 오픈 소스에 무료이고 유지보수자 국적과 무관하지만 서명 주체가 "SignPath Foundation"이라 macOS와 달리 유지보수자 이름이 보이지 않고, 재단의 프로젝트 승인과 릴리스마다 포털 승인 절차가 끼어 태그 push 하나로 끝나는 지금 흐름과 맞지 않는다. 그래서 대체 경로로만 남긴다. 전통 인증서는 2023년 6월부터 개인키를 하드웨어 보관해야 하므로 클라우드 HSM이 붙은 상품만 CI에 쓸 수 있다. Certum의 오픈 소스 개인 인증서는 싸지만 SimplySign이 세션마다 휴대폰 승인을 요구해 무인 서명이 어렵다. DigiCert KeyLocker·Sectigo 계열은 조직 검증 위주이고 비싸다. SSL.com은 개인 신원 검증(신분증 확인)을 국가 제한 없이 받고, eSigner 클라우드 HSM이 TOTP 시크릿으로 무인 서명을 지원하며, 공식 GitHub Action이 있다. 이것으로 정한다. EV 인증서는 2024년부터 SmartScreen 평판을 즉시 주지 않으므로 고르지 않는다. 평판은 서명된 다운로드가 쌓이며 생긴다.

winget과 scoop은 Homebrew tap에 대응한다. scoop은 Homebrew tap과 같은 "자기 저장소의 매니페스트를 bump한다" 모양이라 job을 거의 그대로 옮길 수 있다. winget은 중앙 저장소에 PR을 여는 모양이라 쓰기 권한이 그 저장소 포크로만 좁은 토큰이 필요하고, 병합은 winget 쪽 검증이 정한다. 두 경로 모두 서명된 바이너리를 가리키므로 서명과 같은 마일스톤에 둔다.

man 페이지는 Windows에 `man`이 없다는 이유로 빼지 않는다. 같은 바이트를 자산에 싣고, 같은 내용을 Windows에서 바로 읽는 경로는 이미 있는 `qsh help`로 둔다. 내장 roff 렌더러는 그 경로가 이미 주는 것을 다시 만드는 일이라 가장 싼 선택이 아니다.

절전 감지를 `QueryUnbiasedInterruptTime`으로 바꾸는 이유는 "확인하지 않은 동작"을 남기지 않기 위해서다. 첫 개정은 `Instant`가 절전 중 멈추는지 사람이 한 번 보고 README 문장만 고치기로 했는데, 그러면 결과가 "멈추지 않음"일 때 Windows만 `wake` 이벤트가 없는 플랫폼 차이가 남는다. 절전 시간을 빼도록 문서화된 카운터를 표본으로 쓰면 결과와 무관하게 감지기가 다른 OS와 같은 성질을 갖는다.

초대 코드 콘솔 프롬프트는 첫 개정이 검증 수단이 없다는 이유로 막았다. ConPTY 테스트(결정 17)가 이미 콘솔 계층을 고정하므로 같은 수단으로 "입력한 코드가 출력에 나타나지 않는다"를 단언할 수 있다. 이 프로젝트의 원칙(비밀이 스크롤백에 남는 경로를 테스트 없이 열지 않는다)은 그대로이고, 조건이 충족되었으므로 연다.

나머지 근거는 첫 개정과 같다. named pipe는 같은 사용자 한정을 OS가 강제하는 수단 중 가장 직접적이다. pipe는 DACL로 소유자만 접속하게 만들 수 있고, 원격 접속 거부 플래그가 있으며, 서버와 클라이언트가 서로의 프로세스 토큰을 조회할 수 있다. unix에서 파일 모드와 `SO_PEERCRED`가 맡은 두 겹(접근 권한과 자격 확인)을 DACL과 SID 대조가 그대로 맡는다. pipe 이름 공간은 장비 전체에서 공유되므로 UDS 경로(사용자 디렉터리 안)에는 없는 선점 위험이 생기고, `FILE_FLAG_FIRST_PIPE_INSTANCE`와 클라이언트 쪽 서버 SID 확인이 그것을 막는다. 이름에 사용자 SID를 섞는 것은 보조이고 보안 경계는 DACL과 SID 대조다. crossterm을 쓰지 않는 이유는 architecture §8이 이미 댔다. Win32 콘솔 API는 VT 입력 모드 덕에 입력을 이미 xterm 바이트열로 준다. resize 폴링은 입력 읽기와 충돌하지 않는 유일한 방법이다. DACL을 만드는 순간에 거는 이유는 임시 파일이 rename 전에 상속 ACL로 읽힐 수 있어서다. resume token은 연결이 죽은 뒤에도 사는 유일한 자격이다(ADR-0007). Credential Manager는 다른 OS와 같은 기본값(`auto` = platform 우선)을 주고, 붙이지 못해도 파일 모드가 DACL로 보호되므로 기밀성은 같다.

## 대안과 기각 사유

- **host 역할을 P2에 둔다(첫 개정).** 기각한다. 2026-10-13 사용자 결정이 플랫폼 간 동등을 요구한다. 첫 개정의 논리("정방향 `serve`와 역방향 `serve --to`가 같이 P2이므로 방향 간 동등은 유지된다")는 방향 축만 보았다.
- **M19 하나에 client와 host를 모두 둔다.** 기각한다(2026-10-13 마일스톤 결정). 11.3~19.2ew로 P1에서 가장 크고 신뢰도도 가장 낮다. M19 Windows client와 M20 Windows host로 나누고 결과 절이 결정마다 착지 마일스톤을 적는다. 나누어도 P1 완료 선언은 두 쪽이 모두 닫혀야 한다.
- **ConPTY 백엔드를 `portable-pty`의 Windows 구현으로 만든다.** 기각한다. Job Object를 생성 시점에 붙일 자리가 없어 자식과 Job 할당 사이에 손자 프로세스가 새어 나갈 틈이 생긴다. `portable-pty`는 테스트 쪽(`qsh-testkit`의 ConPTY 구동)에서는 쓸 수 있다.
- **세션 셸로 OpenSSH for Windows의 `DefaultShell` 레지스트리 값을 읽는다.** 기각한다. 다른 제품의 설정을 qsh의 동작 근거로 삼게 되고, 그 값이 없을 때의 기본(`cmd.exe`)은 결정 21과 같다. 사용자가 셸을 고르는 경로는 argv로 이미 있다.
- **신호 셋 전체를 Windows에서 `TerminateJobObject` 하나로 사상한다.** 기각한다. 콘솔 사건 셋이 프로세스에 정리할 기회를 주는데 그것을 버리게 된다.
- **`Quit`·`Usr1`·`Usr2`를 Windows에서 `UNSUPPORTED`로 거부한다(두 번째 개정).** 기각한다. 원칙에 예외를 두지 않는다는 사용자 결정에 어긋나고, 신호가 close 절차의 첫 단계일 뿐이라 거부할 이유도 없다(근거 절).
- **`Int`를 ConPTY 입력에 `0x03`을 써서 보낸다.** 기각한다. 앱이 처리된 입력을 끄면 사건이 아니라 문자가 된다. unix의 `killpg(SIGINT)`는 tty 모드와 무관하게 닿는다.
- **`Usr1`·`Usr2`를 `CTRL_BREAK_EVENT`나 `CTRL_C_EVENT`에 겹쳐 사상한다.** 기각한다. 받는 쪽이 `Quit`/`Int`와 구별할 수 없어 신호를 둘로 나눈 뜻이 사라진다.
- **`Usr1`·`Usr2`를 세션 PTY 입력에 정해진 바이트열로 넣는다.** 기각한다. 그 바이트는 셸과 앱의 입력에 섞여 의도하지 않은 명령이 될 수 있다.
- **서비스 백엔드를 Windows 서비스(SCM)로 만든다.** 기각한다(근거 절). 관리자 권한, 암호 저장, 세션 0의 프로필·DPAPI 문맥 셋이 M9의 사용자 단위 모델과 어긋난다.
- **서비스 백엔드를 시작 프로그램 폴더의 바로가기나 `HKCU\...\Run` 값으로 만든다.** 기각한다. 로그온 때 한 번 띄울 뿐 비정상 종료 뒤 다시 띄우는 수단이 없어 `KeepAlive`/`Restart=always`에 대응하지 못한다.
- **작업 스케줄러 작업을 S4U 로그온으로 등록해 콘솔 창과 로그 문제를 피한다.** 기각한다. 기본 작업의 수명이 로그인 세션 밖으로 바뀌어 linger를 사용자가 고르는 Linux 모델과 어긋나고, DPAPI가 없어 Credential Manager의 키를 읽지 못한다.
- **로그인 밖 상시 기동을 범위 밖에 둔다(두 번째 개정).** 기각한다. Linux는 linger로 이미 그 길이 있고 doctor가 알린다. Windows만 없으면 플랫폼 간 차이다.
- **숨김 진입점 없이 작업이 `qsh.exe listen`을 직접 부른다.** 기각한다. 로그 파일이 없고 로그인 내내 콘솔 창이 떠 있다.
- **`schtasks.exe` 대신 처음부터 작업 스케줄러 COM API로 등록한다.** 이번에는 채택하지 않는다. M9 범위(파일 쓰기와 존재 확인)에는 매니저 호출이 없고, 등록 레시피는 사람이 치는 명령이라 `schtasks`가 문서로 더 낫다. 실행 상태 질의(결정 28)만 COM이 필요하다.
- **역방향 종단 테스트에 test-only target 하니스를 쓴다(첫 개정).** 기각한다. Windows에 실제 `qsh serve --to`가 생겼으므로 지원 범위와 테스트 대상이 같은 CLI가 되는 쪽이 낫다. 하니스는 PTY attach와 resume을 볼 수 없었다.
- **Windows 러너 안에서 대화형 attach를 종단 테스트하지 않고 사람 캠페인에 맡긴다(첫 개정).** 기각한다. 같은 러너의 loopback에 host가 있으므로 ConPTY 안에서 client를 구동해 CI가 본다. 캠페인은 실제 터미널 렌더링과 두 장비 사이 경로처럼 CI가 볼 수 없는 것만 맡는다.
- **절전 감지의 Windows 동작을 확인만 하고 README로 알린다(첫 개정).** 기각한다(근거 절).
- **초대 코드 콘솔 프롬프트를 `UNSUPPORTED`로 유지한다(첫 개정).** 기각한다(근거 절). 검증 수단이 생겼다.
- **crossterm으로 콘솔을 다룬다.** 기각한다. architecture §8의 이유와 Windows API 표면을 키 이벤트 계층까지 끌어오는 비용 때문이다.
- **TCP loopback으로 localctl을 연다.** 기각한다. 127.0.0.1의 포트는 같은 장비의 모든 로컬 사용자가 접속할 수 있고, 접속한 쪽의 사용자를 확인할 수단이 소켓에 없다. 포트를 파일로 광고하고 토큰을 요구하는 방식은 그 토큰의 파일 권한 모델을 다시 만드는 일이며, 선점도 막지 못한다.
- **Windows의 AF_UNIX 소켓을 쓴다.** 기각한다. 최소 지원 버전(1809)에서 `SO_PEERCRED`에 해당하는 peer 프로세스 조회가 확실하지 않고, 소켓 파일의 접근 통제도 NTFS ACL에 기대서 결정 9처럼 우리가 걸어야 하므로 pipe보다 얻는 것이 없다. tokio는 Windows에서 named pipe를 지원하지만 UDS는 지원하지 않는다.
- **`WINDOW_BUFFER_SIZE_EVENT`로 resize를 받는다.** 기각한다. 입력을 레코드로 읽게 되어 바이트 그대로 전달 규율이 깨진다.
- **`icacls`나 PowerShell로 ACL을 설정한다.** 기각한다. 생성과 설정 사이에 노출 구간이 생기고 외부 프로세스·로캘 의존이 들어온다.
- **상속 ACL을 그대로 둔다.** 기각한다. 프로필 디렉터리나 `QSH_STATE_DIR`를 다른 곳으로 둔 경우 보장이 없고, 보장이 환경에 달린 기밀성은 테스트로 고정할 수 없다.
- **`%APPDATA%`/`%LOCALAPPDATA%`에 둔다.** 기각한다. ssh 스타일 예측 가능성(`.config/qsh`)을 세 OS에서 맞추는 쪽이 문서와 지원 비용이 낮고, OpenSSH for Windows도 `%USERPROFILE%\.ssh`를 쓴다. `%APPDATA%`는 로밍 프로필로 복제될 수 있어 키 파일에는 오히려 나쁘다.
- **x86_64 자산 하나만 낸다(첫 개정).** 기각한다. macOS·Linux가 두 아키텍처를 내므로 같은 선을 Windows에 긋는다. 교차 빌드 비용이 작다.
- **Windows 자산을 서명하지 않는다(두 번째 개정까지).** 기각한다. 2026-10-13 사용자 결정이고, macOS 서명·공증과 같은 자리다.
- **Azure Artifact Signing으로 서명한다.** 지금은 채택하지 않는다(근거 절). 한국 거주 개인의 자격이 확인되면 바꾼다.
- **SignPath Foundation으로 서명한다.** 대체 경로로만 둔다(근거 절). 서명 주체가 유지보수자가 아니고 릴리스마다 포털 승인이 끼어든다.
- **EV 인증서를 쓴다.** 기각한다. 2024년부터 SmartScreen 평판을 즉시 주지 않아 OV·개인 검증보다 얻는 것이 없고 비싸다.
- **MSI 설치 관리자를 만든다.** 이번에는 넣지 않는다. macOS·Linux도 패키지 관리자와 설치 스크립트로 내고 `.pkg`·`.deb`를 만들지 않으므로 같은 선이다.
- **man 페이지용 roff 렌더러를 `qsh`에 내장한다.** 기각한다(근거 절).
- **doctor에 Windows 파일 ACL 점검 finding을 더한다.** 넣지 않는다. unix에는 대응하는 finding이 없으므로(읽을 때 검사하지 않는다) 더하면 오히려 Windows만의 표면이 된다. `acl.toml`은 결정 24의 경고가 unix와 같은 자리에서 맡는다.
