# ADR-0035: Windows client는 정방향·역방향의 client 쪽 명령(listener 데몬과 named pipe localctl 포함)과 콘솔 raw 모드 대화형 attach까지 연다. host 역할은 두 방향 모두 열지 않는다

날짜: 2026-10-11 (개정 2026-10-13)
상태: 제안됨

개정 관계: 새 ADR이다. 2026-10-13 사용자 결정(정방향과 역방향은 같은 기능을 갖는다, `docs/PRD.md` §4 '연결 방향과 역할의 분리', `docs/ROADMAP.md` §5.1 원칙 7)과 "Windows client의 역방향 지원을 M19에 넣는다"는 결정으로, 초안이 닫아 둔 `qsh listen`과 localctl 대체(named pipe)를 열도록 결정 1·2·14·15·17~19와 맥락·근거·대안·결과를 고쳤다. `docs/ROADMAP.md` M19(§5)가 이 번호를 Windows client 착수 ADR로 예약했다. 다른 ADR의 결정을 뒤집지 않는다. ADR-0007(resume token custody)에는 "Windows에서 `resume.json`의 기밀성"이라는 빈칸을 채우는 구현을 더한다. ADR-0043(TCP fallback 철회)로 transport는 QUIC 하나이므로 Windows 방화벽·프록시 환경을 위한 우회 경로는 이 ADR의 범위가 아니다. 계약 문서로는 `docs/CLI.md` §4·§6.9·§6.13·§6.14·§6.17·§6.20·§7에 Windows 문장을 더하고 `docs/design/architecture.md` §7·§8, `docs/design/threat-model.md` §3·§4, README Known limitations와 `docs/ROADMAP.md` §3 가드레일 표의 Windows 행을 고친다.

## 맥락

`docs/PRD.md` §7은 Windows client를 P1, Windows host를 P2에 둔다. 오늘 Windows 빌드는 CI에서 컴파일되고 portable 테스트를 도는 수준이다(`ci.yml`의 `test`·`clippy` Windows leg, `release.yml`의 `x86_64-pc-windows-msvc` zip). 지원 약속은 아니다. 실제로 Windows에서 되는 것과 안 되는 것은 이렇다.

- `exec`, `trust`, `identity`, `tunnel open`(`-L`/`-R`/`-D`), `session` value op는 터미널이나 UDS에 기대지 않아 그대로 돈다. `release_smoke`의 `#[cfg(not(unix))]` 쌍둥이가 `init` → `trust` → `exec --json` 왕복까지 본다.
- 대화형 attach(`tui::run`)는 `#[cfg(not(unix))]`에서 `UNSUPPORTED`다. raw 모드는 `nix` termios, 크기는 `TIOCGWINSZ`, resize는 `SIGWINCH`라서 `crates/qsh-cli/src/tui/term.rs`와 `tui/unix.rs`가 통째로 unix 전용이다. `docs/design/architecture.md` §8은 crossterm을 "TUI는 키를 파싱하지 않고 raw byte를 흘려야 한다"는 이유로 채택하지 않았고, 그 이유는 Windows에서도 그대로다.
- localctl(UDS)은 `localctl/` 모듈 트리 전체가 `#[cfg(unix)]`라서 Windows에서 컴파일되지 않는다. 데몬의 소켓은 `$XDG_RUNTIME_DIR/qsh/<pid>.sock`(없으면 `<state_dir>/run/<pid>.sock`)이고 디렉터리 0700, 소켓 0600이며, accept마다 프레임을 읽기 전에 peer euid를 `UnixStream::peer_cred`(Linux `SO_PEERCRED`, macOS `getpeereid`)로 대조한다(`crates/qsh-core/src/localctl/mod.rs` 모듈 doc의 신뢰 모델). 그 게이트가 `qsh listen`의 기동 경로(`reverse/listen.rs`의 `run_listen_unix`)와 reverse hub·conn table·등록 처리의 쌍둥이 메서드까지 번져 있어서, 오늘 `qsh listen`은 Windows에서 `UNSUPPORTED`이고 `qsh hosts`는 forward host만 낸다(`docs/CLI.md` §6.13). 터널은 열린 프로세스에만 산다(`docs/CLI.md` §6.14). `qsh serve --to`가 Windows에서 막히는 이유는 다르다. host 역할이 PTY에 기대기 때문이고(위 목록의 마지막 항목), target 경로 자체(`reverse/target`)는 테스트 빌드에서 이미 Windows에서 컴파일된다.
- 키·상태 파일의 권한이 없다. `ensure_private_dir_io`와 `write_private_file_io`는 `cfg(not(unix))`에서 `create_dir_all`과 모드 없는 임시 파일 + rename(`fsutil::write_atomically`)으로 떨어져, 파일은 상위 디렉터리의 상속 ACL을 받는다. `crates/qsh-core/src/resume.rs` 모듈 doc은 이 상태를 적고 `resume.json`의 기밀성을 Windows client P1의 일부로 둔다.
- keystore는 Windows에서 stub이다. 모든 연산이 `KeyStoreError::Unavailable`을 내므로 `auto`는 파일 모드로 떨어진다(`identity/keystore.rs`). 파일 모드의 개인키는 위 상속 ACL에 놓인다.
- 초대 코드를 터미널에서 받는 프롬프트는 에코 억제가 없어 `UNSUPPORTED`다(`NO_TERMINAL_ECHO_SUPPRESSION`).
- Windows host(ConPTY 백엔드)는 PTY 백엔드(`pty/posix.rs`)가 `#[cfg(unix)]`이고 `pty::factory()`가 비unix에서 `UnsupportedFactory`를 돌려줘서 없고 P2다. `qsh serve`는 Windows에서 뜨지만 PTY 세션을 열 수 없고 `exec`와 터널만 낸다.

`docs/ROADMAP.md` §5.4 위험 5는 비교 표본이 없는 Windows 산정을 "ADR이 명령 집합을 좁히고 첫 스텝 뒤 다시 매긴다"로 다루기로 했다. 이 ADR의 중심 결정은 좁히는 선이다. 설계를 가르는 사실은 셋이다.

- 대화형 attach가 이 마일스톤의 가치 대부분이다. 나머지 명령은 이미 돌고, 모자란 것은 기밀성과 콘솔이다.
- Windows에는 host가 없으므로 Windows 러너 안에서 대화형 attach를 끝까지 돌릴 상대가 없다. 대화형 종단 확인은 사람 캠페인(`docs/ROADMAP.md` §5.5)이 맡고, CI는 콘솔 계층을 따로 고정해야 한다.
- 정방향과 역방향은 같은 기능을 갖는다는 원칙(`docs/PRD.md` §4)이 선을 정한다. 연결 방향마다 같은 선을 긋는다. client 쪽 역할은 두 방향 모두 열고(정방향의 `qsh <name>`·`exec`·`attach`·`tunnel`, 역방향의 `qsh listen`과 그 데몬을 거치는 같은 명령들), host 쪽 역할은 두 방향 모두 P2에 둔다(정방향 `qsh serve`, 역방향 `qsh serve --to`). 역방향의 client 쪽은 controller, 곧 listener 데몬이고, 데몬이 서려면 CLI 프로세스와 데몬 사이의 IPC(localctl)가 Windows에 있어야 한다. 그래서 localctl 대체(named pipe)는 이 마일스톤의 일이다.

## 결정

### A. 명령 집합

1. Windows client가 여는 명령은 다음이다. 선은 `docs/PRD.md` §4가 정한다. 연결 방향과 무관하게 client 쪽 역할(셸·exec·세션·터널·파일 복사를 얻는 쪽)은 열고 host 쪽 역할(내주는 쪽)은 닫는다. 직접 연결(direct route)에서 나가는 명령과 reverse route 위의 명령이 같은 명령 이름이다.
   - `qsh init`, `qsh identity export`, `qsh trust add|add-ca|list|rename|remove`, `qsh trust ssh-preview`
   - `qsh pair accept`(초대 코드는 인자 또는 `--code-stdin`의 파이프·파일 입력, 결정 11)
   - `qsh pair ssh [--reverse]`(ADR-0044 결정 25와 결정 22). 정방향은 Windows가 `ssh.exe`로 원격 host에 닿아 양쪽 pin을 세운다. `--reverse`는 Windows 장비가 listener이고 원격이 target이다. 이 장비의 pin은 원격을 주소 없이 role `reverse`로 쓴다. 응답자(원격)가 Windows이면 ADR-0044 결정 10대로 거부한다.
   - `qsh exec`
   - `qsh session open|get|read|write|resize|close`, `qsh sessions`, `qsh tunnels`, `qsh tunnel close`와 대화형 `qsh [user@]host`, `qsh attach <session-ref>`(결정 5~8)
   - `qsh tunnel open --local|--remote|--dynamic`과 대화형 `-L`/`-R`/`-D`. forward route에서는 터널을 연 프로세스가 holder인 모델 그대로이고, reverse route에서는 데몬의 reverse connection이 carrier다(`docs/CLI.md` §6.14).
   - `qsh cp`(ADR-0029). 로컬 operand는 한 글자 뒤의 `:`를 드라이브 문자로 보고 로컬로 해석한다(ADR-0029 operand 해석 결정이 이 ADR의 승인을 조건으로 둔 문장이다). 정방향과 역방향(ADR-0029 결정 16) 모두 연다. 받은 파일의 권한은 결정 9의 소유자 전용 DACL이 아니라 사용자가 고른 경로의 상속 ACL이고 mode 비트는 쓰지 않는다. 이 처리가 ADR-0029의 mode·덮어쓰기 규칙과 맞는지는 `qsh cp` 착지 때 확인하고 어긋나면 이 ADR을 개정한다. ADR-0029가 착지하기 전이면 이 항목은 착지와 함께 열린다.
   - `qsh listen`과 `qsh setup listener`. 이 장비가 reverse controller가 되는 listener 데몬이고, 데몬과 CLI 프로세스 사이의 IPC는 결정 14의 named pipe다. 데몬이 서면 같은 장비의 `qsh hosts`는 reverse 항목을 내고, `qsh tunnels`는 데몬이 쥔 터널을 낸다. `qsh <name>`·`attach`·`exec`·`session`·`cp`·터널이 reverse route를 고르면 데몬을 거쳐 나간다(`docs/CLI.md` §6.13). `qsh pair ssh --reverse`로 세운 신뢰가 이 데몬과 이어진다.
   - `qsh doctor`, `qsh setup client`, `qsh acl check`, `qsh acl show`, `qsh hosts`, `qsh host`, `qsh schema|capabilities|version`
2. 열지 않는 명령은 리소스를 만들기 전에 `UNSUPPORTED`와 exit `255`로 끝난다. 대상은 host 쪽 역할이고 두 방향이 같다.
   - `qsh serve --to`와 숨김 alias `qsh reverse`(역방향의 host 쪽. 오늘 동작 그대로이고 `qsh listen`이 서도 바뀌지 않는다)
   - `qsh setup host`(`--to` 형태 포함)와 `qsh pair invite`(상환 창구를 여는 host 쪽 명령)
   - `qsh service install|uninstall|status`(M9가 고정한 동작 그대로). 이것은 host 쪽이라서가 아니라 서비스 매니저 백엔드가 없어서 닫는 예외다. listener 데몬을 서비스로 띄우는 `service install`이 Windows에 있으면 편하지만, 지금 백엔드는 systemd 사용자 유닛과 launchd뿐이고 Windows는 Service Control Manager 또는 작업 스케줄러라는 다른 모델과 로그온 세션 모델이 따로 필요하다(ADR-0032 범위). 원칙 7이 요구하는 것은 방향 간 동등이고 플랫폼 간 동등이 아니다. Windows에서 listener 데몬은 사용자가 띄운 foreground 프로세스(또는 사용자가 직접 걸어 둔 작업 스케줄러 항목)이고, 로그오프나 재부팅 뒤에는 사람이 다시 띄우거나 그 항목이 다시 띄운다. `qsh setup listener --service`는 `service` 단계가 오류가 아니라 `skipped`가 된다(`docs/CLI.md` §6.20). README는 이 한계를 적는다.
   - 인바운드 `qsh serve`는 Windows에서 막지 않는다. 오늘처럼 뜨되 PTY 세션 요청에는 `UNSUPPORTED`로 답하고 `exec`와 터널만 낸다. 지원 약속은 아니며 테스트 상대(`release_smoke`, 결정 17)로만 쓴다. README는 이 사실을 "host 역할은 P2이며 이 모양은 지원 범위가 아니다"로 적는다. `qsh serve --to`를 같은 식으로 열지는 않는다. 오늘 `UNSUPPORTED`로 막혀 있어서 열면 새 표면이 생기고, 결정 17의 역방향 테스트 상대는 CLI가 아니라 테스트 하니스 안에서 연다.
3. 위 두 목록을 테스트가 고정한다. `crates/qsh-cli/tests/exit_code_matrix.rs`에 `cfg(windows)` 행을 더해 2번의 각 명령이 `UNSUPPORTED`/exit `255`로 끝나고 상태 디렉터리에 아무것도 만들지 않음을 단언한다. `qsh listen`은 이 행에 들지 않고 기능 테스트가 맡는다(결정 17). 열린 명령의 동작은 기존 테스트가 Windows leg에서 돈다. `cfg(unix)`로 빠져 있던 테스트 중 POSIX 신호·process-group이 아닌 이유로 빠진 것은 이 마일스톤에서 `cfg(windows)` 쌍둥이를 갖거나 빠진 이유를 주석으로 남긴다.

### B. 콘솔과 대화형 attach

4. Windows 콘솔 제어는 `windows-sys`의 Win32 콘솔 API를 `qsh-cli`의 `tui/`에 직접 쓴다. crossterm은 채택하지 않는다(`docs/design/architecture.md` §8의 이유 유지). `qsh-core`는 콘솔을 모른다. 대화형 루프는 `tui/unix.rs`에서 플랫폼 중립 부분(escape 처리, 이벤트 루프, 스레드 구성, 종료 코드 매핑)을 꺼내 작은 터미널 trait(raw 모드 guard, 창 크기 조회, stdin 읽기, 끊김 신호)에 올리고, unix와 Windows가 각자 구현한다. 이 추출은 unix 동작을 바꾸지 않는다.
5. raw 모드는 입력 핸들에서 `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, `ENABLE_PROCESSED_INPUT`을 끄고 `ENABLE_VIRTUAL_TERMINAL_INPUT`을 켠다. 출력 핸들은 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`과 `DISABLE_NEWLINE_AUTO_RETURN`을 켠다. 입출력 코드 페이지는 UTF-8(65001)로 바꾸고 원래 값과 두 핸들의 원래 모드를 저장한다. 키는 파싱하지 않는다. VT 입력이 만든 바이트를 그대로 원격 PTY로 보낸다(`docs/CLI.md` §7). 행 시작 escape 처리는 unix와 같은 코드가 한다. `Ctrl-C`는 `ENABLE_PROCESSED_INPUT`이 꺼져 있으므로 `0x03` 바이트로 원격에 간다.
6. 복원은 모든 종료 경로에서 일어난다. 정상 종료와 오류 종료는 guard의 `Drop`, panic은 전역 slot을 쓰는 panic hook, 콘솔 창 닫기·`CTRL_BREAK`·로그오프·종료(`SetConsoleCtrlHandler`가 받는 `CTRL_CLOSE_EVENT`·`CTRL_BREAK_EVENT`·`CTRL_LOGOFF_EVENT`·`CTRL_SHUTDOWN_EVENT`)는 핸들러가 맡는다. 복원 함수는 멱등이다(unix의 `restore`와 같은 규율). 핸들러가 받은 이벤트는 unix의 SIGHUP/SIGTERM과 같이 detach로 처리한다. 세션은 서버에 남는다(`docs/CLI.md` §7).
7. 콘솔을 준비하지 못하면 세션을 열기 전에 끝낸다. 출력 핸들에 VT 처리를 켤 수 없는 환경(Windows 10 1809 미만의 conhost)이면 `UNSUPPORTED`로 끝나고, 메시지는 최소 버전을 적는다. 이 판정은 `session.open`보다 먼저이므로 호스트에 고아 세션이 생기지 않는다. stdin이 콘솔이 아닌 경우(파이프, 파일 리디렉션, Git Bash의 mintty처럼 pty 대신 파이프를 주는 터미널)는 unix의 비 tty 경로와 같다. raw 모드도 escape 처리도 없이 바이트를 그대로 흘린다(`docs/CLI.md` §7). README는 mintty 계열에서는 `winpty`나 Windows Terminal을 쓰라고 적는다.
8. resize는 이벤트 없이 폴링한다. `WINDOW_BUFFER_SIZE_EVENT`는 `ReadConsoleInput`으로만 오고 그것은 바이트 그대로 읽는 입력 경로와 충돌한다. 전용 스레드가 200 ms마다 `GetConsoleScreenBufferInfo`의 창 영역(`srWindow`) 크기를 읽어 직전 값과 다를 때만 `session.resize`를 보낸다. 최초 크기는 `session.open`에 싣는다. 폴링 간격은 상수로 두고 설정 키는 만들지 않는다. `SessionOpen.term`은 `TERM`이 있으면 그 값, 없으면(Windows의 일반 상태) 7번의 VT 입출력이 켜졌을 때 `xterm-256color`다. locale 환경변수는 Windows에 보통 없으므로 있을 때만 보낸다(`docs/CLI.md` §7 전달 목록의 기존 규칙).

### C. 파일 권한, keystore, 경로

9. 소유자 전용 DACL을 만드는 단일 모듈을 `qsh-core`(`fsutil` 하위)에 둔다. 만드는 쪽은 프로세스 토큰의 사용자 SID로 보호된(protected, 상속 차단) DACL 하나를 쓴다. 파일은 소유자 SID에 `FILE_ALL_ACCESS` ACE 하나, 디렉터리는 같은 SID에 `OBJECT_INHERIT | CONTAINER_INHERIT` ACE 하나다. 파일과 임시 파일은 `CreateFileW`의 `SECURITY_ATTRIBUTES`로 만드는 순간부터 이 DACL을 갖는다. 만든 뒤에 `icacls`로 고치지 않는다(생성과 설정 사이에 상속 ACL로 읽히는 구간이 생기고, 외부 프로세스·로캘에 기대게 된다). 기존 `ensure_private_dir_io`, `write_private_file_io`, resume 저장소의 임시 파일 생성이 `cfg(windows)` 분기에서 이 모듈을 부른다. 대상은 qsh가 Windows에서 쓰는 파일과 디렉터리 전부다. 곧 `identity/device.pem`·`device.key`(파일 모드), `trust.toml`, `config.toml`(쓰는 경우), `resume.json`과 그 `.tmp`·`.lock`, 그리고 config·state 디렉터리다.
10. DACL을 적용하지 못하면 파일을 만들지 않고 fail closed한다. SID 조회 실패, ACL을 지원하지 않는 파일시스템(FAT/exFAT, 일부 네트워크 공유)이 이유다. 오류는 기존 `config_io_error`의 `CONFIG_ERROR`이고 메시지에 경로와 원인을 담는다. 이미 있는 파일이 옛 빌드의 상속 ACL로 만들어졌다면 다음 쓰기(임시 파일 + rename)가 소유자 전용 DACL로 바꿔 놓는다. 읽기 전용 경로는 열 때 ACL을 검사하지 않는다. unix가 `acl.toml` 외에는 읽을 때 모드를 검사하지 않는 것과 같다(README Known limitations의 "Windows ACL checking is out of scope"는 host의 `acl.toml` 이야기라 그대로다).
11. 초대 코드를 터미널 프롬프트로 받는 경로는 Windows에서 `UNSUPPORTED`로 유지한다(`NO_TERMINAL_ECHO_SUPPRESSION`). `qsh pair accept <address> <code>`의 인자와 `--code-stdin`의 파이프·파일 입력은 연다. `--code-stdin`의 stdin이 콘솔이면 같은 `UNSUPPORTED`다(오늘은 콘솔 stdin도 에코를 끄지 않은 채 받아들이므로 `docs/CLI.md` §6.11대로 이 결정이 새로 막는 동작이다). 콘솔 에코 억제는 결정 5의 모드 비트로 구현할 수 있지만 CI가 콘솔 stdin을 만들 수 없어 에코가 실제로 꺼졌는지 단언할 방법이 없다. 단언할 수 없는 비밀 입력 경로는 열지 않는다. 열지 말지는 에코 억제를 ConPTY로 검증하는 후속 결정으로 미룬다(대안 절).
12. keystore는 Windows Credential Manager를 `platform` store로 붙인다. keyring-core 계열 store crate 하나를 `cfg(windows)` 의존으로 더하고, `auto`는 다른 OS와 같이 platform을 먼저 시도하고 `Unavailable`이면 파일 모드(결정 9의 DACL)로 떨어진다. store 호출은 다른 플랫폼과 같이 연산마다 열고 전역 기본 store를 등록하지 않는다. 개인키 blob은 Credential Manager의 크기 상한 안이다. 이 crate가 존재하지 않거나 `deny.toml`(license·advisory)을 못 넘으면 Windows `platform`은 지금처럼 `Unavailable`로 두고 `auto`가 파일 모드를 쓰도록 이 결정의 후반을 접는다. 이 판정은 첫 스텝에서 하고 접으면 이 ADR을 개정한다. 실제 store 왕복은 CI가 못 보므로 다른 플랫폼과 같이 릴리스 전 수동 단계다(`docs/design/testing.md` L1 「플랫폼 키스토어 릴리스 전 수동 단계」에 Windows 줄을 더한다).
13. config·state 경로는 ssh 스타일 예측 가능성을 따른다(`docs/design/architecture.md` §7). Windows에서도 `%USERPROFILE%\.config\qsh`와 `%USERPROFILE%\.local\state\qsh`이고 `QSH_CONFIG_DIR`·`QSH_STATE_DIR`·`XDG_*` 우선순위는 그대로다(`Paths::from_env`의 `home_dir()`가 이미 플랫폼 홈을 고른다). `%APPDATA%`와 `%LOCALAPPDATA%`는 쓰지 않는다. runtime dir은 만들지 않는다. `Paths::runtime_dir()`의 값은 결정 14의 pipe 이름에 섞는 입력일 뿐이다.

### D. localctl, service, supervise

14. localctl transport를 Windows named pipe로 연다. 모양은 unix의 신뢰 모델(`crates/qsh-core/src/localctl/mod.rs` 모듈 doc의 "localctl은 새 권한을 주지 않는다. 같은 OS 사용자만 붙는다")을 그대로 옮긴다.
    - 이름. `\\.\pipe\qsh-<scope>-<pid>`이다. `<scope>`는 현재 프로세스 토큰의 사용자 SID 문자열과 `Paths::runtime_dir()`의 정규 경로(소문자화)를 NUL로 이어 SHA-256을 낸 앞 16 hex다. 사용자 SID와 state dir(곧 `QSH_STATE_DIR`)이 다르면 이름 공간이 갈라져 서로의 데몬을 보지도 건드리지도 않는다. 데몬은 한 번에 하나의 `<pid>`를 쓴다. 발견(`qsh hosts`, `qsh tunnels`)은 `\\.\pipe\`를 열거해 `qsh-<scope>-*` 접두에 맞는 이름만 후보로 삼는다. unix의 `candidate_sockets`가 `<pid>.sock`을 거르는 것과 같다. pipe는 프로세스가 죽으면 사라지므로 오래된 파일을 지우는 경로(unix의 stale 소켓 교체)는 없다.
    - 생성. 서버는 첫 인스턴스를 `FILE_FLAG_FIRST_PIPE_INSTANCE`로 만든다. 그 이름이 이미 있으면(다른 프로세스가 선점했거나 같은 pid의 옛 인스턴스) 기동이 실패한다. 이는 pipe 이름 선점(squatting)을 거부하는 장치이고, 실패하면 QUIC listener를 열기 전에 끝난다(unix에서 runtime dir 권한을 못 박지 못하면 전체 기동이 실패하는 것과 같다). `PIPE_REJECT_REMOTE_CLIENTS`를 항상 켠다. `PIPE_TYPE_BYTE`·`PIPE_READMODE_BYTE`로 두고 프레이밍은 `localctl/frame.rs`가 맡는다.
    - 접근 통제. 모든 인스턴스를 결정 9의 DACL 모듈이 만든 보호된(protected) 소유자 전용 DACL로 만든다. 소유자 SID에 pipe 읽기·쓰기와 `FILE_CREATE_PIPE_INSTANCE`를 주는 ACE 하나다. pipe의 기본 DACL은 Everyone·익명에 읽기를 주므로 반드시 명시한다. 다음 연결을 받을 인스턴스는 현재 연결을 넘기기 전에 만들어 두어, 이름이 빈 틈이 생기지 않게 한다. 소유자 외에는 `FILE_CREATE_PIPE_INSTANCE`가 없으므로 다른 사용자는 같은 이름에 인스턴스를 더 만들지도 못한다.
    - 자격 확인(unix `peer_cred`의 대응). 서버는 accept한 연결마다 프레임을 한 바이트도 읽기 전에 `GetNamedPipeClientProcessId`로 클라이언트 프로세스를 열어(`PROCESS_QUERY_LIMITED_INFORMATION`) 토큰의 사용자 SID가 자기와 같은지 대조한다. 다르거나 조회에 실패하면 말 없이 끊는다. 클라이언트는 연결 직후 첫 프레임을 쓰기 전에 `GetNamedPipeServerProcessId`로 서버 프로세스의 토큰 사용자 SID가 자기와 같은지 대조한다. 다르거나 조회에 실패하면 그 후보를 데몬이 아닌 것으로 건너뛰고 아무것도 보내지 않는다. 클라이언트는 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`으로 열어 가짜 서버가 클라이언트 토큰을 가장(impersonate)하지 못하게 한다. 이 확인은 DACL 뒤의 두 번째 겹이다. 프로세스 ID 재사용과 조회 사이의 틈이 이론상 남지만, DACL이 소유자 밖의 접속을 이미 막으므로 이 확인이 막는 것은 DACL이 틀렸거나 서버가 가짜인 경우다. 같은 사용자의 상승(elevated)·비상승 토큰은 SID가 같아 통과한다. unix에서 같은 euid의 모든 프로세스가 통과하는 것과 같다.
    - 공통 부분. 프레이밍과 wire(`qsh.local.v1`, `LOCAL_ADMIN`·`LOCAL_CONTROL`·`LOCAL_STREAM`)는 OS와 무관하게 바뀌지 않는다. localctl은 인가 계층이 아니고(데몬은 `Authorizer::check`를 conduit에 대해 부르지 않는다) 클라이언트가 보낸 principal 값을 믿지 않는다는 규칙도 그대로다. resume token은 어떤 localctl 프레임에도 실리지 않는다.
    - 모듈 구조. `localctl/`에서 플랫폼에 닿는 부분만 `cfg`로 가른다. `frame.rs`와 `client.rs`는 `AsyncRead + AsyncWrite` 스트림에 대해 일반화하고 연결·인스턴스 생성·자격 확인은 `localctl/transport/unix.rs`와 `localctl/transport/windows.rs`로 옮긴다. `frame.rs`·`client.rs`는 파일로 남아 `xtask arch`의 파일 단위 금지(`qsh_transport`·`quinn`·`rustls`)를 그대로 받는다. 새 transport 파일 둘도 같은 금지 목록에 올리고, `daemon.rs`는 지금처럼 면제다. `qsh-cli/src`의 금지는 UDS 토큰에 `named_pipe`와 `\\.\pipe`를 더한다. `localctl/mod.rs`의 `#[cfg(unix)]` 게이트와 `lib.rs`의 모듈 선언 주석은 걷어 낸다. 같은 이유로 `reverse/listen.rs`·`reverse/listen/hub.rs`·`registration.rs`의 `cfg(unix)`/`cfg(not(unix))` 쌍둥이를 없애고 `run_listen`의 `cfg` 분기도 지운다. `windows_unsupported()`는 `qsh serve --to`(host 쪽)만 부른다.
    - `qsh listen`의 나머지. 종료 신호는 Windows에서 `tokio::signal::ctrl_c`와 콘솔 닫힘 이벤트(결정 6의 핸들러 계열)다. config·정책 진단·감사·ACL 규율(`acl.toml` 1회 로드, default-deny, 감사 fail closed)은 unix와 같고 감사 로그는 결정 9의 디렉터리 DACL 아래에 쓴다. stateless reset key 파일(ADR-0036)도 결정 9 모듈로 만든다. 데몬은 방화벽 허용이 필요한 UDP 포트를 연다. `qsh doctor`의 `controller_unreachable` 문안이 그대로 쓰이고, Windows Defender 방화벽 안내는 README가 적는다.
    - 동작 요약. Windows에서 `qsh hosts`는 forward host와 데몬이 알리는 reverse 항목을 낸다(데몬이 없으면 forward만이고 오류가 아니다). `qsh tunnels`는 데몬 항목을 포함한다. `qsh tunnel close <id>`는 이 프로세스 밖의 터널을 데몬들에 묻는다. 위 변화를 `docs/CLI.md` §6.9·§6.13·§6.14의 Windows 문장에 반영한다.
15. `qsh tunnel open --supervise`는 Windows에서 그대로 열린다. forward route에서는 supervisor가 터널을 연 프로세스 안에 있다. reverse route의 `--remote`는 데몬의 reverse connection이 carrier이고 운영자 닫기를 `LocalHostList`·`LocalTunnelList`로 판별하는데(`docs/CLI.md` §6.14), 이 두 요청이 named pipe 위에서 같은 값을 돌려주므로 판별 규칙은 바뀌지 않는다. 데몬이 재시작하면 reverse 등록과 그 위의 터널이 모두 끝나는 점은 unix와 같다. 절전 감지는 wall clock과 monotonic clock을 비교하는데 Windows의 monotonic clock이 절전 중 멈추는지는 확인된 적이 없다(README Known limitations). 이 ADR은 그 확인을 계약으로 삼지 않는다. 멈추지 않는다면 절전 감지는 일반 dead-path 감지로 대신되고 `qsh.event/v1`의 `wake` 이벤트가 안 나올 뿐 터널 복구는 된다. 캠페인 문서(결정 18)에 Windows 절전 회차 한 줄을 더해 사람이 한 번 확인한다. 결과는 README 문장을 확정하는 데만 쓴다.

### E. 출고, CI, 문서

16. release 자산은 `qsh-<tag>-x86_64-pc-windows-msvc.zip`을 유지하고 구성(`qsh.exe` 하나, man 페이지 없음)과 `SHA256SUMS`·attestation 대상도 그대로다. 설치 스크립트(`install.sh`)는 Windows 경로를 갖지 않고 README가 zip 수동 설치를 적는 지금 형태를 유지한다. 코드 서명(Authenticode)은 이 마일스톤에 넣지 않는다. 자산은 서명되지 않으며 SmartScreen 경고가 뜰 수 있음을 `RELEASE-NOTES.md`와 README가 적는다. 아키텍처는 x86_64 하나다. `aarch64-pc-windows-msvc`는 열지 않는다.
17. CI의 `windows-latest` leg은 다음을 더한다.
    - 결정 9~10의 DACL 단언 테스트. 소유자 전용 DACL로 `identity/device.key`, `trust.toml`, `resume.json`을 만들고 `GetNamedSecurityInfoW`로 읽어 SE_DACL_PROTECTED, ACE 하나, 그 SID가 토큰 사용자, 접근 마스크가 `FILE_ALL_ACCESS`임을 단언한다. 적용 실패를 주입한 변형에서는 대상 파일이 만들어지지 않음을 단언한다.
    - 결정 14의 named pipe 테스트. (1) 같은 이름의 pipe를 먼저 만들어 둔 상태에서 데몬 기동이 QUIC listener를 열기 전에 실패한다. (2) 만들어진 pipe 인스턴스의 보안 설명자를 읽어 SE_DACL_PROTECTED, 소유자 SID의 ACE 하나, Everyone·익명 ACE 없음을 단언하고, `PIPE_REJECT_REMOTE_CLIENTS`가 켜졌는지는 생성 옵션을 담은 순수 함수의 단위 테스트로 고정한다. (3) 자격 확인은 "프로세스 ID에서 사용자 SID를 얻는 함수"를 주입할 수 있게 쪼개서, 서버가 다른 SID의 클라이언트를 프레임을 읽기 전에 끊고 클라이언트가 다른 SID의 서버에 아무것도 쓰지 않음을 단언한다. 진짜 다른 사용자 계정은 CI 러너에서 만들 수 없으므로 주입 범위까지만 CI가 보고, 실제 두 번째 계정의 접속 거부는 캠페인 회차(결정 18)가 맡는다. (4) pipe 이름 규칙: 사용자 SID나 state dir이 다르면 이름이 다르고 같으면 같다. (5) `candidate_sockets`에 대응하는 열거가 접두에 맞는 이름만 고른다. (6) `frame.rs`·`client.rs` 테스트는 스트림 일반화 뒤에도 unix와 Windows 양쪽에서 같은 케이스로 돈다.
    - 역방향 경로의 기능 테스트. Windows 러너에는 host가 없으므로 종단은 Windows의 `qsh listen`(데몬 프로세스)에 target 쪽 상대를 붙여 본다. 이 상대를 CLI의 `qsh serve --to`로 하지는 않는다(결정 2). `qsh-core`의 target 경로(`reverse/target`)가 이미 테스트 빌드에서 Windows에 컴파일되므로, 테스트 하니스가 그 라이브러리 경로를 같은 러너에서 in-process로 띄워 데몬에 등록하게 한다. 이 상대는 결정 2의 인바운드 `qsh serve`가 `release_smoke`의 상대일 뿐인 것과 같은 논리의 test-only 상대이고 지원 범위가 아니다. PTY가 없으므로 이 상대로 볼 수 있는 것은 `exec`, `-L` 터널의 TCP echo 왕복, `qsh cp` 왕복(`qsh cp`가 착지한 뒤), `qsh hosts`의 reverse 항목, 데몬을 죽인 뒤 `qsh hosts`가 reverse 항목을 못 내고 forward만 냄, 새 데몬이 서면 target이 재등록하는 것이다. PTY attach와 resume은 사람 캠페인 몫이다. 상대 쪽 파일 op이 Windows에서 돌지 않으면(host 쪽 파일 처리가 unix 전용이면) `qsh cp` 왕복은 이 leg에서 빼고 캠페인에 올린다. 이 판단은 첫 스텝에서 하고, 하니스를 만들 수 없으면 이 항목 전체를 캠페인으로 옮기고 ADR을 개정한다.
    - 결정 4~8의 콘솔 계층 테스트. 테스트 바이너리가 ConPTY(`portable-pty`의 Windows 백엔드)를 열고 그 안에서 콘솔 probe(`qsh-testkit`의 작은 실행 파일)를 띄운다. probe는 raw 모드 진입 후 입력 바이트가 가공 없이 읽히는지, ConPTY 크기를 바꾸면 폴링이 한 번만 `resize` 콜백을 부르는지, 정상·강제 종료 뒤 콘솔 모드가 원래 값으로 돌아오는지를 stdout으로 보고한다. 모드 비트 계산(원래 모드에서 raw 모드를 만드는 순수 함수)은 단위 테스트가 따로 고정한다.
    - `release_smoke`의 `cfg(not(unix))` 쌍둥이를 넓힌다. 기존 `init` → `trust` → `exec --json`에 `doctor --json`과 `tunnel open --local`의 TCP echo 왕복을 더한다. 상대는 같은 바이너리의 인바운드 `qsh serve`다(결정 2). PTY·detach·attach 축은 Windows에 host가 없어 뺀다. 역방향 축은 바로 위 항목의 하니스가 맡고 `release_smoke`는 넓히지 않는다. 이 쌍둥이가 만든 파일에도 결정 9의 DACL 단언을 건다.
    - clippy는 이미 Windows를 돈다. `cargo xtask arch`의 의존 방향 규칙은 바뀌지 않는다(`windows-sys`는 `qsh-core`와 `qsh-cli`가 `cfg(windows)`로만 의존한다).
18. 사람 캠페인 문서 `docs/campaigns/p1-windows-client.md`를 M19 구현 마지막 스텝 전에 사전 고정해 커밋한다. 회차는 Windows Terminal과 conhost 각각에서 Linux host와 macOS host로 붙어 (1) bash/zsh 입력과 한글·이모지 출력, (2) vim 전체 화면과 종료 뒤 화면 복원, (3) 창 크기 변경 전파, (4) `~d` detach 뒤 `qsh attach` resume, (5) 콘솔 창 닫기 뒤 세션 생존과 터미널 모드 복원, (6) `Ctrl-C` 전달, (7) 결정 15의 절전 회차를 본다. 역방향 회차를 더한다. Windows 장비에서 `qsh listen`을 띄우고 Linux와 macOS의 `qsh serve --to`가 등록한 뒤 (8) `qsh <name>` attach의 입력·vim·resize, (9) `qsh exec`, (10) `-L`/`-R` 터널과 `qsh cp` 왕복, (11) 콘솔 창 닫기나 데몬 재시작 뒤 `qsh hosts`의 reverse 항목 소실과 target 재등록, 재등록 뒤 detach했던 세션의 `qsh attach` resume, (12) 같은 장비에 둘째 Windows 사용자 계정을 만들어 그 계정의 `qsh`가 첫 사용자의 pipe에 붙지 못하고 pipe 이름 선점 시도가 기동 실패로 끝남, (13) `qsh pair ssh --reverse`로 세운 pin이 위 (8)~(11)에 그대로 쓰임을 본다. 합격 기준은 캠페인 문서가 정한다. 이 회차는 마일스톤을 막지 않고 P1 완료 선언을 막는다(`docs/ROADMAP.md` §5.5).
19. 문서 개정은 `docs/design/threat-model.md` §3에 진입점 행 둘을 더한다. 하나는 "Windows 콘솔 입력"(로컬 사용자, VT 입력 바이트는 키 해석 없이 원격으로 가며 해석하는 쪽은 원격 PTY)이고, 다른 하나는 기존 "localctl UDS" 행 옆의 "localctl named pipe"(same-SID 로컬, `qsh-<scope>-<pid>`, 소유자 전용 보호 DACL, `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, 양방향 SID 대조)다. §4에는 위협을 더한다. B(무단접근)에 다른 로컬 사용자의 pipe 접속, A(스푸핑)에 pipe 이름 선점과 가짜 데몬(클라이언트 토큰 가장 포함)을 올리고 통제를 결정 14로, 핀 테스트를 결정 17의 named pipe 테스트로 적는다. D(정보노출)에는 DACL 통제와 결정 17의 핀 테스트를 올린다. 잔여 위험(§7)에는 프로세스 ID 재사용 틈과 같은 사용자의 모든 프로세스가 통과한다는 점(unix와 같다)을 적는다. `docs/design/architecture.md`는 §1의 localctl 줄(pure UDS를 pure 로컬 스트림으로), §7의 Windows 경로 줄과 runtime dir·pipe 이름 줄, §8의 `windows-sys` 행과 keystore 행의 Windows 항목을 고친다. `docs/CLI.md`는 §6.9·§6.11·§6.12·§6.13·§6.14·§6.20의 Windows 관련 문장과 §7에 새로 더할 Windows 지원 범위 문장을 고친다. §6.13의 "Windows에서는 `qsh listen`/`qsh serve --to` 둘 다 `UNSUPPORTED`" 문단은 `qsh serve --to`만 남도록 고치고 `qsh listen`의 Windows 방화벽·foreground 한계를 더한다. 코드 쪽으로는 `xtask/src/arch.rs`의 localctl 상수와 사유 문구(결정 14), README Known limitations, `docs/ROADMAP.md` §3 Windows 행, `crates/qsh-core/src/resume.rs` 모듈 doc의 "inherited directory ACL" 문단, `crates/qsh-core/src/localctl/mod.rs` 모듈 doc의 `cfg(unix)` 문단을 새 범위에 맞춘다.

## 근거

선은 연결 방향이 아니라 역할로 긋는다. `docs/PRD.md` §4(2026-10-13)는 정방향 route에서 되는 기능이 역방향 route에서도 되어야 하고 한쪽만 지원하는 설계는 이유를 ADR에 적어 승인받으라고 한다. 이 ADR이 Windows에서 여는 것은 client 쪽 역할이다. 정방향에서는 `qsh <name>`·`exec`·`attach`·`tunnel`, 역방향에서는 같은 명령들이 데몬을 거쳐 reverse route로 나가는 것과 그 데몬인 `qsh listen`이다. 닫는 것은 host 쪽 역할이다. 정방향의 `qsh serve`와 역방향의 `qsh serve --to`가 모두 P2에 남는다. 방향마다 같은 선이므로 "Windows에서는 정방향만 된다"가 아니라 "Windows에서는 client 역할만 된다"가 되고, 그래서 한쪽 방향만 지원하는 설계가 아니며 PRD §4와 어긋나지 않는다. `pair invite`와 `setup host`는 상환 창구를 여는 host 쪽 명령이라 그대로 닫힌다. `pair ssh`는 어느 쪽이 pin을 세우는 client인지에 따라 정방향과 `--reverse`를 모두 연다(ADR-0044 결정 22). 응답자가 Windows이면 거부하는 것은 host 쪽이라서다.

가치 대부분이 대화형 attach에 있고 그 비용도 거기에 있어서 정방향의 중심은 거기까지다. 나머지 정방향 명령은 이미 돌고 모자란 것은 기밀성(DACL)과 콘솔(raw 모드, resize)이다. 역방향을 열면 비용이 하나 더 든다. controller가 되려면 CLI 프로세스와 데몬 사이의 IPC가 있어야 하고, 그 IPC는 같은 사용자만 붙는다는 unix의 신뢰 모델(0700 디렉터리, 0600 소켓, `peer_cred` 대조)을 Windows 수단으로 다시 세워야 한다. 초안은 생산자(`qsh listen`)가 없다는 이유로 소비자(`hosts`·reverse 경로)만 여는 IPC를 기각했지만, 원칙 7이 생산자를 열라고 하므로 이유가 사라졌다.

named pipe를 고르는 이유는 같은 사용자 한정을 OS가 강제하는 수단 중 가장 직접적이라서다. pipe는 DACL로 소유자만 접속하게 만들 수 있고, 원격 접속 거부 플래그가 있으며, 서버와 클라이언트가 서로의 프로세스 토큰을 조회할 수 있다. unix에서 파일 모드와 `SO_PEERCRED`가 맡은 두 겹(접근 권한과 자격 확인)을 DACL과 SID 대조가 그대로 맡는다. pipe 이름 공간은 장비 전체에서 공유되는 전역 공간이라 UDS 경로(사용자 디렉터리 안)에는 없는 위험, 곧 다른 사용자가 이름을 먼저 차지하는 선점이 생긴다. `FILE_FLAG_FIRST_PIPE_INSTANCE`와 클라이언트 쪽 서버 SID 확인이 그 위험을 막는 장치이고, 이름에 사용자 SID를 섞는 것은 정상 상태에서 서로의 이름을 건드리지 않게 하는 보조다. 보안 경계는 이름이 아니라 DACL과 SID 대조다.

`qsh service`는 같은 원칙 아래에서도 연다고 약속하지 않는다. 원칙 7은 방향 간 동등이고 플랫폼 간 동등이 아니다. Windows에서 listener 데몬을 로그온과 무관하게 띄우는 일은 서비스 매니저 백엔드라는 별개의 설계이고(ADR-0032), 그것이 없어도 `qsh listen`을 사람이 띄우면 역방향의 client 쪽은 기능으로서 갖춰진다. `docs/ROADMAP.md` §5.4 위험 5가 말한 "좁힌다"는 이제 host 역할과 서비스 매니저를 빼는 것이다.

crossterm을 쓰지 않는 이유는 architecture §8이 이미 댔다. 이벤트 루프와 키 파서는 raw byte 전달과 충돌한다. Win32 콘솔 API는 VT 입력 모드(`ENABLE_VIRTUAL_TERMINAL_INPUT`) 덕에 입력을 이미 xterm 바이트열로 준다. unix의 termios raw 모드와 같은 일을 하는 모드 비트 몇 개가 전부다. 원격 PTY가 해석한다는 점도 같아서 escape 처리 코드를 공유할 수 있다.

resize를 폴링으로 하는 이유는 입력 읽기와 충돌하지 않는 방법이 이것뿐이어서다. 이벤트를 받으려면 `ReadConsoleInput`으로 입력을 레코드 단위로 읽어야 하는데, 그러면 VT 모드가 만든 바이트를 레코드의 문자로 다시 조립하게 되어 "바이트를 그대로"라는 규율이 깨진다. 200 ms는 사람이 창을 끄는 속도에서 체감 지연이 없고 비용은 값이 안 바뀐 동안 시스템 호출 하나다.

DACL을 만드는 순간에 거는 이유는 임시 파일이 rename 전에 상속 ACL로 읽힐 수 있어서다. resume token은 연결이 죽은 뒤에도 사는 유일한 자격이므로(ADR-0007) 이 구간이 곧 노출이다. 소유자 SID 하나만 두는 것은 unix 0600과 대응한다. 관리자는 소유권을 가져올 수 있으므로 같은 사용자의 다른 프로세스와 다른 사용자를 막는 모델이라는 점이 unix 0600과 같다.

초대 코드 에코를 열지 않는 이유는 검증 가능성이다. 모드 비트는 쉽지만 "에코가 꺼졌다"를 단언하는 CI 수단이 없다. 이 프로젝트는 비밀이 스크롤백에 남는 경로를 테스트 없이 열지 않는다(`NO_TERMINAL_ECHO_SUPPRESSION`의 기존 판단). 인자와 파이프 입력이 열려 있어 Windows 사용자는 pairing을 막히지 않는다.

Credential Manager를 붙이는 것은 다른 OS와 같은 기본값(`auto` = platform 우선)을 주기 위해서고, 붙이지 못해도 파일 모드가 DACL로 보호되므로 최악의 경우에도 기밀성은 같다. 그래서 결정 12는 접을 수 있게 써 두었다.

## 대안과 기각 사유

- **Windows host(ConPTY 백엔드)를 함께 연다.** 기각한다. PRD §7이 P2로 두었고 PTY 코드 전체가 `cfg(unix)`다. 이 ADR의 범위가 아니고, 열면 Windows 러너에서 대화형 attach를 자체 종단 테스트할 수 있다는 이점이 있다. 그 이점은 P2 ADR에서 얻는다. 정방향 `qsh serve`와 역방향 `qsh serve --to`가 같이 P2에 남으므로 방향 간 동등은 유지된다.
- **crossterm으로 콘솔을 다룬다.** 기각한다. architecture §8의 이유와 Windows API 표면을 키 이벤트 계층까지 끌어오는 비용 때문이다.
- **named pipe로 localctl을 Windows에 연다.** 채택한다(결정 14). 초안은 생산자(`qsh listen`)가 없다는 이유로 기각했으나 2026-10-13 결정으로 `qsh listen`이 열려 생산자가 생겼다.
- **Windows에서 역방향을 닫는다(초안).** 기각한다. `docs/PRD.md` §4가 정방향과 역방향의 동등을 요구하고, client 쪽 역할은 방향과 무관하게 같은 선으로 열린다. 이 대안은 열린 정방향 명령과 `pair ssh --reverse`가 가리키는 reverse route가 Windows에서만 막히게 만든다.
- **TCP loopback으로 localctl을 연다.** 기각한다. 127.0.0.1의 포트는 같은 장비의 모든 로컬 사용자가 접속할 수 있고, 접속한 쪽의 사용자를 확인할 수단이 소켓에 없다. 포트를 파일로 광고하고 토큰을 요구하는 방식은 그 토큰의 파일 권한 모델을 다시 만드는 일이며, 선점(다른 사용자가 먼저 같은 포트에 bind)도 막지 못한다. unix `peer_cred`와 대응하는 자격 확인이 없다는 것이 결정적이다.
- **Windows의 AF_UNIX 소켓을 쓴다.** 기각한다. Windows 10 1803 이후 `AF_UNIX`가 있지만, 최소 지원 버전(1809)에서 `SO_PEERCRED`에 해당하는 peer 프로세스 조회가 확실하지 않다(더 새 빌드에서 생긴 것으로 알고 있으나 확인하지 못했다). 소켓 파일의 접근 통제도 NTFS ACL에 기대서 결정 9처럼 우리가 걸어야 하므로 pipe보다 얻는 것이 없다. tokio는 Windows에서 named pipe를 지원하지만 UDS는 지원하지 않는다.
- **서비스 매니저 통합(`qsh service`)을 Windows에 함께 연다.** 이번에는 기각한다(결정 2). 서비스 모델이 다르고 listener 데몬의 상시 가동은 사람이 띄우는 foreground 프로세스로 대체된다. 요구가 관측되면 ADR-0032 계열 후속 결정으로 연다.
- **역방향 종단 테스트를 위해 CLI의 `qsh serve --to`를 Windows에서 연다.** 기각한다. 같은 이름의 명령이 한 장비에서는 지원 약속이고 다른 곳에서는 test-only가 되고, host 역할이 사실상 열린 것으로 읽힌다. 테스트 상대는 하니스 안에서만 연다(결정 17).
- **`WINDOW_BUFFER_SIZE_EVENT`로 resize를 받는다.** 기각한다. 입력을 레코드로 읽게 되어 바이트 그대로 전달 규율이 깨진다.
- **`icacls`나 PowerShell로 ACL을 설정한다.** 기각한다. 생성과 설정 사이에 노출 구간이 생기고 외부 프로세스·로캘 의존이 들어온다.
- **상속 ACL을 그대로 둔다.** 기각한다. 사용자 프로필 아래 상속은 대개 소유자·SYSTEM·Administrators라서 일견 안전해 보이지만 프로필 디렉터리나 `QSH_STATE_DIR`를 다른 곳으로 둔 경우 보장이 없고, 보장이 환경에 달린 기밀성은 테스트로 고정할 수 없다. ROADMAP DoD도 소유자 전용을 요구한다.
- **`%APPDATA%`/`%LOCALAPPDATA%`에 둔다.** 기각한다. ssh 스타일 예측 가능성(`.config/qsh`)을 세 OS에서 맞추는 쪽이 문서와 지원 비용이 낮고, OpenSSH for Windows도 `%USERPROFILE%\.ssh`를 쓴다. `%APPDATA%`는 로밍 프로필로 복제될 수 있어 키 파일에는 오히려 나쁘다. 사용자가 원하면 `QSH_CONFIG_DIR`로 옮길 수 있다.
- **초대 코드 콘솔 프롬프트를 지금 연다.** 기각한다(근거 절). ConPTY 기반 에코 검증 테스트가 서면 후속 ADR 없이 `NO_TERMINAL_ECHO_SUPPRESSION`의 조건만 바꾸는 작은 변경으로 열 수 있다.
- **Windows 러너 안에서 대화형 attach를 종단 테스트한다.** 현재는 기각한다. 상대가 될 host가 Windows에 없고, GHA 러너끼리는 UDP 경로가 없다. 콘솔 계층은 ConPTY probe로, 종단은 사람 캠페인으로 나눠 고정한다. WSL 배포판을 러너에 띄우는 방법은 러너 이미지 의존이 커서 여기서는 채택하지 않는다.
- **Authenticode 서명과 winget·scoop·MSI를 이번에 넣는다.** 기각한다. 서명 인증서 발급·보관 절차(`docs/deploy/release-secrets.md`)가 먼저 필요하고 Windows 자산이 한 번도 사람 확인을 받지 않았다. 캠페인 합격 뒤에 별도 항목으로 연다.
- **doctor에 Windows 파일 ACL 점검 finding을 더한다.** 이번에는 넣지 않는다. 읽을 때 검사하지 않는 unix와 같은 규율을 유지하고 `EXPECTED_DOCTOR_CODES`를 늘리지 않는다. 옛 빌드의 느슨한 파일은 다음 쓰기에서 고쳐진다(결정 10). 요구가 관측되면 additive finding으로 연다.

## 결과

- 고정할 테스트(이름은 구현 시 확정, 위치만 정한다).
  - `crates/qsh-cli/tests/exit_code_matrix.rs`의 `cfg(windows)` 행: 결정 2의 각 명령이 `UNSUPPORTED`/exit `255`이고 리소스를 만들지 않음. 터미널 초대 코드 프롬프트와 콘솔 stdin의 `--code-stdin`이 `UNSUPPORTED`, 파이프 입력은 성공.
  - `qsh-core`의 Windows DACL 테스트(결정 9~10): 보호·단일 ACE·소유자 SID·접근 마스크, 적용 실패 주입 시 파일 부재, 옛 상속 ACL 파일이 다음 쓰기에서 교체됨.
  - `qsh-cli`의 콘솔 모드 계산 단위 테스트와 `qsh-testkit` ConPTY probe 테스트(결정 17): raw 입력 무가공, resize 폴링 한 번, 모드 복원, 비 콘솔 stdin의 verbatim 경로, VT를 켤 수 없을 때 `session.open` 이전 `UNSUPPORTED`.
  - 결정 14의 named pipe 테스트: 이름 선점 시 기동 실패, 보호 DACL·단일 ACE 단언, 주입한 SID 불일치 거부(서버·클라이언트 양쪽), 이름 규칙과 열거, `frame.rs`·`client.rs` 공통 케이스가 두 OS에서 도는 것.
  - 역방향 경로 기능 테스트(결정 17): Windows의 `qsh listen`에 test-only target 상대를 붙여 `exec`, `-L` 터널 echo, `qsh hosts`의 reverse 항목, 데몬 재시작 뒤 재등록, `qsh cp` 왕복(착지 뒤). 하니스를 만들 수 없으면 캠페인으로 옮긴다.
  - `exit_code_matrix.rs`의 `cfg(windows)` 행에 `qsh serve --to`·`qsh service`·`qsh setup host`·`qsh pair invite`가 들고, 데몬이 없을 때 `qsh hosts`가 forward만 낸다는 동작을 고정한다.
  - `release_smoke`의 `cfg(not(unix))` 쌍둥이 확장(결정 17).
  - unix 회귀: 터미널 trait 추출(결정 4) 뒤에도 `tui_expect`와 기존 attach 테스트가 그대로 초록이어야 한다.
- `qsh.cli/v1`, `qsh.event/v1`, wire 프로토콜, `ErrorCode`, capability 문자열, `EXPECTED_DOCTOR_CODES`는 바뀌지 않는다. 새 fixture도 없다(fixture는 OS 공통이고 Windows 행은 위 매트릭스 테스트가 맡는다). doctor는 Windows에서 service 유닛과 host 역할에 기대는 finding(`service_not_registered` 등)을 내지 않고, listener 쪽 finding(`controller_unreachable` 등)은 다른 OS와 같이 낸다. 어휘는 늘리지 않는다. 이 부분이 현재 코드와 어긋나면 첫 스텝에서 드러나므로 그때 이 ADR을 개정한다.
- 의존 추가: `windows-sys`(`qsh-core`, `qsh-cli`의 `cfg(windows)`), Windows keystore store crate 하나(결정 12), 개발 의존으로 `portable-pty`(`qsh-testkit`, Windows; 워크스페이스 의존으로는 이미 있고 `qsh-core`에서 unix 전용으로 쓴다). `deny.toml` 통과가 조건이다. `cargo xtask arch`의 의존 방향 행렬은 바뀌지 않는다. 다만 localctl 구조가 바뀐다(결정 14). `frame.rs`·`client.rs`는 파일로 남아 지금의 금지를 그대로 받고, 새 `localctl/transport/{unix,windows}.rs`는 금지 목록에 더해야 하며, `qsh-cli/src` 금지의 토큰에 `named_pipe`를 더해야 한다. 어느 쪽이든 파일이 디렉터리로 바뀌거나 그 반대가 되는 이동이 있으면 `xtask/src/arch.rs`를 같은 커밋에서 고친다(`CLAUDE.md`의 path-scoped 금지 규칙). 의존으로는 `windows-sys`의 보안·pipe 관련 feature가 늘고 tokio의 `net` feature(이미 켜짐)가 named pipe를 맡는다.
- 문서 개정은 결정 19의 목록이 전부다. 새 `docs/campaigns/p1-windows-client.md`가 생긴다. `docs/man/`은 clap 트리가 안 바뀌므로 변하지 않는다.
- 크기: `docs/ROADMAP.md` M19의 4.7~7.0ew를 5.7~9.5ew로 다시 매긴다(초안은 4.3~6.9ew, 2026-10-13 역방향 범위가 +1.4~2.6ew). 구성은 ADR 0.3 / 콘솔 모듈 1.0~1.6 / 터미널 trait 추출 0.5~0.8 / DACL 모듈과 fail closed 0.8~1.3 / keystore 0.2~0.5 / ConPTY probe를 포함한 테스트 0.8~1.2 / CI·release smoke 0.3~0.5 / 문서·threat model·캠페인 사전 고정 0.3~0.5 / 마감 0.1~0.2에, 역방향 범위로 다음을 더한다. (a) `cfg(unix)` 게이트 걷어내기 0.3~0.5: `localctl` 모듈 선언, `run_listen`의 분기, reverse hub·conn table·등록의 쌍둥이 메서드와 그 위 import 정리, Windows clippy `-D warnings`를 통과시키는 일. (b) localctl transport 분리 0.2~0.4: `frame.rs`·`client.rs`의 스트림 일반화, unix 코드 이동, `arch.rs` 갱신. 동작이 바뀌지 않는 이동이라 unix 회귀 테스트가 안전망이다. (c) named pipe 서버·클라이언트와 이름 규칙·열거 0.3~0.5. (d) pipe DACL(결정 9 모듈의 확장)과 양방향 SID 확인, 선점 거부 0.2~0.4. DACL 모듈 자체는 위 0.8~1.3에 있고 여기는 pipe 변형과 프로세스 토큰 조회만이다. (e) pipe·역방향 경로 테스트와 test-only target 하니스 0.3~0.6.
