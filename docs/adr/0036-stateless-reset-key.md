# ADR-0036: stateless reset key는 config 디렉터리의 0600 파일 `stateless_reset.key`에 두고, 읽을 수 없거나 형식이 틀리면 파일을 건드리지 않은 채 이번 기동만 임시 키로 뜬다

날짜: 2026-10-01
상태: 승인됨 (2026-10-01 사용자 확정)

개정 관계: 새 ADR이다. 다른 ADR을 개정하지 않는다. 비밀을 디스크에 두는 규율은 ADR-0007(resume token custody)의 결을 따르고, 읽기 실패에도 프로세스가 뜨는 모양은 `docs/CLI.md` §6.12의 `acl.toml` 기동 계약과 같은 쪽을 고른다. 이 번호는 P1 예약(0027~0035) 밖의 첫 새 번호다.

## 맥락

`docs/design/reexec-estimate.md` §3의 H1b 행은 stateless reset key를 고정하자는 후보다. 오늘 서버 endpoint는 quinn의 `EndpointConfig::default()`로 만들어지고, 그 기본값은 프로세스가 뜰 때마다 새 HMAC 키를 뽑는다. 그래서 `qsh serve`가 재시작하면 새 프로세스는 옛 연결의 connection ID에 맞는 stateless reset token을 계산하지 못한다. RFC 9000 §10.3의 stateless reset이 성립하지 않으니, attach 중이던 클라이언트는 path watch가 사망을 선언하거나 `max_idle_timeout` 45초가 끝날 때까지 끊긴 줄 모른다(`docs/design/protocol.md` §10 "Path 사망 감지"). 키를 재시작 너머로 유지하면 재시작 뒤 첫 패킷이 reset을 받아 1 RTT 안에 단절이 드러난다. 같은 행의 "잃는 것" 칸이 적듯 세션은 여전히 죽는다. H1b가 바꾸는 것은 감지 지연이다.

같은 행은 비용 칸에 "키 보관 위치 결정 1건"을 남겼고, `docs/ROADMAP.md` M13 범위 (f)와 DoD (f)가 그 결정의 테두리를 정했다. reset key 파일은 0600이다. 읽을 수 없거나 형식이 틀린 파일을 만나면 조용히 새 키를 만들지 않는다. 그다음을 기동 거절(`CONFIG_ERROR`)로 할지 이번 기동만 쓰는 임시 키와 기동 진단으로 할지는 골라서 적어야 한다. 키는 로그와 audit 어디에도 나오지 않는다. wire diff는 0이다.

설계를 가르는 사실은 이렇다.

- quinn-proto 0.11의 `EndpointConfig::new(reset_key)`와 `EndpointConfig::reset_key`가 HMAC 키를 주입받는다. 키를 바꾸는 데 wire 변경이 없고 `qsh-proto`의 `.proto`도 건드리지 않는다.
- reset key가 새면 공격자는 관측한 connection ID마다 유효한 reset token을 만들 수 있다. 그러면 경로 위에 있지 않아도 그 서버의 연결을 끊을 수 있다. 세션 내용을 읽거나 인증을 우회하는 비밀은 아니지만 가용성을 쥔 비밀이다.
- 이 키가 없어도 qsh는 오늘처럼 동작한다. 감지가 path watch나 idle timeout으로 늦어질 뿐이다. 키는 감지 지연을 줄이는 최적화이지 정확성의 전제가 아니다.
- `acl.toml`이 없거나 파싱에 실패해도 `qsh serve`/`qsh listen`은 뜨고 bind한 뒤 모든 요청을 거부하고 원인은 stderr 기동 진단으로 한 번 알린다(`docs/CLI.md` §6.12·§6.13). 운영자가 유닛 로그에서 원인을 읽을 수 있는 상태로 떠 있는 것을 재시작 루프보다 낫다고 본 계약이다.
- `docs/deploy/service.md`의 유닛 예시는 재시작 정책을 켠다. 기동이 결정적으로 실패하면 유닛은 같은 실패를 되풀이한다.
- `identity/`를 치우고 `qsh init`을 다시 돌리는 것이 identity 교체의 공식 경로다(`docs/CLI.md` §6.11). 그 경로가 reset key까지 지울 까닭은 없다.
- 플랫폼 키스토어 로드는 blocking이고 재시작 뒤 서비스 복귀 시간에 그대로 더해진다(`docs/design/reexec-estimate.md` §1).

## 결정

1. 키를 쓰는 프로세스는 서버 endpoint를 여는 `qsh serve`와 `qsh listen`이다. 클라이언트와 `qsh serve --to` target은 쓰지 않는다. stateless reset은 재시작한 쪽이 옛 연결의 패킷을 받을 때만 쓸모가 있고 그런 쪽은 서버 endpoint뿐이다. 같은 config 디렉터리를 쓰는 두 프로세스는 같은 키를 나눠 쓴다. 두 프로세스는 서로 다른 포트에 bind하므로 한쪽이 만든 token이 다른 쪽 연결에 닿지 않는다.

2. 키는 32바이트 OS 난수이고 config 디렉터리 바로 아래 `stateless_reset.key`에 원시 바이트로 둔다. `identity/` 아래에 두지 않는다. identity 교체 경로가 이 키를 같이 지울 이유가 없고 반대로 이 키를 지우는 일이 identity를 건드려서도 안 된다. 플랫폼 키스토어는 쓰지 않는다.

3. 파일이 없으면 첫 기동이 만든다. unix에서 모드는 0600이다. 같은 디렉터리의 임시 파일에 쓰고 fsync한 뒤, 대상 이름이 이미 있으면 실패하는 방식(`link(2)`)으로 제자리에 올린다. 두 프로세스가 동시에 처음 뜨면 한쪽만 이기고 진 쪽은 이긴 쪽 파일을 읽는다. 읽는 쪽이 반쯤 쓰인 파일을 보는 일은 없다.

4. 파일이 있고 unix에서 권한이 0600보다 넓으면 키를 그대로 쓰되 stderr 기동 진단 한 줄을 낸다. 진단에는 경로와 관측한 모드만 담는다.

5. 파일을 읽을 수 없거나(권한 거부, I/O 오류 등 없음 이외의 모든 오류) 길이가 32바이트가 아니면 그 파일을 덮어쓰거나 지우거나 새로 만들지 않는다. 대신 이번 기동에만 쓰는 임시 키를 메모리에서 뽑아 뜨고 stderr 기동 진단 한 줄을 낸다. 진단에는 경로, 오류 종류, "재시작 뒤 단절 감지가 idle timeout으로 늦어진다"는 결과, 파일을 고치거나 지우면 다음 기동이 정상 경로로 돌아온다는 remedy를 담는다. 문면 상수는 `qsh-core`에 두고 CLI는 그대로 출력만 한다(`docs/CLI.md` §6.12 기동 진단과 같은 조립 방식).

6. reset key 바이트는 로그, audit, 기동 진단, doctor finding의 `detail`, JSON 출력 어디에도 나오지 않는다. 메모리에서는 `Zeroizing` 버퍼에 두고 `qsh-core`가 읽어 `qsh-transport`의 서버 endpoint 생성 함수에 인자로 넘긴다. `qsh-transport`는 파일 경로를 모른다.

7. 회전 명령은 두지 않는다. 파일을 지우고 재시작하면 새 키가 만들어진다. 그 재시작 한 번은 옛 키를 모르므로 attach 중이던 클라이언트의 감지가 오늘처럼 늦는다. 유출이 의심될 때도 이 절차를 따른다.

## 근거

이 키는 최적화이므로 읽기 실패에서 기동을 거절하지 않는다. 키를 잃은 서버는 오늘의 서버와 같게 동작한다. 감지가 늦을 뿐 인가, 세션, 터널의 정확성은 그대로다. 반면 기동 거절은 서버를 통째로 내린다. 재시작 정책이 걸린 유닛에서는 같은 실패가 되풀이되고 그동안 새 연결도 받지 못한다. 최적화 하나의 실패가 서비스 전체의 가용성을 가져가는 것은 균형이 맞지 않는다. `acl.toml` 기동 계약도 같은 판단 위에 서 있다. 정책이 망가져도 프로세스는 떠서 원인을 알리고 거부는 요청 단위에서 한다.

그렇다고 조용히 새 키를 만들어 파일에 쓰는 것은 막는다. 읽지 못한 파일을 덮어쓰면 운영자가 권한이나 디스크 문제를 볼 기회가 사라지고 재시작 감지가 왜 느려졌는지 설명할 흔적도 남지 않는다. 임시 키는 메모리에만 있고 파일은 그대로다. 그래서 진단을 본 운영자가 원인을 고치면 다음 기동이 원래 키로 돌아온다. 파일이 깨진 채 남아 있는 동안에는 기동마다 임시 키가 새로 뽑히고 그 기간의 재시작 감지는 H1b 이전과 같다. 그 이상 나빠지지는 않는다.

권한이 넓은 파일을 거절하지 않고 쓰는 이유도 같다. 키가 이미 다른 uid에게 읽혔을 수 있다는 사실은 거절한다고 되돌려지지 않는다. 운영자에게 알리는 일이 필요하고 조치(권한을 좁히거나 파일을 지우고 재시작)는 운영자가 고른다.

플랫폼 키스토어는 비용과 가치의 비례를 따져 쓰지 않는다. 키스토어 로드는 재시작마다 blocking 시간을 더하는데, 재시작 직후의 복귀 시간을 줄이자는 것이 H1b의 목적이다. 이 키가 지키는 것도 가용성 하나라서 device 키만큼의 보관 비용을 들일 대상이 아니다. 0600 파일은 ADR-0007이 resume token에 쓴 수준과 같다.

## 대안

- 읽기 실패에서 기동을 `CONFIG_ERROR`로 거절한다. 기각한다. 근거 절의 이유 그대로다. 최적화의 실패가 서비스 전체를 내리고, 재시작 정책이 걸린 유닛은 같은 실패를 되풀이한다. 파일이 틀렸다는 사실을 운영자가 가장 확실히 알게 된다는 장점은 있지만 그 목적은 기동 진단으로도 이룬다.
- 읽기 실패에서 새 키를 만들어 파일을 덮어쓴다. 기각한다. `docs/ROADMAP.md` DoD (f)가 명시적으로 막은 동작이고 권한이나 디스크 문제의 흔적을 지운다.
- device identity 키에서 HKDF로 reset key를 파생한다. 새 파일도 새 읽기 실패 경로도 생기지 않는다는 장점이 크다. identity를 읽지 못하면 서버는 어차피 뜨지 못하므로 이 ADR이 다루는 실패 모드가 사라진다. 그래도 이번 결정으로 고르지 않는다. reset key를 갈려면 identity를 갈아야 하고 그러면 모든 peer가 다시 pin해야 한다. device 키 바이트를 TLS 인증 밖의 용도에 입력으로 쓰는 첫 사례가 되어 그 규율을 따로 세워야 한다. `docs/ROADMAP.md` DoD (f)의 문면도 키 파일을 전제한다. 사용자가 이 안을 고르면 결정 2~5가 파생 한 줄로 바뀌고 ROADMAP DoD (f)의 파일 문장을 개정해야 한다.
- `identity/` 아래에 둔다. 기각한다. `identity/`를 치우는 교체 경로(`docs/CLI.md` §6.11)가 이 키까지 지우게 되고 두 수명이 이유 없이 묶인다.
- 플랫폼 키스토어에 둔다. 기각한다. 근거 절의 이유 그대로다.
- 권한이 0600보다 넓으면 키를 버리고 임시 키로 뜬다. 채택하지 않는다. 이미 넓게 열려 있던 키를 버린다고 유출이 되돌려지지 않고 운영자가 권한만 좁히면 계속 쓸 수 있는 키를 매 기동 버리게 된다. 진단으로 알리는 쪽이 조치의 선택을 운영자에게 남긴다.
- `qsh serve --to` target과 클라이언트도 키를 고정한다. 기각한다. 결정 1의 이유 그대로다. 그쪽은 재시작해도 옛 연결의 패킷을 서버로서 받지 않으므로 고정해서 얻는 것이 없고 비밀 파일을 읽는 프로세스만 는다.

## 결과

- `qsh-transport`의 서버 endpoint 생성 함수가 `EndpointConfig::default()` 대신 주입된 키로 `EndpointConfig`를 만든다. 클라이언트 endpoint와 testkit의 raw quinn 경로는 `default()`를 유지한다. wire 변경은 0이고 RFC 9000 §10.3을 따른다.
- `docs/CLI.md` §6.12·§6.13에 키 파일과 두 기동 진단(넓은 권한, 읽기 실패)을 적는다. 진단 문면에는 키 바이트가 없다.
- `docs/design/threat-model.md` §4 D에 "reset key 유출로 경로 밖에서 연결을 끊는다" 행이 오른다. 통제는 0600 파일, 로그·audit·진단 금지, 파일 삭제로 하는 회전이다. §4 G에는 재시작 뒤 감지 지연이 1 RTT로 줄어드는 행이 오르고 읽기 실패 동안에는 오늘과 같다는 잔여 위험을 적는다.
- `docs/deploy/service.md`의 재시작 고지 문단에 재시작 뒤 클라이언트가 곧바로 단절을 안다는 사실과 그 전제(키 파일이 정상)를 더한다. `docs/design/protocol.md` §10의 재시작 감지 서술과 README Known limitations의 해당 문장도 같이 고친다.
- `docs/design/reexec-estimate.md`에는 H1b가 착지한 커밋을 가리키는 추기 한 줄만 더한다.
- `qsh.cli/v1` JSON, fixture, `ErrorCode`, doctor 진단 코드 수는 바뀌지 않는다. 읽기 실패를 doctor finding으로도 알릴지는 이 ADR의 범위 밖이고 필요해지면 새 진단 코드로 따로 더한다.
- 재시작한 서버가 같은 UDP 포트를 다시 잡아야 reset이 클라이언트에 닿는다. 서버는 `SO_REUSEADDR`를 쓰지 않으므로(`docs/design/reexec-estimate.md` §1) 재시작 사이에 다른 프로세스가 그 포트를 잡으면 reset은 오지 않고 감지는 오늘처럼 늦는다. 이것은 잔여 위험으로 남긴다.
- 이 ADR이 승인되면 `docs/ROADMAP.md` M13 DoD (f)의 "골라 커밋에 적는다"가 이 문서로 채워지고 H1b 구현이 열린다.

## 추기 (구현, 213001f)

- 재시작한 서버가 reset을 보내려면 클라이언트가 쓰던 connection ID를 자기 것으로 알아봐야 한다. quinn의 기본 connection ID 생성기는 프로세스마다 키를 새로 뽑으므로, 같은 reset key만으로는 재시작한 endpoint가 그 패킷을 모르는 ID로 버린다. 구현은 생성기 키를 reset key에서 HMAC-SHA256과 별도 라벨로 파생한다. 둘째 파일은 없고 wire는 그대로다.
- 키 파일을 만들 수 없는 경우(설정 디렉터리가 없거나 쓸 수 없음)도 읽기 실패와 같이 다룬다. 이번 기동만 임시 키로 뜨고 같은 진단 한 줄을 낸다.
