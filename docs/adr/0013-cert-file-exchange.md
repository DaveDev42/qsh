# ADR-0013: 인증서 파일 교환을 프로비저닝 1급 경로로 승격한다(ADR-0002 개정)

날짜: 2026-09-09
상태: 승인됨

## 맥락

이 ADR이 승격하는 파일 교환 경로(결정 1, 8)는 2026-09-09에 사용자가 확정한 항목이다(`DECISIONS.md`). ADR-0002는 기본 pairing UX를 `qsh trust invite`가 발급하는 고엔트로피 일회용 invite code로 정하고, `qsh trust add --fingerprint`(연결 없는 수동 pin)를 "스크립트/프로비저닝용 1급 fallback"으로 유지한다고 결정했다. 이 결정은 신뢰를 맺는 두 당사자가 모두 `qsh trust invite` 또는 `qsh trust accept`를 부를 수 있다는 것, 즉 상환 창구를 쥔 쪽이 언제나 인바운드 연결을 받는 host라는 것을 전제로 쓰였다.

이 배제는 M9 개명이 새로 만드는 구멍이 아니다. `qsh serve`의 기동 경로에 invite 상환을 배선한 것은 M7 Step 4였고, 그때 이미 같은 상환 창구가 `qsh reverse`가 공유하는 `host_runtime`에는 없었다(`crates/qsh-core/src/serve.rs:60-66`의 주석: "ADR-0002 / M7 Step 4 … deliberately wired here in `run_serve`, not in the `host_runtime` `qsh reverse` also shares"). M9는 그 구멍을 새로 파는 대신, `qsh reverse <controller>`를 `qsh serve --to <listener>`로 개명하고 `qsh listen`을 유지함으로써(DECISIONS.md Q2) 사람이 실제로 부딪히는 시나리오로 끌어올릴 뿐이다. 이 구도에서 `qsh listen`은 인바운드 연결을 받는 쪽이지만 셸을 내주는 host가 아니라 그것을 원격에서 조작하는 client다. `SharedInviteStore::open`은 `crates/qsh-core/src/serve.rs:69`에서 `qsh serve`의 기동 경로에만 배선돼 있고, `crates/qsh-core/src/reverse/listen.rs`에는 이 store를 여는 코드가 전혀 없다. 같은 파일 3654~3656행의 주석이 이 사실을 명시적으로 적어 둔다. "`Listen` never sees `Principal::Pairing` (pairing is a `qsh serve`-only concept)". 결과적으로 target이 `qsh listen`을 신뢰하려는 시나리오(설계 §3 B)에서는 어느 쪽이 코드를 발급하고 어느 쪽이 상환하든 코드 pairing이 물리적으로 성립하지 않는다.

ADR-0002가 정한 신뢰 경로는 셋이다. invite code, fingerprint 수동 확인, 그리고 private CA(ADR-0008, `docs/PRD.md` §6). private CA 경로는 상환 창구 없이도 listener를 인증하지만, `cert issue`가 로컬 발급만 지원해 서명이 필요한 장비마다 `ca.key`를 복제해야 한다(이 한계와 해법은 ADR-0016으로 예약한다). CA를 아직 세우지 않은 배치에서는 남는 경로가 fingerprint 육안 대조 하나뿐이고, 이 경로는 사람이 SHA-256 fingerprint 전체 또는 축약형을 육안 대조해야 하는 원래 결점을 그대로 지니며, `identity export`가 만들어 낼 leaf PEM 파일을 그대로 옮기는 경로보다 프로비저닝 스크립트에 얹기 번거롭다.

이 ADR은 인증서 파일(leaf PEM) 교환을 invite code와 나란한 1급 프로비저닝 경로로 승격하고, 그 경로를 여는 두 명령 `identity export`와 `trust add --cert-file`의 계약을 정한다. `trust add-ca`는 같은 절에서 신설하지만 신뢰 근원을 여는 것이 아니라 이미 존재하는 `[[ca]]` 등재 작업(`TrustStore::add_ca`, `crates/qsh-core/src/trust/mod.rs:278`)의 CLI 프런트엔드일 뿐이므로 ADR-0002 개정 대상은 아니다. 오늘은 `cert issue`가 자기 CA 루트를 자동 등재하는 경로만 있고, 남의 CA 루트를 등재하려면 `trust.toml`을 손으로 고쳐야 한다.

## 결정

1. ADR-0002의 결정 문단 중 "Fingerprint 수동 확인(`qsh trust add --fingerprint`)은 스크립트/프로비저닝용 1급 fallback으로 유지한다(Ansible, cloud-init 등 사람이 개입하지 않는 경로)."를 다음과 같이 개정한다. "Fingerprint 수동 확인(`qsh trust add --fingerprint`)과 인증서 파일 교환(`qsh identity export` + `qsh trust add --cert-file`)을 스크립트/프로비저닝용 1급 fallback으로 유지한다(Ansible, cloud-init 등 사람이 개입하지 않는 경로, 그리고 `qsh listen`처럼 invite 상환 창구 자체가 없는 상대). 인증서 파일 교환은 fingerprint 수동 확인과 달리 사람의 육안 대조를 요구하지 않는다." ADR-0002의 다른 문단(근거, QR 코드, 중앙 pairing 서버 기각, 그리고 대안 절의 "대신 스크립트/헤드리스 경로의 1급 fallback으로는 유지한다")은 그대로 둔다. invite code가 기본이라는 결정 자체는 바뀌지 않는다.
2. 초대 코드는 시나리오 A(양쪽 다 `qsh serve`/`qsh init` 페르소나)의 기본으로 그대로 유지한다. TLS exporter 채널 바인딩(RFC 5705 `export_keying_material`)이 도청된 코드로도 재생·중계를 막는다는 ADR-0002의 근거는 인증서 파일 교환에는 적용되지 않는다. 인증서 파일을 손상된(도청·변조 가능한) 채널로 옮기면 그 파일이 진짜 상대의 것인지 보장할 방법이 파일 자체에는 없다. 그래서 파일 교환은 코드 pairing의 대체가 아니라, 코드 pairing이 애초에 닿지 않는 상대(listener)를 위한 별도 경로다.
3. `identity export [--out <path>]`를 신설한다. `qsh identity`는 신설 명령 그룹이다. 오늘 `identity.init`은 `qsh init`으로만 노출돼 있고(`docs/CLI.md` §6.11) 최상위에 `identity` 서브커맨드가 없다(`crates/qsh-cli/src/cli.rs`의 `Command` enum에 `Init`은 있어도 `Identity`는 없다). `identity export`는 이 그룹의 첫 구성원이고, 기존 `qsh init`과의 관계(그대로 두는지, `qsh identity init`을 별칭으로 더하는지)는 이 ADR이 결정하지 않는다. human 모드에서는 이 장치의 leaf 인증서 PEM 하나만 표준출력(또는 `--out`이 가리키는 파일)에 낸다. `--json`/`--jsonl` 모드에서는 원시 PEM을 stdout에 그대로 내지 않는다. `docs/CLI.md` §2.2("stdout: 요청한 결과 또는 JSONL event만 출력")와 machine-mode stdout 각 줄이 순수 JSON이어야 한다는 계약 아래, PEM은 `IdentityExportData`의 필드(`cert_pem`)로 envelope 안에 실린다. `--out`을 쓰면 두 모드 모두 결과에는 파일 경로만 남고 PEM 본문은 stdout에 나오지 않는다. 결정 6의 `qsh identity export | ssh box 'qsh trust add laptop --cert-file -'` 관용구는 human 모드 전용이며, 자동화가 이 관용구에 `--json`을 붙이면 파이프에 PEM이 실리지 않는다는 것을 문서에 명시한다.
   소스는 `identity/device.pem`(`crates/qsh-core/src/identity/mod.rs:36`의 `CERT_FILE`)이다. 이 파일이 leaf 하나로만 쓰인다는 것은 읽기가 아니라 쓰기 경로에서 온다. `qsh init` 시 `mod.rs:138` 부근이 `generated.cert_pem`을, CA 승격 시 `promote_to_ca_issued`(`mod.rs:288` 부근)가 CA 서명본 `cert_pem`을 각각 파일 전체로 덮어쓴다. 읽기 쪽(`mod.rs:333` 부근의 `pem::decode_first(pem::CERTIFICATE, &text)`)은 여분 블록이 있어도 첫 블록만 조용히 취하므로, 단일 블록 보장은 쓰기가 지키는 불변식이지 읽기가 검증하는 것이 아니다. 개인키는 `device.key`(`crates/qsh-core/src/identity/mod.rs:38`의 `KEY_FILE`) 또는 `--key-store platform`/`auto`일 때는 OS credential store(`identity/mod.rs:345,358`)에 있으며, `identity export`를 포함해 어떤 명령도 이 경로를 인자로도 출력으로도 놓지 않는다. `identity export`는 `device.pem`만 읽고 `KeyStore`를 열지 않는다. identity가 아직 없으면 기존 `read_identity` 경로대로 `CONFIG_ERROR`("no local identity; run `qsh init` first", `identity/mod.rs:275`)를 낸다. `--out`이 기존 파일과 겹치면 조용히 덮지 않고 거부한다. 산출물은 공개값(leaf 인증서)이라 파일 권한을 0600으로 강제할 필요는 없다.
4. `trust add <name> --cert-file <pem|->`를 신설한다(`--address`는 `--fingerprint` 경로와 마찬가지로 선택이다. `docs/CLI.md` §6.11, `Ops::trust_add`는 fingerprint가 있으면 address를 요구하지 않는다). `-`는 표준입력에서 읽는다는 뜻이다. 입력은 `CERTIFICATE` PEM 블록을 정확히 하나만 담아야 하고, `CERTIFICATE` 외의 PEM 블록(특히 `PRIVATE KEY`)이 하나라도 섞여 있으면 거부한다. `pem::decode_all`(`crates/qsh-core/src/identity/pem.rs`)로 `CERTIFICATE` 블록 수를 세어 2개 이상이면(체인·번들) `INVALID_ARGUMENT`(`qsh_proto::ErrorCode::InvalidArgument`, `crates/qsh-proto/src/error.rs:37`)로 거부한다. 블록이 0개면 `decode_all`이 이미 내는 `PemError::NoBlock`을 같은 코드로 옮긴다. `PRIVATE KEY` 블록이 섞여 있으면 파싱 실패와 같은 취급으로 `INVALID_ARGUMENT`를 내되, 오류 문면과 감사 기록 어디에도 입력 내용을 되비추지 않는다. 결정 3이 세우는 "개인키는 어느 명령의 인자로도 오르지 않는다"는 계약을 이 검증이 우회 가능하게 두지 않기 위해서다.
   통과하면 이 leaf에서 fingerprint(SPKI SHA-256, `crates/qsh-transport/src/identity.rs`)를 계산해 `TrustStore::add_peer`(기존 `trust.add` 경로)로 pin한다. `--cert-file`은 기존 `--fingerprint`와 상호 배타이며, 이름(`name`) 생략은 허용하지 않는다(기존 `TrustAddArgs::name`이 이미 필수 위치 인자다. 이 필수 자체는 ADR-0014 결정 10이 이미 유지하기로 기록했으므로 여기서 다시 결정하지 않는다). 이름이 이미 다른 fingerprint로 pin돼 있으면 `--cert-file` 경로도 기존 `--fingerprint` 경로와 동일하게 무동작이다(`TrustStore::add_peer`, `trust/mod.rs:230-233`: 이름이 있고 fingerprint가 다르면 `created=false, updated=false`로 성공을 반환한다). 재바인딩은 `trust remove` 후 `trust add`다. pin은 인증서 전체가 아니라 SPKI 위에 걸리므로(`crates/qsh-transport/src/identity.rs:23-24`, "survives cert re-issuance with the same key") `cert issue`로 같은 키에 재발급해도 pin은 유지되고, 키 자체를 바꿀 때만 위의 무동작 사례에 해당한다. `--cert-file`은 유효기간을 검사하지 않는다. 만료는 handshake에서 강제된다. 결과 모양은 fingerprint 수동 pin과 동일하다.
5. `trust add-ca <name> --cert-file <pem|->`를 신설해 `[[ca]]`의 수기 편집을 없앤다. 로직은 이미 있는 `TrustStore::add_ca(name, cert_pem)`(`crates/qsh-core/src/trust/mod.rs:278`, `cert issue`가 자기 CA 루트를 등재할 때 쓰는 것과 같은 함수)를 호출하지만, 오퍼레이터 입력을 받는 호출자를 새로 붙이는 이상 그 함수의 기존 문서 주석(같은 파일 274~277행)이 서 있는 전제가 깨진다. 그 주석은 이름이 같고 `cert_pem`이 다를 때의 제자리 덮어쓰기(`updated=true`)를 "이것은 같은 이름 아래 CA를 로컬에서 재-init할 때만 생기며, 여기 어떤 코드도 이름이 같다는 이유만으로 원격 루트를 가져오거나 신뢰하지 않는다"로 정당화하는데, `trust add-ca`가 오퍼레이터가 준 이름과 PEM을 그대로 넘기면 이 전제가 더는 성립하지 않는다. 그래서 `trust add-ca`는 `add_ca`를 그대로 두지 않고, 이름이 이미 있고 저장된 `cert_pem`과 다르면 확인 없이 덮어쓰지 않고 `INVALID_ARGUMENT`로 거부한다. 같은 이름의 CA를 교체하려면 `trust remove`로 먼저 지워야 한다. ADR-0008 결과의 "`[[ca]]` 등재는 additive·append-only"라는 문장(`trust/mod.rs:262-265`가 인용)은 `cert issue`의 로컬 재-init 경로에는 그대로 적용되고, `trust add-ca`가 새로 여는 오퍼레이터 입력 경로에서는 append만 허용하고 update는 허용하지 않는 것으로 갈라진다.
   `--cert-file`의 leaf 단일 검증(결정 4)과 달리 CA 루트는 self-signed 단일 인증서이면 되고 체인 검증은 하지 않지만, 구조 검증은 결정 4와 같은 규율을 적용한다. `decode_all`로 `CERTIFICATE` 블록 수를 세어 정확히 하나가 아니면 `INVALID_ARGUMENT`로 거부하고, 등재 전에 DER을 X.509로 파싱해 실패하면 같은 코드로 거부한다. `TrustStore::parsed_cas`(`trust/mod.rs:319`)는 저장된 `cert_pem`에 `pem::decode_first`를 걸어 블록이 여러 개면 첫 블록만 앵커로 남기고, 파싱 실패는 등재 시점이 아니라 로드 시점에 `WARN` 한 줄로만 흘러간다("ignoring CA entry with unparsable PEM"). 등재 시점에 검증하지 않으면 `trust add-ca`는 성공을 보고하고 CA 경로는 조용히 죽은 상태가 남는다.
   `trust add --cert-file`의 `<name>`은 그 자체가 `device:<name>` principal이고(`crates/qsh-cli/src/cli.rs`의 `TrustAddArgs::name` doc: "also the `device:<name>` principal it authenticates as"), leaf의 SAN을 보지 않는다. 반면 CA path는 leaf의 SAN URI에서 principal을 뽑으므로(`crates/qsh-transport/src/tls.rs:269-270`, `principal_from_san`), `trust add-ca <name>`의 `<name>`은 `[[ca]]` 항목 라벨일 뿐 principal이 아니고, 그 CA가 서명한 어떤 leaf든 자기 SAN이 자칭하는 principal로 인증된다. `trust add-ca`는 이름 결정권을 CA에 위임하는 행위이고, 이것이 두 명령을 같은 절에서 다루면서도 결정 6의 비목표가 `add-ca`에는 다르게 적용되는 이유다. 이름 생략은 마찬가지로 허용하지 않는다.
6. 비목표로 명시한다. 인증된 대역 외 채널 없이 pin하는 경로를 기본값이나 플래그로 만들지 않는다. `qsh identity export | ssh box 'qsh trust add laptop --cert-file -'`는 통과한다. 이 파이프의 신뢰 근거는 qsh가 아니라 ssh known_hosts에서 온다(전달 경로 자체가 이미 인증돼 있다). 일반 TOFU와 pin 방향 축(inbound/outbound 구분)은 ADR-0017 결정 5의 소관이다. 여기서 거절하는 것은 파일 교환 경로에 붙는 `--trust-on-first-use` 부류의 플래그뿐이며, 그런 플래그는 인증서 파일 교환이 코드 pairing 대신 요구하는 유일한 것(전달 채널의 인증)을 플래그 하나로 면제해 버린다.
7. 주소를 코드 토큰에 합치는 안을 기각한다. invite code에 `host:port`를 인코딩해 `trust accept`가 dial까지 자동으로 하게 만드는 안은 결정 2가 유지하는 "코드 pairing은 시나리오 A 전용, listener는 파일 교환"이라는 역할 분리를 흐린다. 코드 표면을 넓히는 대신 listener 문제(코드 상환 창구 부재)는 여전히 풀리지 않는다.
8. history 문제(셸 히스토리에 코드가 남는 것)는 파일 교환이 아니라 코드 pairing 쪽 결함이지만, 같은 라운드에서 함께 고정한다. `pair accept`(ADR-0012가 `trust accept`를 개명)의 `code` 위치 인자를 선택으로 바꿔, TTY 표준입력이면 에코 없는 프롬프트로 받고, 파이프(비-TTY)면 `--code-stdin`으로 표준입력을 끝까지 읽어 앞뒤 공백을 제거한 값을 코드로 쓴다(`qsh_proto::pairing::parse_invite_code`가 Crockford 심볼 외 문자를 거부하므로 후행 개행을 그대로 넘기면 첫 시도부터 실패한다). `--json`/`--jsonl` 모드에서는 인터랙티브 prompt를 열지 않는다. `docs/CLI.md` §2.1이 machine-readable mode에서 "추가 입력이 필요한 경우 prompt 대신 `TRUST_REQUIRED` 또는 `INVALID_ARGUMENT` 오류를 반환한다"고 못박은 것을 그대로 따른다. 코드 인자도 `--code-stdin`도 주어지지 않고 `--json`/`--jsonl`로 부르면 `INVALID_ARGUMENT`를 반환한다. fingerprint는 공개값이라 로그나 히스토리에 남아도 위험이 아니라고 도움말에 적는다. 소비된 코드(또는 만료된 코드)는 `INVITE_TTL`(`crates/qsh-core/src/trust/pairing.rs:64`, 10분) 1회용이라는 기존 제약 때문에 셸 히스토리에 남아도 재사용할 힘이 없다는 것도 같은 줄에 적는다.

listener를 상대로 한 코드 pairing 자체(상환 창구를 `qsh listen`에도 열지, 연다면 신뢰 방향을 누가 갖는지)는 이 ADR이 결정하지 않는다. ADR-0015로 예약한다. `cert issue`가 로컬 발급만 지원해 CA 키를 서명이 필요한 장비마다 복제해야 하는 한계(결정 5가 다루는 CA 루트 등재와는 다른 문제로, 발급 권한 자체의 문제다)와 그 해법인 CSR 흐름은 ADR-0016으로 예약한다. doctor가 CA 등재는 성공했는데 `acl.toml`의 `auth_path = "ca"` 설정이 없는 상태를 잡아내는 진단(`acl_ca_auth_path_missing`류, 오늘 저장소에는 없는 신설 대상)의 명세는 ADR-0017 몫이다.

## 결과

- 신규 op는 `identity.export`, `trust.add_ca` 둘이다(op 이름 표기는 `docs/CLI.md` §2.4가 지금까지 쓴 dotted-lowercase 관례를 따르되, 이 관례에 복합어 segment 선례가 없어 `trust.add_ca`/`trust.addca` 중 확정은 CLI.md §2.4 개정 시점에 고정한다). 각각 `qsh-proto::types`에 `IdentityExportData`/`TrustAddCaData` schemars 타입을 추가하고, `qsh-proto::schema::cli_v1_data_schema`에 대응 `match` arm을, `CLI_V1_SCHEMA_COMMANDS`(`crates/qsh-proto/src/schema.rs:23`)에 정렬된 이름을 추가해야 한다. 이 목록에서 `cli_v1_data_schema`로 가는 방향의 누락은 `every_registered_command_has_a_schema`(`schema.rs:104`)가 잡지만, `Operation` impl과 `const COMMAND`(`crates/qsh-core/src/ops/`)를 만들고도 위 두 목록에 등록하지 않는 반대 방향의 누락은 그 테스트가 못 본다. 양방향 완전성은 별도 통합 테스트 `crates/qsh-core/tests/schema_commands_registry.rs`가 게이트한다. `trust.add`는 기존 op를 그대로 쓰되 `--cert-file` 입력 시의 실패 모드(`INVALID_ARGUMENT`)만 늘어난다. 새 op가 아니다.
- 각 신규 op는 `crates/qsh-cli/src/render/human.rs`와 `render/json.rs` 양쪽에 렌더러 분기가, `docs/CLI.md` §6.11에 문서 행이, §2.5의 "인가 불요" 행(오늘은 `identity.init`만 이름으로 열거한다)에 `identity.export` 추가가, `docs/man/`에 `qsh-identity-export.1`과 `qsh-trust-add-ca.1`(기존 `qsh-cert-init.1` 등 하이픈 연결 관례를 따름, `qsh identity` 그룹 자체의 `qsh-identity.1`도 함께)이, `docs/PRD.md` §11(명령 체계 표에 `qsh identity export`·`trust add-ca` 행)과 §6(신뢰 설정 경로 열거에 파일 교환 추가)에 반영이 필요하다. 시나리오 B(설계 §3)의 본문은 이 두 명령의 실제 호출 두 줄(양방향이므로 왕복 네 줄)로 CLI.md와 README에 실린다.
- `crates/qsh-cli/tests/fixtures/cli-v1/`의 append-only 규칙에 따라 `identity.export`·`trust.add_ca`·`trust.add`(cert-file 경로) 각각의 새 JSON fixture를 추가한다. 기존 `trust.add` fixture는 손대지 않는다. 새 fixture 파일 이름은 `crates/qsh-cli/tests/fixtures.rs`의 `REQUIRED_FIXTURES` 상수(77행)에도 등록해야 `every_required_fixture_exists`가 그것을 요구한다. fixture 파일만 추가하고 이 상수를 갱신하지 않으면 아무 테스트도 누락을 잡지 않는다.
- CLI.md §6.11에 "초대 상환이 `qsh serve` 전용이라 `qsh listen` 상대로는 코드 pairing이 안 된다"는 문장과 그 대체 경로(이 ADR의 파일 교환)를 명시한다. §6.13(`qsh listen`/`qsh reverse` 절, ADR-0012가 `qsh serve --to`/`qsh listen`으로 개명)에서도 이 한계를 상호 참조한다. README의 Known limitations에도 "listener는 코드 pairing 대상이 아니다"를 한 줄 추가한다(설계 §3 B).
- `docs/adr/README.md` 색인에 0013 행을 추가한다.
- `identity export`가 나오면 "개인키는 어느 명령에도 인자로 안 오른다"는 문장이 처음으로 CLI 계약에 명문화된다. 지금까지는 이것이 코드 사실(어떤 명령도 `device.key`/`KeyStore`를 인자·출력 경로에 놓지 않는다)이었을 뿐 계약 문서 어디에도 문장으로 없었다. ADR-0002 파일 자체에는 이 개정을 가리키는 포인터를 남기지 않는다. 개정본 문장으로 원문을 직접 교체하므로, ADR-0002를 단독으로 읽어도 옛 문장은 남지 않는다.

## 대안

- fingerprint 수동 확인만으로 listener 프로비저닝을 커버한다: 기각. `qsh listen`을 처음 신뢰할 때도 사람이 SHA-256 fingerprint 전체 또는 축약형을 육안 대조해야 하는 ADR-0002의 원래 결점이 그대로 남고, 여러 대를 한 번에 세팅하는 프로비저닝 스크립트에서는 fingerprint 문자열을 안전하게 전달하는 것 자체가 인증서 파일을 전달하는 것과 난이도가 같다. 파일이면 기존 파일 전송 채널(ssh, 사내 배포 시스템)을 그대로 쓸 수 있는데, fingerprint 문자열은 별도 out-of-band 채널이 필요하다.
- `qsh listen`에도 invite 상환 창구를 연다: 기각(이 ADR에서는). `SharedInviteStore`를 host·listener 두 프로세스 종류에서 열리게 만드는 일과 "누가 코드를 발급하고 누가 상환하는가"라는 신뢰 방향 재설계가 함께 필요해 이 ADR의 범위(파일 교환 두 명령)를 크게 넘는다. ADR-0015로 예약해 별도로 다룬다.
- 주소를 코드 토큰에 합쳐 `pair accept`가 dial까지 한 번에 하게 만든다: 기각. 결정 7에 적은 대로 코드 표면만 넓히고 listener 문제는 풀리지 않으며, 코드 안에 주소가 들어가면 코드 자체가 더 길어져 history 문제(결정 8)도 오히려 악화된다.
- `--trust-on-first-use` 플래그를 추가해 파일 교환 없이도 처음 본 인증서를 바로 믿게 한다: 기각. 결정 6에 적은 대로 이 ADR이 파일 교환에 요구하는 유일한 안전장치(전달 채널이 인증돼 있어야 한다)를 플래그 하나로 면제하는 것이라, "인증된 대역 외 채널 없이 pin하는 경로를 기본값이나 플래그로 만들지 않는다"는 비목표에 정면으로 위배된다.
- `identity export`가 leaf 대신 체인 전체(leaf + CA 루트)를 낸다: 기각. `trust add --cert-file`의 검증(결정 4)을 "leaf 하나"에서 "체인 중 leaf만 골라내기"로 복잡하게 만들 뿐 이득이 없다. CA 루트가 필요한 경우는 `trust add-ca`(결정 5)라는 별도 명령으로 이미 커버된다. 두 신뢰 근원(leaf pin, CA 루트)을 한 출력에 섞으면 받는 쪽이 무엇을 pin하는지 명령 하나로 판단하기 어려워진다.
- `trust add-ca`가 기존 이름에 다른 PEM이 오면 `add_ca`의 원래 동작대로 조용히 덮어쓴다: 기각. 결정 5에 적은 대로 `add_ca`의 덮어쓰기 정당화(로컬 재-init에서만 발생)는 오퍼레이터 입력 호출자 앞에서 깨진다. 신뢰 앵커 교체를 이름 재사용만으로 통과시키면 다른 CA를 같은 라벨로 밀어 넣는 경로가 확인 없이 열린다.
