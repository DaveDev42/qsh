# SC1 스톱워치 캠페인 하네스

`docs/campaigns/m7-stopwatch.md`가 요구하는 "한 번도 설정한 적 없는 두 장비"를 회차마다
새로 만들고 버리기 위한 컨테이너 한 쌍이다. 캠페인 문서가 기준이고 이 디렉터리는 그
기준을 만족하는 환경을 준비할 뿐이다 — 판정 기준을 여기서 다시 정의하지 않는다.

## 이 하네스가 하는 일과 하지 않는 일

**한다.** 컨테이너 두 개를 bridge 네트워크에 띄우고, 각각의 홈 디렉터리를 회차마다
비우고, §3의 여섯 전제 조건을 실제로 검사해서 하나라도 어긋나면 타이머를 시작하지
말라고 알린다. 예행이 걸렸던 세 가지(포트를 선점한 leftover `qsh serve`, PATH 앞쪽의
구버전 `qsh`, 잔존 프로세스)가 검사 항목에 들어 있다.

**하지 않는다.** 측정은 자동화하지 않는다. §9가 이미 그 이유를 적어 뒀다 — 예행에서
스크립트가 fingerprint를 파싱해 대신 채우는 바람에 사람 시간이 0으로 잡혔고, 그건
실측이 아니라 과소측정이었다. 300초 예산은 사실상 전부 사람 시간이므로, 사람이 읽고
치지 않으면 SC1을 잰 것이 아니다.

## 한 회차 돌리기

```bash
scripts/stopwatch/round.sh 1
```

작업 트리를 그대로 빌드하므로 측정 대상은 published release가 아니라 지금 커밋이다.
스크립트가 전제 조건을 통과시키면 진행자에게 두 개의 `docker exec` 명령을 출력한다.
그 둘을 화면 분할로 나란히 띄우는 것이 §4가 고정한 배치다. compose는 쓰지 않는다 —
별도 플러그인이라 이 리포가 붙는 daemon마다 있으리라는 보장이 없고, 컨테이너 두 개에
필요하지도 않다.

회차가 끝나면:

```bash
docker rm -f qsh-sw-host qsh-sw-client && docker network rm qsh-stopwatch-net
```

## 컨테이너를 쓸 때 실장비와 달라지는 점 — 진행자가 알고 선택해야 한다

§3은 VM·컨테이너·실장비를 모두 허용하지만, 셋이 같은 것을 재지는 않는다. 이 이미지에서
달라지는 것은 하나다.

**OS 자격 증명 저장소가 없다.** 컨테이너 안에는 Secret Service도 Keychain도 없어서
`qsh init`이 keystore 파일 fallback으로 내려간다. 실제 macOS나 데스크톱 Linux에서는
같은 명령이 자격 증명 저장소에 항목을 쓰고, macOS에서는 프롬프트가 뜬다(§9가 잡은
부작용이 이것이다). 그 프롬프트를 처리하는 시간이 컨테이너 회차에서는 0이다.

즉 **컨테이너 회차는 실장비 회차보다 관대한 조건**이고, 여기서 5분을 넘긴다면 실장비는
확실히 넘긴다. 반대 방향은 보장되지 않는다. SC1을 "사용자가 실제로 겪는 최초 연결"로
읽는다면 최소 1회차는 실장비 두 대로 하는 편이 취지에 맞다. 어느 쪽을 택하든 §8 기록표의
"격리 방식" 행에 사실대로 적고, 컨테이너로 돌렸다면 이 문단을 근거로 그 사실을 함께
남긴다 — 조건을 유리하게 고른 것을 감추지 않는다.

`dave` 계정은 이미지가 만들어 둔다. README "First run"의 마지막 명령이 `qsh dave@box`이고
`user@`는 `qsh serve`를 실제로 돌리는 계정과 일치해야 하므로, 그 문면이 성립하려면
계정이 실재해야 한다.
